# Boot validity, flash lifecycle, and object-15 reachability

> **Scope:** Sienna EPS `8965B4512000`
>
> **Document type:** subsystem analysis
>
> **Status:** active
>
> **Evidence profile:** mixed — claims carry individual grades; see FINDINGS ARCH-003
>
> **Canonical artifacts:** —
>
> **Verification:** `tests/verify_boot_trust.py`
>
> **Related:** [firmware-architecture](firmware-architecture.md), [payload-gate](../security/bootloader-payload-gate.md)

This report completes the statically recoverable boot-trust analysis for
China-market Sienna EPS firmware `8965B4512000`. It documents the four-check
handoff gate, the validity-marker and CRC-descriptor machinery, the
flash-operation lifecycle reached on failure or reprogram, and the exhaustive
caller proof that SecOC triplicate object 15 (namespace-`0x100` index `0x10F`)
has no static producer in this calibration.

Addresses are CodeFlash virtual addresses. Raw-image checks are in
`tests/verify_boot_trust.py`; the deterministic caller census is generated by
`tools/generate_object15_reachability.py` into
`data/object15_reachability.csv` and `data/object15_reachability_summary.json`.

## 1. Handoff gate

`boot_application_handoff` at `0x13B0` is the single gate between boot and
application execution. It calls four setup/check functions in a fixed order,
then evaluates the integer result of the validity check at `0x119E`:

```c
// 0x13B0 — decompiled
FUN_00000c9a();          // setup #1
FUN_00000e54();          // setup #2
FUN_00000f80();          // setup #3
FUN_000010c6();          // setup #4
iVar4 = FUN_0000119e();  // validity gate
if (iVar4 == 0)
    (*application_entry_pointer)();   // indirect call of *(0xFFDB8) = 0x20880
else {
    FUN_00001206();                   // failure prologue
    // ... clear status array ...
    FUN_00001398();                   // failure main loop
}
```

The success path reads the 32-bit entry pointer at CodeFlash `0xFFDB8`
(obtaining `0x00020880`) and calls it indirectly. The four `jarl` call sites
at `0x13B4`, `0x13B8`, `0x13BC`, `0x13C0` encode the fixed setup order, and
the validity-check `jarl` is at `0x13C4`. These encodings are pinned in
`verify_boot_trust.py`.

On failure the function writes a status byte and clears an array, then enters
`FUN_00001398` — a non-returning failure main loop. The handoff function
itself ends in an unconditional `do { } while(true)` so that neither the
success nor failure path can return to its caller.

## 2. Validity decision tree (`0x119E`)

The gate function runs two retry-bounded phases, each with a ceiling of three
attempts (loop counter compared against `2`):

### Phase 1 — CRC descriptor verification

```c
// 0x119E — decompiled
uVar4 = 0;
while (true) {
    iVar2 = memory_crc_verify_descriptors(1);   // region 1
    iVar3 = memory_crc_verify_descriptors(0);   // region 0
    bVar1 = (iVar2 != 0) || (iVar3 != 0);
    iVar2 = FUN_0000115a();                     // flash status helper
    if (!bVar1 && iVar2 == 0) break;            // both CRCs pass + flash idle
    uVar4++;
    if (2 < uVar4) return 1;                    // give up → failure
}
```

`memory_crc_verify_descriptors` checks the per-region CRC embedded in flash
against a live computation. `FUN_0000115a` (`0x115A`) is a flash-sequencer
status helper: it polls the flash status register at `0xFFD62034` (the P1M-E
FCU command/examine register window), returns non-zero if a flash error bit
(OR of bit 0 and bit 2 of the status snapshot at `0xFFC62030`) is set, and
writes the `0xA5` flash examine-code sequence before re-reading. A non-zero
return forces the loop to retry.

### Phase 2 — validity-marker comparison

```c
// continuation of 0x119E
uVar4 = 0;
while (true) {
    iVar2 = FUN_00006c5a(0xffe00);                       // region 1 marker @0xFFE00
    iVar3 = FUN_00006c5a(&codeflash_region0_validity_marker); // region 0 @0x17E00
    if (iVar2 == 0 && iVar3 == 0) break;                 // both markers present
    uVar4++;
    if (2 < uVar4) return 1;
}
return 0;   // success
```

`FUN_00006c5a` at `0x6C5A` is a one-line marker predicate:

```c
bool FUN_00006c5a(int *param_1) {
    return *param_1 != 0x5aa5a55a;
}
```

The validity marker value is `0x5AA5A55A`. It is written by
`program_region_validity_marker` (RID `0x10F2`, the write path embeds the
immediate at the programming routine) and checked at both marker domains.
The gate returns `0` (success) only when both CRC regions verify and both
markers are present.

## 3. Region table, CRC descriptors, and marker domains

Three region descriptors at `0x8E00` define the validity-checked ranges:

| Region | Data range | Data end | Marker addr | Marker value |
|---|---|---|---|---|
| 0 (low CodeFlash) | `0x10000..0x17DFF` | `0x17DF0` | `0x17E00` | `0x5AA5A55A` |
| 1 (high CodeFlash) | `0x18000..0xFFDFF` | `0xFFDF0` | `0xFFE00` | `0x5AA5A55A` |
| 2 (RAM payload) | `0xFEBF0000..0xFEBF0FFF` | `0xFEBF0FF0` | `0` (null) | n/a |

Each CodeFlash region also has a CRC descriptor (base `0x8DD0`) recording the
data base address, length, and the embedded address/length fields that the CRC
verifier reads:

| Region | Desc base | Data | Len | Emb addr | Emb len |
|---|---|---|---|---|---|
| 0 | `0x8DD0` | `0x10000` | `0x7DF0` | `0xFFDD0` | `0xFFDD4` |
| 1 | `0x8DE0` | `0x18000` | `0xE7DF0` | `0xFFDE0` | `0xFFDE4` |

The embedded address/length fields at `0xFFDD0`/`0xFFDE0` match their
descriptors. The application vector base `0x20000` falls inside region 1 only,
confirming it is covered by the high-flash CRC and marker.

Both marker domains currently hold `0x5AA5A55A` in this calibration, so the
marker phase passes. Region 2 (the RAM payload window) has a null marker field
and is not marker-checked — it is the authenticated RAM region managed by the
payload gate (`../security/bootloader-payload-gate.md`).

## 4. Flash lifecycle on failure

When the validity gate returns non-zero, `boot_application_handoff` calls
`FUN_00001206` (`0x1206`) which zeroes three CAN/frame-control registers at
`0xFFFEE980/982/988`, then enters the failure main loop `FUN_00001398`:

```c
// 0x1398 — decompiled
FUN_00001338();        // failure-loop setup
FUN_00007244(0);       // boot diagnostics / status
__enable_irq();        // interrupts on for flash task
do {
    FUN_0000137a();    // one failure-loop iteration
} while (true);
```

`FUN_0000137a` (`0x137A`) is the cyclic failure-loop body:

```c
DAT_febf2904 = 2;                     // set boot-state flag
FUN_0000078c();                        // periodic setup
flash_operation_task();               // @ 0x4428 — flash sequencer worker
bootloader_main_operation_release();  // release pending operation
memory_crc_verify_task();             // CRC task
```

This loop keeps the flash-operation and CRC tasks alive so that a diagnostic
re-flash session (UDS `0x34`/`0x37`, RID `0x10F2`) can program a new image and
write fresh validity markers. The markers are written by
`program_region_validity_marker`, which embeds the `0x5AA5A55A` immediate;
the next reset then re-runs the validity gate, which succeeds if both CRCs
verify and both markers are present.

The flash sequencer landmarks are:

- `flash_operation_task` `@ 0x4428` — the cyclic flash worker;
- `flash_program_start` `@ 0x4188` — initiates a program sequence;
- `flash_program_queue_bytes` `@ 0x4276` — queues data into the program buffer;
- the indirect callback dispatch at `0x4350`/`0x435E` (documented in
  `../security/bootloader-payload-gate.md` as the authenticated-flash-driver entry).

### 4.1 The failure runtime is also the normal programming-mode runtime

Two audit results refine the picture above (recovered by independent pseudocode
re-derivation against raw bytes; split-CodeFlash file offset == VA):

1. **Application-initiated programming enters this loop live.** When the
   application observes a programming request (predicate `FUN_00065E88`:
   programming requested and neither `0xA5` nor `0xFF` veto markers present),
   `FUN_00064EC8` clears the ICU-S marker RAM window
   `0xFFC0A000..0xFFC0A00C`, then calls `FUN_00009F00` ->
   `FUN_0000148E` (retained `{kind=0,id=7A1,session=2}` config record at
   `0x31914`) and jumps **directly** into `boot_failure_main_loop` (`0x1398`)
   without any CRC/validity failure and without a reset. The trailing
   `system_hard_reset()` in that path is unreachable.

   This live handoff also preserves the application's XCP/shadow payload window.
   `FUN_00064EC8 @ 0x64EE6` explicitly loads `r6 = 0x31914` before calling
   `0x9F00`; the nine-dword copy at `0x148E` therefore has a fixed CodeFlash
   source and is **not** an attacker-selected pointer. `0x9F00` establishes
   `SP=FEBE8000`, `GP=FEBF9800`, `TP=0x869C`, writes `MPM=0`, and calls
   `0x148E` without touching `FEBF7C00..FEBFFBFF`. The subsequent
   `0x1398 -> 0x1338` boot-runtime initialization likewise does not call
   reset-startup initializer `0x1404`; direct xrefs make `boot_reset_startup @
   0x1F2` its sole caller. The apparent `0x1426` `FEBF7C00` clear remains the
   CORR-067 zero-trip loop (`FEBF7C00 > FEBE7000`). Consequently bytes written
   into the XCP window immediately before `10 02` remain resident across the
   normal application-to-boot transition. This is a **retention primitive, not
   code execution**: no boot control-transfer consumer into that window is
   established here. `tests/verify_xcp_boot_handoff_retention.py` pins this
   composition directly from raw CodeFlash.

2. **Failure-loop setup arms diagnostics, but the two entry states are not
   equivalent.** `FUN_00001338` (the `0x1398` prologue) reaches
   `FUN_000069D2`, which sets the diagnostic master flag `DAT_febf2bd0` whenever
   retained config word0 at `0xFEBF2908` is `0x00` or `0xFF`. `FUN_00006A22`
   then initializes the DCM through `FUN_00005086`, which sets
   `uds_current_session = 1`. Only the normal application-to-PROGRAMMING
   retained path (`word0 == 0x00`) executes `FUN_00006504`; its
   `FUN_00005148 -> FUN_0000630C` pre-hook temporarily installs session 3 and
   clears the initializer delay before the retained request is injected as
   synthetic bootloader `10 02`. The failed-validity `word0 == 0xFF` branch
   does not call `FUN_00006504`; it remains in default session 1. This matters
   because `uds_diagnostic_session_control @ 0x614A` explicitly rejects a
   direct default-session `10 02` with NRC `0x7E`. UDS request processing in
   both cases is gated on the armed master flag at `0x6AAC`.

Consequence: a degraded ECU (failed validity, interrupted marker write) and a
healthy programming transition converge on the same long-lived bootloader /
DCM / flash-worker runtime, but **not on the same initial diagnostic session**.
The degraded path is DCM-armed in default session; the normal retained handoff
performs the synthetic transition into programming state. The mutation boundary
is unchanged: the same 20-entry SID table at `0x8E54` is present, every
erase/write/reset/RAM-exec path still requires SecurityAccess level 2
(`0xFEBF2B0F == 2`; writer census: only send-key success writes `2` —
SEC-BOOT-007), and no unauthenticated mutating path was recovered. Watchdog/reset
transitions likewise cannot preserve UDS privilege because sanitization in
`FUN_00005086` precedes IRQ enable at `0x1398`. See CORR-089.


## 5. Object-15 reachability (bounded negative)

The SecOC triplicate key-bearing object is index 15 in namespace `0x100`,
giving a full dispatch index of `0x100 | 15 = 0x10F`. The update dispatcher
`secoc_nvm_object_update` at `0x65CD8` selects a persistence namespace from
the high byte of its first argument:

```c
// 0x65CD8 — decompiled
param_1 &= 0xff;            // low byte = object index
uVar3 = param_1 & 0xff00;   // high byte = namespace
if (uVar3 == 0x000)  → FUN_000666a4   // checkpoint namespace
if (uVar3 == 0x100)  → secoc_nvm_redundant_object_update  // 0x66E48
if (uVar3 == 0x200)  → FUN_000660e0   // third configured namespace
```

The exhaustive caller census (`tools/generate_object15_reachability.py`)
enumerates every `UNCONDITIONAL_CALL` xref to `0x65CD8` and its thin wrapper
`0xFF09C`, recovers each object-index argument (literal `movea`, decompiler
trace, or bounded dynamic set), and records whether any static call selects
index `0x10F`.

### Result

**No static producer recovered.** Index `0x10F` is never statically selected
in this calibration. The observed namespace-`0x100` indices are
`0x100..0x103`, `0x105`, and `0x106` — index `0x10F` is absent. The census
covers:

- 27 direct callsites of `0x65CD8`;
- 19 wrapper callsites through `0xFF09C`;
- two dynamic-index maps: `0x53B70 → {0x14, 0x15, 0x17}`,
  `0x53EF2 → {0x12, 0x13}`;
- application `0xAB`/`0xBA` service callbacks have no call edge to
  `0x65CD8`/`0xFF09C`.

A raw-byte machine check confirms no `movea 0x10F,r6` encoding
(`20 36 0F 01`) lies within 64 bytes of any update callsite, and no callsite
prelude combines `mov 15,r6` with `movea 0x10F,r6`.

### Distinguished checkpoint object 15

Checkpoint namespace-0 object 15 (index `0xF`, the
`operating_state_snapshot`) is a different configured object and must not be
equated with the SecOC key. It has exactly two wrapper producers
(`0xBB482`, `0xBB5EC`) whose notes explicitly record "NOT SecOC".

### Descriptor

The redundant object-15 descriptor remains `length=32`, `base_block=41`,
`ram_mirror=0xFEBF02E8`. The related-variant SecOC key field maps raw
`0xFF206E14`, XOR55 `0xFF206D14`, XORAA `0xFF206C14`, RAM `0xFEBF02F8`.

### Scope

This is a single-image bounded negative. A provisioned unit, an external
gateway, or a dynamic-only producer (a register-computed index, a callback
table entry, or ICU-S-protected material) could select object 15 at runtime.
These remain explicitly out of scope for static analysis.
