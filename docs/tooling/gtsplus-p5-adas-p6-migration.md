# GTS+ P5 ADAS to P6 ADCU semantic migration

> **Scope:** current GTS+ NA/EU/JP master databases plus `LDA_P5`,
> `PCS1_P5`, `DSSystem_P5`, `Fr_RadSen_P5`, `RoadSign_P5`, `PCS2_P5`,
> `ADCU_P6`, and `ADCU_P6F` diagnostic databases/plugins; current P6 host
> Data List, per-DTC FFD, and RoB consumers across their regional bindings.
>
> **Status:** deterministic cross-generation census plus current-release native
> P6 Data List, per-DTC freeze-frame, and Record-on-Behavior semantic recovery.
>
> **Artifact:** `data/generated/gtsplus_2026/p5_adas_p6_migration.json`,
> generated by `tools/techstream/extract_gtsplus_p5_adas_p6_migration.py` and
> checked by `tests/techstream/verify_gtsplus_p5_adas_p6_migration.py`.

## 1. Why this comparison matters

Current GTS+ contains three useful ADAS generations at once:

1. the older distributed P5 stack built from `LDA_P5`, `PCS1/2_P5`,
   `DSSystem_P5`, `Fr_RadSen_P5`, `RoadSign_P5`, and the original front-camera
   family;
2. the category-498 `FRC_P5` TSS3 generation documented separately in the
   fleet map; and
3. generation-22 `ADCU_P6` / `ADCU_P6F`, where Toyota moves a very large ADAS
   diagnostic/recorder surface into an `ADAS Domain Controller`.

The point is not to label P6 as TSS3. It is to use Toyota's successor
vocabulary and grouping as an oracle for concepts that are ambiguous in the
preceding distributed systems.

## 2. The pre-498 P5 longitudinal/ADAS stack is a separate family

Current install-set joins show that the P5 categories most suggestive of
longitudinal ownership are **not part of category-498 FRC_P5 install sets**.
Instead they form older architectures of their own.

The clearest high-end stack is exact in NA:

`PCS1_P5 (427) + DSSystem_P5 (428) + Fr_RadSen_P5 (429) + RoadSign_P5 (431) + PCS2_P5 (432)`

It occurs in **35 install rows and exactly three model names: LS500, LS500h,
and MIRAI**.

The wider P5 fleet uses simpler combinations:

- `Fr_RadSen + RoadSign + PCS2`: 340 NA rows;
- `Fr_RadSen` alone among the selected categories: 275 NA rows;
- `Fr_RadSen + PCS2`: 25 NA rows.

This matters for TSS3 RE because it prevents a bad transfer: `DSSystem_P5` or
`PCS2_P5` naming can explain older Toyota control concepts, but those categories
are not themselves the category-498 TSS3 producer on current GTS+ install
sets.

## 3. P5 functional partition from Toyota's own diagnostic vocabulary

### Front radar (`Fr_RadSen_P5`)

The radar database is primarily a sensing/health/calibration endpoint. Its
monitors name, among other things:

- dirt detection separately for **PCS** and **Radar Cruise**;
- radar-cruise destination variation;
- front-radar temperature and heater state;
- horizontal/vertical optical-axis misalignment;
- internal microwave/antenna communication failures;
- communication error between Front Radar Sensor and System Control ECU.

That is strong evidence for a sensor/perception role.

### PCS output controller (`PCS2_P5`)

`PCS2_P5` is much closer to an output/request surface. Named monitors include:

- `LPB Request`
- `PB Request`
- `PBA Request`
- `PBH Request`
- `PBR Request`
- `FPB Request`
- `Warning Brake Request`
- `PCS Steering Request`
- `AVS Control Request`
- `VGRS Activation Request`
- multiple PCS warning/display/buzzer requests and invalid flags.

Its three routine Active Tests are PCS warning buzzer, reminder buzzer, and
PCS collision-avoidance assist.

### Lane controller (`LDA_P5`)

The older lane database exposes driver-torque input/cancel state, LDA control,
selected lane-center distance, and both torque-sensor and touch-sensor
"Not Holding Steering Wheel" judgments. Its two routines are steering-wheel
vibration and meter buzzer.

### `PCS1_P5`, `RoadSign_P5`, `DSSystem_P5`

`PCS1_P5` carries the seat-belt pretension/fitting-assist side of pre-collision
operation. `RoadSign_P5` owns traffic-sign/navigation fusion state.
`DSSystem_P5` has a small monitor surface but a dependency-heavy DTC graph,
consistent with a coordinating Driving Support System role in the LS/Mirai
stack.

## 4. P6 consolidates the recognition/planning recorder surface

Current GTS+ names categories 6037 and 6537 **ADAS Domain Controller**, both
generation 22. `ADCU_P6` is a much larger database than any single P5 peer:

- **1,645** deduplicated Data Monitor names;
- **183** DTCs;
- **22** routine Active Tests;
- **2,045** Record-on-Behavior data IDs;
- **501** RoB diagnostic codes;
- a separate DDR surface with **445 data IDs**, **1,797 freeze-frame rows**,
  and **1,165 invalid-condition rows**.

The keyword surface includes LTA/lane, PCS/brake-request, steering-control,
radar-sensing, road-sign, and cruise/longitudinal concepts in the same
controller. This is the semantic consolidation that makes P6 useful as a
cross-generation oracle.

`ADCU_P6F` is byte-identical in the relevant database payload and is emitted
as a reference to the P6 vocabulary rather than duplicating thousands of rows
in the generated artifact.

## 5. Diagnostic ABI continuity is deliberate

Toyota did not throw away the host diagnostic architecture when moving to P6.
The master DLL-role table keeps the same logical role IDs while swapping in P6
implementations:

| Role | P5 | P6 |
|---|---|---|
| `0x05` | `GetDatMonListP5_DT` | `GetDatMonListP6_DT` |
| `0x41` | `GetDatMonSignalInfoP5_DT` | `GetDatMonSignalInfoP6_DT` |
| `0x52` | `GetCID_SID22_DT` | `GetCID_SID22_P6_DT` |
| `0xA0` | `GetRoBP5_DT` | `GetRoBP6_DT` |
| `0xA1` | `DelRoBP5_DT` | `DelRoBP6_DT` |
| `0x19` | `DelDiagCodeP4` | `DelDiagCodeP6_DT` |

P6 then adds roles not used by these P5 peers, including routine Active-Test
initialization/signal-info (`0xAE/0xAF`), image-FFD detection (`0xD2`),
per-freeze-frame retrieval (`0xB5`), and a simple-operation utility result
(`0xB3`).

This stable host ABI is useful RE evidence: matching role numbers are a much
stronger guide to semantic continuity than DLL filenames alone.

## 6. Direct semantic continuations

Exact and near-name joins show Toyota carrying familiar P5 concepts into the
ADCU vocabulary. Examples from `PCS2_P5`:

- `LPB Request` -> `PCS LPB Request Flag`
- `PBA Request` -> `PCS PBA Request Flag`
- `PB Request` -> `PCS PB Request Flag` / the related LPB request family
- `PCS Function ON/OFF State` -> `PCS Function ON/OFF State Stored`

The P5 and P6 DTC dictionaries also retain numerous communication subjects,
including Brake System Control, front/rear Power Steering, Steering Angle
Sensor, ECM/PCM, IPC, restraints, TCM, telematics, and navigation.

At the same time, many P5 peer-module dependencies disappear from the P6
external dependency set while P6 gains direct camera/radar/link-oriented fault
vocabulary. That is consistent with **internalization of perception/planning
responsibilities**, but it is not sufficient by itself to claim a particular
P5 software function moved line-for-line into one P6 task.

## 7. Recorder evolution

The P5 databases already have `RecordOnBehavior` behavior codes/data IDs.
ADCU_P6 expands this into both a very large RoB dictionary and a separate DDR
(event-recorder) family. Recovered DDR trigger text includes examples such as:

- sudden braking history;
- sudden turning history;
- acceleration above a threshold;
- steering-angle-speed threshold exceeded;
- SOS button trigger.

Together with the PCS Data Viewer TSS3 dictionary, this reinforces a broader
Toyota design pattern: ADAS ECUs retain rich internal incident/state history
whose diagnostic representation is more semantically expressive than the
ordinary live Data List.

## 8. Boundaries for TSS3 work

- `PCS1/DSSystem/Fr_RadSen/RoadSign/PCS2_P5` are **not** category-498 TSS3
  install-set members in the current fleet census. Use their names as
  prior semantics.
- `ADCU_P6` is generation 22 and must not be relabeled "TSS3". It is a
  successor oracle.
- A same-name P5/P6 monitor establishes semantic continuity of Toyota's
  diagnostic vocabulary.
- Active Tests remain diagnostic routines; do not confuse their request path
  with the vehicle's normal ADAS command path.

For current TSS3 longitudinal work, the highest-value use of this artifact is
therefore **naming and hypothesis generation**: take a PCS/ACC/brake-request or
arbitration concept recovered from PCS Data Viewer/FRC recorders, then search
both the older P5 partition and P6 successor vocabulary to constrain likely
module role and state-machine meaning before touching firmware/CAN.

## 9. P6 Data List: admission and live acquisition

[Source-checked evidence](../../data/generated/gtsplus_2026/p6_data_list_semantics.json)
is regenerated with
`uv run python -m tools.techstream.extract_gtsplus_p6_data_list --recovered-root build/out/gts-all-unprotected/GTSPlus`.
It pins the current list/metadata plugins, installer-plaintext `CommandCommon`,
`DataMonitorPhase6_DT`, `DataListIF`, and conversion libraries, and retains
compact `ADCU_P6` / `Engine_CM_P6` raw-row, metadata, and request witnesses.

The P6 list enumerates **type 62**, not a union with type 157. Current P5 and
P6 callers both invoke `CCommCachePlusP5::CheckSupportPid`; their enabled-DID
acquisition is distinct. P6 starts with `22 A1 00`, interprets up to 32
MSB-first bitmap bytes, queries the selected `A1xx` pages, and derives actual
DIDs from their second-level bitmaps. The shared field gate requires enabled
primary DID membership, a successful read, and `end_bit < payload_length*8`.
Type-61 support modes 0/2 pass that length gate; mode 1 additionally checks the
end-bit-position mask in the **preceding payload byte**. Type-63 cross-DID
conditions and the final row `+0x4B` override are separate: 0 preserves the
support result, 1 forces visibility, other nonzero values hide the row.
`flags & 1` controls list emission; the recovered composite branch additionally
requires its type-26 dependencies. List merging preserves original row order.

Role `0x41` joins monitor `+0x3A` to type 13, its unit key to type 15,
and monitor `+0x42` to type 14. Those rows supply multiplier/divisor/offset,
sign mode, decimal precision, units, and converted-value pattern strings.
P6's native LSB adjustment is recovered, but no applicable regional database
contains type 64. The ordinary live reader is independently identified:
`DataListIF::CCommEventPhase6DM` builds **one `22 <DIDbe16>` request per DID**,
then copies response bytes after the three-byte `62 <DID>` header into
expected-length slots. Short payloads leave zero padding; excess bytes are
discarded. Optional dynamic-DID setup is a separate current P6 assembler path.

There are **104 role-05 P6 bindings per region**. Available NA/EU/JP databases
number **68/71/104**, with **27,923/28,110/44,302** type-62 row occurrences,
respectively; missing/blank database bindings remain explicit. In NA,
`ADCU_P6` has 1,647 type-62 rows versus 1,637 type-157 rows;
`Engine_CM_P6` has 1,488 versus 1,478. These counts are category-row occurrences,
not live-supported monitor counts. Native selection, metadata joins, and
ordinary request/response handling are recovered; exporting complete runtime
monitor catalogs and special-format UI presentation is separate work.

Independent offline execution of the native reader covered full, short, excess,
empty, and mismatched-DID payloads, checking slot bytes and request progression;
only the CRT `memcpy` operation was supplied by the harness. The native field
gates passed seven length-boundary cases and eight visibility-override cases.

## 10. P6 per-DTC freeze frames: selected records and DID lengths

[Source-checked evidence](../../data/generated/gtsplus_2026/p6_freeze_frame_semantics.json)
is generated by `tools/techstream/extract_gtsplus_p6_freeze_frame.py`.
Current `GetEachFrzFrmDatP6_DT` uses confirmed selector `0xCF` and predictive
selector `0xD0`, inserting DTC bytes at request offsets 2–4 and a selected
nonzero snapshot number at offset 5. Its parser requires the returned DTC to
belong to the selected list. P5's current parser instead supports repeated
snapshot headers and an all-record-first request with individual-record
fallback; the P6 path is selected-record-first.

P6's DID-length decision is **type 61 `+4` when nonzero**, otherwise an inline
u8 length below DID `0x9000` or an inline big-endian u16 length at/above it.
Fixed-length blocks have no inline length byte. The parser keeps the first
duplicate DID, treats count zero as scan-to-bounds, and preserves complete
earlier blocks when a later block is truncated. FFD membership is type-62
`flags & 2`, with the **alternate DID at `+0x48`**; type-80 conditions are
evaluated against DIDs in that snapshot. Types 157/156/89 are not merged into
this contract.

`ADCU_P6` has 601 FFD fields per region, all fixed-length; `Engine_CM_P6`
has 939/939/941 NA/EU/JP fields, including 73 inline-u16 fields per region
and 21 conditioned fields. Selector `0x13E` is a separate additional-info
path for current electrified-powertrain P6 categories, using type 171 and
native vehicle-family DID remapping. Its request/parser and condition helper
accept different vehicle-group sets; the artifact retains that discrepancy
and bounded raw witnesses rather than normalizing it into ordinary FFD.
The regional B5-bound census and all three length modes have database witnesses.

## 11. P6 Record-on-Behavior: independent acquisition and record parsing

[Source-checked evidence](../../data/generated/gtsplus_2026/p6_rob_semantics.json)
is generated by `tools/techstream/extract_gtsplus_p6_rob.py`.
P6 RoB does not use P5's `AB01/02/03` acquisition. It enumerates
`19 17 <status-mask> <memory>` (`59 17` response, DTCbe24/status entries),
then queries `31 01 D0 00 <DTCbe24> <memory>` after enabled-RID admission
for `D000`. Response format 0 returns byte frame IDs, fetched with
`19 18 <DTCbe24> <frame8> <memory>`; format 1 returns big-endian 32-bit
selectors and a fetch RID, used by
`31 01 <returned-RIDbe16> <framebe32>`. Frame IDs are sorted and deduplicated.
Memory selectors are `11/12/13`.

The RoB parser uses **type 90**, not type 151, for fixed lengths, with the
same fixed/u8/u16 threshold decision described in its native evidence.
Count-zero, truncation, and first-duplicate behavior are recovered for both
formats. Type 163 selects the enabled DTC/memory records; type 164 supplies
the 48-byte signal rows, type 89 supplies cross-DID support conditions, and
types 13/15/14 supply physical/unit/pattern metadata directly. This P6 RoB
consumer does not invoke the P6 LSB adjustment.

Native scalar extraction uses a **32-bit accumulator and x86 masked shifts**.
The current NCM P6/P6F catalogs contain 80-bit fields that therefore fold into
32 bits: bytes `00 01 02 03 04 05 06 07 08 09 0A`, bits 8–87, yield
`070C0D0E`. Independent synthetic native-instruction execution covered 5,152
ordinary MSB0 cases and this wide-field case; these are offline inputs, not
vehicle captures. All acquisition/record branches have pinned native evidence;
live enabled RIDs, returned formats/frame selectors, and record payloads remain
target inputs.

These artifacts close the three current host-side semantic investigations;
their full Data List/FFD/RoB runtime catalogs remain unexported. The related RID
support correction is exported: current `CommandCommon @0x10067EEA` skips the
inclusive `D1F0..D1FE` page range. Independent execution of all 256 `D1nn`
selectors matched the corrected bundle, including queried boundaries `D1EF`
and `D1FF`. P6 remains the generation-22 successor family; these findings do
not assign its protocols or ECU producers to Camry/TSS3.
