# GTS+ TSE/GTSE saved-session format

> **Scope:** current GTS+ TSEConverter 01.02.002, its 171/173/180 template
> CSVs, `Converter.dll`, `RingBufferParser.dll`, `TseCompression.dll`,
> `TSEConverter.exe`, and native `GTSFileController.dll`.
>
> **Status:** saved-session structure **and recovered managed reader/compression
> semantics**. The shipped managed files are protector-zeroed inputs, but the generic CP
> recovery materializes their executable IL. Four public Toyota-generated legacy TSE
> specimens now validate the shared header/FAT/position-marker lineage against real bytes.
> A **true-TSS3** TSE is still required to validate current PCS Operation/Image FFD section
> population and the complete latest-layout traversal end-to-end.
>
> **Artifacts:** `data/generated/gtsplus_2026/tse_converter_surface.json` captures the
> installed/template/native storage surface; `data/generated/gtsplus_2026/tse_managed_semantics.json`
> captures the CP-recovered procedural reader/ring/compression semantics. They are generated by
> `tools/techstream/extract_gtsplus_tse_converter.py` and
> `tools/techstream/extract_gtsplus_tse_managed_semantics.py`, and checked by
> `tests/techstream/verify_gtsplus_tse_converter.py`, `tests/techstream/verify_gtsplus_tse_managed_semantics.py`,
> and the fresh auxiliary CP-recovery oracle.

## 1. Result

Toyota's TSE file is not an opaque monolithic dump. The shipped template is effectively
an OEM binary-layout grammar: it declares a header, a FAT/search-key table, per-section
position records, fixed-width scalar types, variable strings, nested list levels, and
per-function persisted payload structures.

For TSS3 work the important result is that **PCS time-series Operation FFD and PCS Image
FFD are first-class saved-TSE sections**. They are not concepts invented by PCS Data
Viewer after the fact. `GTSFileController.dll` independently exposes native add/get/count
APIs for both section families.

The current TSE-to-GTSE conversion path has a critical preservation boundary: the shipped
`TSEConverter.exe.config` sets `BinarySkipDataNames` to:

```text
RecordOnBehavior共通
MILMessage
PCS時系列作動時FFD
PCS画像FFD
FuelConsumption
オシロ連携データ
```

So **the current converter is configured to skip PCS Operation FFD and PCS Image FFD while
reading the binary TSE for GTSE conversion**. If those sections matter to RE, preserve the
original TSE rather than assuming the `.GTSE` conversion retains them.

The installed component is `GTS+ TSEConverter 01.02.002`; its config selects

|---|---:|---|
| 171 | 12,696 | distinct |

The 173→180 template transition therefore did not change the declared binary grammar in
this distribution.

## 3. Header and FAT model

The configured template declares:

- 8-byte file extension field;
- file header ID (`DWORD`), version (`WORD`), reserved (`WORD`);
- legacy save-existence flag and store counter;
- destination/region information;
- variable-length GTS version and user-type strings;
- a top-level FAT with **12-byte search-key fields plus 32-bit positions**;
- per-ECU FAT records for Data List, DTC, Active Test, Drive Recorder, RoB,
  PredictiveFFD and other function families.

The current template contains **38** declared 12-byte FAT/search-key fields. Relevant
first-class top-level positions include:

- Health Check;
- timestamps;
- RecordOnBehavior common;
- CAN Bus;
- VehicleControlHistory common;
- **PCS time-series Operation FFD**;
- **PCS Image FFD**;
- ECU function data.

This was originally only a declared-format result. The recovered `BinaryRead::.ctor` now
pins the runtime position dictionary too: it contains **35 exact 8-byte marker values**.
Selected high-value entries are `VehicleControlHistory共通 -> FFFFFFFFFFFFFF23`,
`PCS時系列作動時FFD -> FFFFFFFFFFFFFF27`, `PCS画像FFD -> FFFFFFFFFFFFFF28`,
`TMR -> FFFFFFFFFFFFFFFE`, and error report -> `FFFFFFFFFFFFFFFF`.

The reader's traversal contract is now recovered rather than inferred from the CSV:

- the template's columns **15..22** are consumed as `Type`, `Size`, `SizeF`, `IsList`,
  `LevelF`, `ExistF`, `PositionF`, and `PositionSkipF`;
- position records are **8 bytes** and are compared to the runtime marker dictionary as
  case-insensitive hexadecimal strings;
- the resynchronization scanner looks for `FF FF FF FF <selector> FF FF FF`; generic
  traversal accepts selector `0x01..0x33` or `0xFE`, while ECU-skip mode accepts only
  `0x30`, `0x33`, or `0xFE`;
- `PositionF == 1` skip paths scan to the next recognized marker, and terminal/skip cases
  rewind exactly **8 bytes** so the outer traversal can consume that position record;
- `GetFatData` projects the parsed tree through **15 dictionary levels**, removes the
  top-level `ヘッダ情報` and `初期車両情報` nodes, recursively retains children, and
  disambiguates repeated list keys as `{name}_{index:03d}`. Raw ring-buffer bytes survive
  the projection as `RawValue`.

These rules are pinned by recovered IL and fresh CP recovery. TMS-086 now adds real-file
validation for the stable framing layer: four public Toyota Techstream 11.30.137 TSEs use
this same header/FAT family and the same 8-byte position-record shape. They are legacy
pre-TSS3 files, so they do **not** establish current PCS section population or prove that
`180_Template.csv` directly parses their old layout. Current `TSEConverter` explicitly
normalizes historical input first through `GFCConvertOldTSEToLatestTSE`, writes an
`_NEW.TSE`, and only then gives that upgraded file to `BinaryRead` with the configured
current template.

### 3.1 Real Toyota TSE lineage validation

A public 2017 Toyota diagnostic discussion provides three downloadable RAR attachments
containing four genuine `.TSE` sessions. The repository intentionally does **not** retain
those raw third-party sessions or their original filenames/vehicle identifier. Instead,
`data/external/public_techstream_tse_lineage.json` records privacy-minimized structural
facts plus the public attachment and TSE SHA-256 identities.

All four files are GTS `11.30.137`, header version `0x102A`. Their common prefix is:

- signature/file-extension bytes `9A 53 DB 12 54 53 45 00`;
- `DWORD ID=1`, `WORD Ver=0x102A`, `WORD reserved=0`;
- the legacy-save flag, store counter and destination fields in the same widths/order as
  the current 171/173/180 template;
- length-prefixed GTS-version and user-type strings, ending at byte `0x2E`; then
- a 14-entry legacy top-level FAT made of **12-byte ASCII key + little-endian DWORD
  absolute position** records (`IniCarInfo`, `ConfCarInfo`, `MultiPID`, ... `ImgFFD`,
  `ECUInfo`).

Most importantly, all **56/56** retained FAT targets are in bounds and begin
`FF FF FF FF <selector> FF FF FF`, exactly the current recovered
`BinaryRead::GetNextReadPosition` scan shape. The first three entries are consistently
selectors `01`, `02`, and `17`. Repeated legacy FAT positions can point at the next
present section when an intermediate family is absent, so the observation is deliberately
about FAT/position-record framing rather than projecting a current section meaning onto
every old key.

This removes the generic “no real TSE specimen” blocker. What remains specimen-blocked is
narrower: a **true-TSS3** raw TSE with PCS Operation/Image FFD, needed to validate current
section population plus the post-upgrade 180-template traversal on the data we actually
care about.

## 4. PCS recorder sections

The template gives both PCS sections the same outer shape:

```text
<section>
  position information    DWORD*2 (8 bytes)
  file version            WORD
  count                    WORD
```

The native storage ABI independently confirms the sections are real GTS store objects:

```text
GFCAddPCSMultiOperationFFDData
GFCGetPCSMultiOperationFFDData
GFCGetPCSMultiOperationFFDDataCount
GFCRemoveAllPCSMultiOperationFFDData

GFCAddPCSImageFFDData
GFCGetPCSImageFFDData
GFCGetPCSImageFFDDataCount
GFCRemoveAllPCSImageFFDData
```

These are corresponding storage schemas, not proof that the current application sends
a raw TSE directly to PCS Data Viewer. The executable lifecycle now distinguishes:

```text
legacy TSE sections -> TSEConverter (configured PCS/RoB skips) -> legacy GTSE archive
current browser session JSON -> direct .gtse archive
current recorder logs -> .vdas -> PCS Data Viewer
```

## 5. Ring-buffer grammar

The same template fully declares the metadata that accompanies stored high-rate monitor
ring buffers. The first repeated ring-buffer block contains:

### Frame table

- frame-table byte size (`DWORD`);
- object version / reserved fields;
- frame size (`DWORD`);
- **256 frame indexes (`WORD*256`)**;
- **256 frame lengths (`WORD*256`)**;
- optional standard-value records keyed by PID ID.

### Signal table

Per signal the template stores:

- signal ID (`WORD`);
- communication-frame ID (`BYTE`);
- start/end bit (`WORD`, `WORD`);
- UTF-16 full name, short name and unit;
- data type and genre;
- signedness;
- **MUL / DIV / OFFSET** (`DWORD` each);
- decimal position;
- graph min/max;
- display-pattern records and button values;
- raw data min/max.

`RingBufferParser.SignalInfo` independently exposes the same model:
`signalId`, `signalName`, `unitName`, `dataType`, `genreId`, `signed`, `mul`, `div`,
`offset`, `decPntCnt`, `dataMax`, `dataMin`, `dispPattern`, `frameId`, `startBit`, and
`endBit`. Its parser surface names `ParseFrameTable`, `ParseSignalInfoList`,
`ParseRingBuffer`, `ConvertDataFrame`, and `ConvertNumericValue`.

The recovered bodies make that parser procedural rather than metadata-only.
`ParseFrameTable` builds frame-index -> frame-length mappings; `ParseSignalInfoList`
reads the Japanese template keys for signal/frame ID, start/end bit, name/unit, type,
signedness, MUL/DIV/OFFSET, decimal position, min/max and display pattern.
`ParseRingBuffer` uses an **8-byte timestamp** and computes each record width as
**`8 + 2 * sum(frame lengths)`**. `ConvertNumericValue` handles signed 1/2/4/8-byte
integers and unsigned mask/shift extraction and then evaluates
**`(raw * MUL / DIV + OFFSET) / 10^decimal_places`** before formatting.

### Ring state/data

The saved ring itself carries:

- phase;
- packets per block;
- total/free buffer size;
- write start;
- read start;
- write end;
- write-buffer size;
- saved-buffer size;
- raw byte buffer.

This means a TSE capture retains enough OEM metadata to reconstruct engineering-unit
signals without rediscovering bit positions/scalings from CAN traffic, provided the
section is preserved.

## 6. GTSE model

`Converter.BinaryWrite` exposes the JSON/GTSE output model, including tree/info/data
writers, vehicle/ECU maps and function IDs. `Converter.BinaryRead` is now executable after
CP recovery and exposes the typed binary-reader branches (`BYTE`, `CHAR`, `SHORT`, `WORD`,
`INT`, `UINT`, `LONG`, `ULONG`, `DWORD`, `DOUBLE`, `BOOL`, `SYSTEMTIME`, `UNSIGNED CHAR`,
`CCMDSTRING`, and `WCHAR_T`), array handling, code-page string decoding, raw ring-buffer
retention, position-marker resynchronization, and recursive list/FAT projection described
above.

`TseCompression.dll` closes the outer GTSE archive contract. It recursively enumerates the
source directory, appends a fixed **20-byte salt** to each file before SHA-256,
records relative path + uppercase digest in `list.txt`, writes that manifest in Shift-JIS
with header `Target Folder`, creates a ZIP with Shift-JIS entry names via
`ZipFile.CreateFromDirectory`, then moves the ZIP to the requested `.GTSE` destination.
The exact salt recovered from `TSECompression::.cctor` is:

```text
e7 b7 77 97 f2 e6 2c e7 4b 5d c5 8f 8d 15 c8 2c 57 4d 8a 4a
```

The installed/protected inputs still have zeroed bodies, which remains useful provenance,
but it is no longer an RE boundary. Generic CP recovery materializes all current managed
components; the coree-managed `TSEConverter.exe` specifically recovers **27/27** nonzero-
RVA method bodies with clean CLR entrypoint `0x6BAE`. The whole-corpus recovery validator
now rejects any managed output whose nonzero `MethodDef` RVA remains unmaterialized.

### 6.1 Current save, playback, and retention lifecycle

`data/generated/gtsplus_2026/lifecycle_persistence.json`, generated by
`tools/techstream/extract_gtsplus_lifecycle_persistence.py`, joins authenticated
`gts.gui` JavaScript to materialized managed bodies and pinned native instructions.
The current normal save path is **not** the legacy binary TSE conversion path:

- `StoredDataManager` maintains the working session's tree, metadata and capture JSON.
  Buffer `saveAck` acknowledges receipt, not completed persistence. Only after ACK installs
  the per-save completion handler does the interface wait for `saveFinish` and metadata
  before tree/hash publication. **A rejected nonfinal chunk before ACK is a stalled
  save/close branch:** the worker posts `saveFinish/Failed`, but the interface drops it
  because no per-key handler exists. The chunk catch resolves its local return without
  settling the deferred appended to `savingProm`, so both caller save and worker close
  remain pending. Post-ACK/final-write failures instead reject the caller and release the
  worker deferred. Whole-file pre-ACK failure also stalls the caller, but its worker
  finalizer settles and permits close. The normal close-drain path is not a universal
  failure-path guarantee.
- Current constants select `.gtse`, format version `0.0.1`, and the `tree.json`,
  `fileInfo.json`, `vehicleInfo.json`, `info.json`, `data.json`, `activityreport.json`,
  `tseName.json`, `cooperation.json` and `event.json` members. Current hash handling uses
  `list.cpt`, with legacy `list.txt` compatibility. The `TseCompression.dll` salt/manifest
  contract above describes the separate legacy converter, not every current archive.
- Export conditionally refreshes the embedded hash manifest and packages the working
  directory; it does not require positive verification to archive. Optional DataSync copying
  does not itself clear that directory. Import clears the workspace first, extracts and
  verifies the archive, then reconstructs playback state. **Recovery can delete without a
  successfully preserved export:** a verified root manifest, missing folder list, or
  ineligible no-manifest version skips export and clears directly. Where export runs,
  `exportTseFile` catches failures into a resolved `{result:false,...}`; `exportPrevData`
  ignores that result and still clears the working maps and wildcard-deletes a nonempty
  workspace. Archive preservation is not a deletion guard.
- File-open `GTSE/GTSPlusTSEStartup.exe::Main` (RVA `0x2050`) accepts exactly one path,
  URL-escapes it into the local HTTPS `GTSStoredMain.html?tse=` page and launches it.
  Graph and comparison viewers receive one capture path or two paths separated by `|`.
  Graph writeback still writes `data.json` after failed hash verification; manifest
  regeneration occurs only after a positive verification result.
- Native `DiagAdaptation.dll!SettingFileName` (`0x1000c7b0`) requests special folder
  **`0x2e`, CSIDL_COMMON_DOCUMENTS / Public Documents**, then appends configured
  `productFolder` and `DataLogger/latestDrsFile/{timestamp}.{drs,drsp}`. This is not
  CommonApplicationData / ProgramData (`0x23`). Native writer close patches its header
  and closes the file; no stronger filesystem-durability guarantee is established.

The artifact also separates CSV converter IPC from VDAS CSV conversion, records the
save-dialog overwrite/retry/cancel branches, and pins graph writeback, recorder cleanup
and ErrorReport package retention. These lifecycle findings do not supply a real TSS3
payload specimen.

CSV cancellation is now a source-closed negative contract, not an uninspected Windows
boundary. The frontend sends relay `commandId:99`; broker
`MessageExecuteTask.ExecuteGuiRelay` (RVA `0xec74`) forwards the inner data string
unchanged to matching named sessions. All **884 materialized method bodies in the ten
converter assemblies** were traversed: there is no relay-command reader, subscription,
or cancellation-token consumer in the conversion tasks. Websocket receiving occurs
inside ordinary request-response calls, including translation requests during conversion,
not a persistent relay dispatcher. Thus an unsolicited relay can remain unread or be
consumed as an ordinary response/error; it has **no implemented task-cancel transition**.
Successful relay sending is not proof that conversion stopped. The artifact records
the exhaustive callgraph drift checks and decisive receiver/broker IL.

### 6.2 Publication and failure-prefix contracts

These are application call-order contracts, **not crash-durability or multi-file atomicity
guarantees**. The generated artifact's `publication_contracts` and new leaf-body evidence
separate completed API calls from the state left by a later failure.

| Boundary | Implementation and failure prefix |
| --- | --- |
| Capture content and metadata | `GTSPlusFileAdapt.dll::WriteFile` (RVA `0x2814`) implements mode **0** as `File.Exists` check followed by `StreamWriter(...,append:false,UTF8Encoding(false))`; this is not race-free `CreateNew`. Mode **1** creates/truncates, mode **2** appends/creates. Parent directories are created, and the writer is disposed. Data and info writes are independent; their rendezvous precedes tree mutation/write, not a transaction. A later failure cannot undo earlier content or metadata. |
| Tree and manifest | `addData` mutates maps/rawTree **before** mode-1 `tree.json` overwrite. `createHashFile` then deletes the old manifest and attempts a replacement, swallowing list/delete/create errors. An awaited refresh can therefore leave no matching manifest. PF `CreateHashFile` (RVA `0x5dfc`) rejects an existing output, inventories/hashes before opening it, writes `.cpt` using `FileMode.Create` with IV+ciphertext or plaintext using UTF8 `WriteAllText`, and attempts deletion after write failure. There is no temporary-manifest rename or restoration of the deleted manifest. |
| Current export | `verifyHashFile` runs **before** activity-report copying. Only positive verification enables embedded-manifest delete/recreate; missing, invalid or errored verification still permits export, without regenerating the embedded manifest. A separate root-level check manifest is always refreshed and lies **outside** the ZIP source. Report-copy errors are ignored. `ArchiveFile` (RVA `0x4d2c`) honors overwrite refusal, but the ZIP folder leaf (RVA `0x25e8`) **deletes an existing final archive before** `CreateFromDirectory(...,includeBaseDirectory:false)`. Compression writes the final pathname directly; its catch attempts deleting partial output. After deletion, the old archive is not preserved. Export does not clear the workspace. A failed subsequent DataSync copy returns `result:false` even though the archive exists; successful parallel folder exports are not rolled back when another fails. |
| Legacy converter | `TseCompression::Compression` (overload RVA `0x2100`) deletes old `list.txt`, inventories/hashes, writes/disposes a create/truncate Shift-JIS manifest, then makes sibling `temp_yyyyMMddmmssfff.zip`. Only after ZIP creation does `changeExtZipToGTSE` (RVA `0x2504`) delete the final destination and call `File.Move`. ZIP creation failure preserves the old destination but can leave partial temporary output. Move failure **after deletion** loses the old destination and leaves the completed temporary ZIP. The catch does not clean temporary ZIPs. This is not atomic replacement. |
| Graph writeback | `JsonFileUtility.Write` (RVA `0x4e98`) opens `FileStream(path,FileMode.Create)` **before serialization**, so even a serializer exception can truncate the old `data.json`. Finally blocks dispose streams, but do not restore content. Verified writeback writes data, deletes the embedded manifest, then requests asynchronous hash creation. Verification-false/request-failure writeback still writes data but does not regenerate the manifest. Hash-create success and failure callbacks (RVAs `0x12abc`/`0x12b04`) send the **same** UI notification. These callbacks update extracted workspace, not the user archive. |
| Import | Browser import splits the basename on backslashes, clears first, extracts to `workPath/basename`, then chooses the first enumerated root folder, not the PF `changedFolderPath` response. PF `ExtractFile` (RVA `0x5404`) sniffs ZIP/gzip and selects an unused `_001`-style directory on collision. Extraction failure attempts recursive deletion of that selected directory. After successful extraction, hash/JSON/info reconstruction failure merely resolves error flags: extracted files and partially rebuilt maps are not cleaned or restored. |

`GTSPlusArchiver.ZipFile.DecompressFileToFile` (RVA `0x26e8`) calculates each destination
with `GetFullPath(Path.Combine(destination,entry.FullName))`, creates parents and calls
`ExtractToFile(...,overwrite:true)` for nonempty names. **This wrapper has no explicit
destination-containment check.** Paths normalized outside the selected extraction directory
are not covered by PF's recursive cleanup of that directory. This is a source-level path
handling finding, not evidence that any supplied archive contains such members.

Production-date persistence joins through the shipped misspelled
`StoredDataManager.overwirteVehicleInfo`: verify first, then mode-1 overwrite
`vehicleInfo.json` regardless of the verification boolean; refresh the manifest only
when verification was positive. Write errors reject, but refresh errors can resolve.
This backend cannot turn an unawaited service callback into a durable metadata update.

The managed hash wrapper calls native
`GTSPlusFileCryptographic.dll!CalculateFileHashDevide` (`0x10001050`):
`CreateFileW(GENERIC_READ,FILE_SHARE_READ,OPEN_EXISTING)` → 1-MiB reads →
`CloseHandle` → fixed 20-byte salt → SHA-256. Disassembly at `0x10001158` and
`0x100011a0` confirms that it ignores `ReadFile`'s BOOL and tests only `bytesRead`;
the open gate also tests zero rather than `INVALID_HANDLE_VALUE`. A failed read
that leaves a zero byte count can therefore finalize a prefix hash. This leaf is
read-only and supplies neither a consistent snapshot nor a publication barrier.

The inspected publication leaves use stream disposal, but no `File.Replace`,
`ReplaceFile`, `MoveFileEx`, `FlushFileBuffers`, or `FileStream.Flush(true)`.
Legacy `File.Move` follows destructive deletion. Neither ordinary API success nor
viewer/worker close notification establishes hardware durability.



## 7. Practical use for TSS3 RE

The saved-session pipeline is now useful in three ways:

1. **Preserve original `.TSE` files.** The current GTSE converter skip policy targets
   exactly the PCS/RoB evidence we care about.
2. **Use TSE ring buffers as named signal captures.** Their stored signal table includes
   bit geometry and engineering conversion metadata.
3. **Join PCS FFD captures to the recovered PCS Data Viewer dictionary.** The TSE layer
   proves where the proprietary FRC recorder data is persisted between acquisition and
   offline interpretation.

The remaining high-value closure is specifically a **true-TSS3** TSE sample containing
PCS Operation FFD or Image FFD. The pinned Toyota Diagnostics tree and repository
`REFERENCE/`, `community/`, and `targets/` corpora contain zero such specimens, and the
retained CAN captures contain no genuine `0x792<->0x79A` AB11/EB11 recorder exchange.
TMS-086 supersedes the broader “no real TSE specimen” framing: public legacy Toyota TSEs
now validate the common header/FAT/position-record lineage, but they predate TSS3 and cannot
populate the current PCS sections.

The minimum acquisition needed to close that validation boundary is therefore concrete:

1. connect current GTS+ to a true-TSS3 vehicle through Toyota VCI/J2534;
2. select the category-498 Front Recognition Camera / PCS recorder surface and retrieve
   Operation FFD (`AB11/12/13 -> EB11/12/13`, selector `0x66`);
3. preserve any original binary `.TSE` produced by the applicable legacy/export workflow;
   the current browser's ordinary save produces `.gtse` directly and is not evidence of
   an intermediate raw TSE;
4. preserve that TSE before legacy conversion, because current `BinarySkipDataNames`
   omits `RecordOnBehavior共通`, `PCS時系列作動時FFD`, and `PCS画像FFD`; and
5. pin the specimen SHA-256 plus vehicle/FRC software identity, then exercise the recovered
   35-marker FAT/list traversal and PCS dictionary join against its populated sections.

Until such true-TSS3 source data exists, there is no further static implementation RE to do
here: the managed executable-body, old-file upgrade handoff, TSE traversal, ring-buffer and
GTSE compression boundaries are closed. **PCS TSS3 real-section validation** remains
source-data blocked rather than code-analysis blocked; generic real-TSE framing no longer is.
