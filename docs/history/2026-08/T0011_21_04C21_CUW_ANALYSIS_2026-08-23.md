# T-0011-21 / 04C21 CUW analysis — 2026-08-23

## 1. Scope and specimen identity

This note records a byte-level analysis of the external Toyota calibration
package `T-0011-21 - 04C21.cuw`. The raw package remains an ignored local
`REFERENCE/` artifact; only its identity and deterministic derived evidence are
tracked.

```text
filename  T-0011-21 - 04C21.cuw
size      2,825,257 bytes
sha256    e0525b4fe0224772a3dde68d16bf2fb7a808d6d937fa32a337db34d95f5ba61d
```

The package is a Format-Version-4 CUW. Both CRC layers validate and the declared
file size is exact. Its first member is `attach.att` (410 bytes, CRC32
`DE1824C4`, SHA-256
`a1edd8a8767ade5b30f5795a3d71d005212c146426ddb600d61589c50f43032e`).
The Version-4 tail contains exactly one CPU-image member,
`8966304C2100.txt` (2,824,778 bytes, CRC32 `2BD15E25`, SHA-256
`c6dec16cafe641d66a1f4c7a0628b405ac4178f251483ae87177ef19278af9a7`),
and consumes the package exactly.

## 3. Selected Techstream V18 route

The descriptor selects key `0P5-CAN86`. Decoded V18 `Ini/Parameter.ini` has
exactly one matching row:

```text
ParamFileKeySystemProtocolMicon = 0P5-CAN86
PasswordAddress                 = 0000100E
ByteOrder                       = 0
CalibrationType                 = 2
EngineTypeFlag                  = 1
FORESTTypeFlag                  = 1
M16CTypeFlag                    = 0
FlagToUseCIDGetterAndFlashWriterDLL = 0
FlagToUseGetFlashSizeFunc       = 1
```

`TCUWCalibrationFile.dll` exports independently resolve:

```text
KindOfECU 0  -> ENG & ECT
CPUType 86   -> VFOREST_2_0M
```

This is therefore the **legacy integrated VFOREST path**, not a modern dynamic
Unified prepare+flash route. `Cuw.exe` constructs the integrated VFOREST writer
at `0x477B13 -> 0x5886EC`. The common `CCanFlashWriter::Execute` body calls the
legacy reprogramming/security path at `0x45E8FF -> 0x464254`, then dispatches
this package's VFOREST `FlashWrite` at `0x461F42 -> 0x587AD4`.

The name `VFOREST_2_0M` must not be silently expanded to "RH850". The same
Techstream export table separately names explicit V850 CPU families, and this
specimen belongs to the older Denso D76F0xxx/newGen ecosystem according to
independent tooling. The exact instruction-set/core identity is outside what the
CUW bytes prove.

## 4. The `.xxz` layer is ASCII-hex `ZV` / LZF framing

`8966304C2100.txt` is not an S-record. It is ASCII hexadecimal text with line
breaks. Removing whitespace and hex-decoding it produces exactly 1,329,128
bytes:

```text
sha256  37b832f7899776c27d64483365ac83d9144cf590ba81483320afd5f3313d47db
```

`Cuw.exe` supplies the official vocabulary. Its parser at `0x43F4CC` contains
and checks `5A5600`, `5A5601`, and the error text **`LZF-Format data`**. The
adjacent `0x43F730` helper performs the ASCII-hex conversion. The VFOREST record
walker at `0x587D8C` recognizes exactly two record forms:

```text
ZV 00 || stored_len:u16be || raw[stored_len]
ZV 01 || stored_len:u16be || expanded_len:u16be || lzf[stored_len]
```

The real stream consists of exactly **512 records** and has no residual bytes:

```text
ZV00 raw records       6
ZV01 LZF records     506
expanded size/record 4096 bytes for all 512 records
logical total         512 * 4096 = 0x200000 bytes
raw record indices    0, 1, 149, 150, 168, 181
compressed sizes      57 .. 4093 bytes
```

The `ZV01` data obey standard LZF control-byte semantics. A standalone decoder
implemented in `tools/techstream/inspect_cuw_vforest.py` expands **all 506 real
compressed records** to each record's declared `0x1000` bytes without a single
length/reference error. The six `ZV00` records copy directly.

The reconstructed logical image is therefore exact and deterministic:

```text
length  2,097,152 (0x200000)
sha256  feb1e7ff00f7268ece3f043a56ac39a33bd22dffbe4f7f23fad1286b53db8e04
```

It contains `89663-04C21` at logical offset `0x100C`, independently tying the
expanded image to the descriptor. The public exact-software record's stated
2,097,152-byte complete-binary size independently agrees with this reconstruction.

There is also a strong erased/fill representation: records 396 through 510
(115 complete 4-KiB blocks) all expand to repeated word `E2 03 F1 33`; the
expanded block SHA-256 is
`4e1da2228f2acfec26fbd1054db55e95b393986119bde211ccabb0f182ab479e`.

### Important boundary

This closes the **CUW/LZF compression** layer. It does not prove that the
resulting two-megabyte byte sequence is native executable plaintext for the
underlying MCU. Quick ISA probing is not coherent enough to promote that claim,
and the repeated `E203F133` fill is unlike a conventional erased `FF` image.
The exact Denso/VFOREST code/storage representation remains bounded.

There is no evidence of a cryptographic encryption layer in the CUW wrapper or
LZF framing itself. The remaining question is representation semantics after
LZF expansion, not access to the bytes.

## 5. Techstream does not LZF-expand before transmitting

The host/ECU boundary is distinct from our offline reconstruction. Techstream
itself converts ASCII hex into the binary ZV stream, parses the `ZV00/ZV01`
records, and retains the raw/compressed record bodies for the VFOREST writer.
The selected writer bodies are pinned as:

| body | VA | size | SHA-256 |
|---|---:|---:|---|
| ASCII LZF parser | `0x43F4CC` | `0x262` | `f80f34dd9ea7d8892c8a84afa119ac5a96c81a3e828374370900655f0bade55e` |
| hex decode helper | `0x43F730` | `0x70` | `a52fd347fdc75c426e8612e551b055336ea1994493a94181f6f5a61008307c0e` |
| VFOREST FlashWrite | `0x587AD4` | `0x2B8` | `ca32c157f997ac78c5a1762f400a1b2650aec3cf55c97ddbdf957fa8dcb8108e` |
| ZV record walker | `0x587D8C` | `0x1D0` | `0c1016b9a7ef845b5a2d6ba75530b5cad8ded6431dcf9f54daaaa1cb7902f2cb` |
| WriteWithErase | `0x587F5C` | `0x320` | `3254e7b5cead2622b0527b4d453069c4f111ce8efad2949052ea2be614c7b0f6` |

The sender copies its caller-provided stored chunk directly into the J2534

reconstruction. The exact ECU-side decompression/storage implementation is not
claimed here.

## 6. Old/new software password and CheckID

This specimen uses the same legacy **software-password CheckID** architecture
recovered for T-0087, but its values and byte order are specimen-specific.

### Source/old password

The target descriptor carries:

```text
TargetData = 3532323734463D4A
```

The already recovered `Cuw.exe:0x4B3880` transform hex-decodes eight bytes and
subtracts output indices `0..7`; the uint reader then parses the resulting ASCII
hex. Here it yields:

```text
source calibration  8966304C2000
password uint32      0x51040A7C
CheckID wire bytes   7C 0A 04 51
```

### New-image password

The selected row is materially different from T-0087:

```text
PasswordAddress = 0x100E
ByteOrder       = 0
```

`PasswordAddress` indexes Techstream's **hex-decoded ZV/LZF archive buffer**,
not the LZF-expanded two-megabyte image. The exact stream bytes at `0x100E` are:

```text
FF 0C EF 56
```

`CalibArchivedFile::GetPassword @ 0x10002EF0` with `ByteOrder=0` reverses those
bytes while formatting/parsing the uint32, so the host password value is:

```text
new-image password uint32  0x56EF0CFF
```

`CalibrationFile::GetNewPassword @ 0x10003090` falls back to that archived
password because the descriptor has no explicit `NewPassword`. The shared
CheckID routine emits the selected uint32 little-endian, which restores the
archive byte order on the wire:

```text
FF 0C EF 56
```

For `LocationID=00 02 00 01 00 07 07 20`, the exact five CheckID payloads after
the common four-byte CAN/J2534 identifier prefix are:

```text
old/source:
00
00
20 07 01 00 02 00
07 00
7C 0A 04 51

new-image:
00
00
20 07 01 00 02 00
07 00
FF 0C EF 56
```

This proprietary CheckID password is independent of diagnostic SecurityAccess.

## 7. SecurityAccess and route-generation boundary

Because this package uses the integrated `CCanFlashWriter`, its Execute path
calls the same `ChangeReprogrammingForECU @ 0x464254` recovered for T-0087.
That path performs the legacy four-byte SecurityAccess exchange:

```text
TX 27 01
RX 67 01 || seed[4]
key = seed XOR 00 60 60 00
TX 27 02 || key[4]
RX 67 02
```

This specimen therefore gives a second real package demonstrating separation
between diagnostic SecurityAccess and the package-derived CheckID software
password.

The descriptor contains none of the modern Unified fields
`ECUAuthKey/ServiceAuthKey/SeedKey/Nonce/OffsetAddress/SecurityProperty2`.
Nothing in this package transfers those modern credentials or algorithms to the
tracked RH850 EPS targets.

Likewise, this integrated VFOREST path must not be conflated with the separate
**Security-VFOREST dynamic writer** analyzed in TMS-010. That later factory
family transfers calibration-file `Nonce`/`SeedKey` material through
`SendNonceAndSeedKey`; this actual `0P5-CAN86` package selects
`FlagToUseCIDGetterAndFlashWriterDLL=0` and the older integrated writer instead.

## 8. What is closed and what remains bounded

Closed for this specimen:

- complete CUW outer/member framing and CRCs;
- exact descriptor and V18 route selection;
- ASCII-hex `.xxz` conversion;
- exact `ZV00/ZV01` grammar;
- standard-LZF expansion of all 506 compressed records;
- exact reconstructed 2-MiB logical image and hash;
- host-side writer boundary: no LZF decompression before J2534 transmission;
- old/source and new-image software passwords, byte order, and CheckID wire
  transcript;
- use of the shared legacy four-byte SecurityAccess path;
- independent Toyota provenance for `8966304C2000 -> 8966304C2100`.

Still bounded:

- exact underlying D76F0xxx MCU suffix from first-party evidence;
- exact CPU ISA/core identity implied by Toyota's `VFOREST` name;
- whether the LZF-expanded 2-MiB representation is direct native flash code or
  retains another Denso storage/coding transform;
- exact ECU-side LZF decompressor/storage implementation;
- runtime timing/response behavior without a captured reflash session.

These remaining questions do **not** prevent extraction or deterministic
reconstruction of every byte carried by this CUW. They prevent only stronger
claims about the final MCU-native representation.
