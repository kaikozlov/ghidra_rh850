# T-0087-17 CUW analysis — 2026-08-22

## Scope and provenance

A user-supplied Toyota calibration package, `T-0087-17.cuw`, was analyzed
against the pinned Techstream V18.00.003 binaries and decoded parameter corpus.
The raw 5,112,447-byte package is intentionally **not** committed. Its immutable
identity is:

```text
SHA-256 d40cc0988f7310ce0417fba17e512ae915719b40fed9a98f829ca1c5639c3cbd
```

The normalized observations used by repository tests are retained in
`data/generated/techstream_v18/cuw_t0087_17_specimen.json`. This package is a
useful independent calibration-format specimen, but it is **not** a matching
TSS3 EPS package.

## 1. Vehicle and ECU identity

The package's CRC-validated `attach.att` identifies:

```text
DateOfIssue=2017-06-16
VehicleType=ZRE172L
EngineType=2ZR-FAE
VehicleName=Corolla
ModelYear=15-16
ContactType=CAN
KindOfECU=0
CPUImageName=89663-02U13.xx
NewCID=302U1300
CPUType=70
```

It updates three prior calibration IDs:

```text
302U1000
302U1100
302U1200
```

to `302U1300`. Therefore the filename's `17` does not mean model year 2017:
the descriptor says **2015–2016 Corolla** and the package was issued in 2017.

Toyota bulletin **T-SB-0336-17**, `MIL "ON" DTC P2610` (2017-12-21),
independently corroborates this identity. Its calibration table lists the
2015–2016 Corolla / 2ZR-FAE / CVT-Gate Main ECM transition
`302U1000,302U1100,302U1200 -> 302U1300`; Toyota describes the update as an
ECM-logic change intended to reduce DTC P2610 (Engine Off Timer Performance).
The bulletin is provenance for package applicability and calibration identity,
not evidence for the transport/security protocol recovered below. The source is
the Toyota bulletin mirrored by NHTSA as `MC-10127065-9999`.

The pinned `TCUWCalibrationFile.dll` export tables independently resolve:

- `KindOfECU=0` → `glptrKindOfECU_ENGAndECT` → engine/ECT;
- `CPUType=70` → `glptrCPUType_SH72544R_2560K` → Renesas SH72544R,
  2560-K class.

Combining descriptor fields exactly as the legacy parameter selector does gives
`0CAN70`. Decoding V18 `Ini/Parameter.ini` produces exactly one matching row.
Important values are:

```text
PasswordAddress=001FFF00
ByteOrder=1
CalibrationType=2
EngineTypeFlag=1
FlagToUseGetFlashSizeFunc=1
FORESTTypeFlag=0
FlagToUseCIDGetterAndFlashWriterDLL=0
```

`FlagToUseCIDGetterAndFlashWriterDLL=0` is decisive: this is the old integrated
`CCanFlashWriter` path in `Cuw.exe`, not a modern prepare/flash DLL route such as
Unified or ReproStd.

## 2. Real Format-Version-4 CUW container

The specimen validates the previously static-only outer framing exactly:

```text
00 "CALIBRATION" 00
formatType = 04
stored CRC32 = D9AD63D2
u32be declared size = 5,112,447
first member = attach.att, 524 bytes, CRC32 057704E2
```

The stored outer CRC32 equals zlib CRC32 over `[18, declaredTotal)`, exactly as
recovered from `Cuw.exe` `0x413BF0/0x412C98`. The first named member is read by
`0x412F9C` and ends at file offset 566.

Format Version 4's formerly opaque remainder is now closed both statically and
by the specimen. The parser at `0x413E74` reads a **one-byte CPU-image archive
count**, and `0x413F42..0x413F70` iterates objects whose vtable `+8` slot
(`0x5D5E30`) points back to the same member reader `0x412F9C`. Therefore:

```text
Version-4 tail :=
    image_count:u8
    repeat image_count times:
        name_len:u16be
        name[name_len]
        payload_len:u32be
        payload_crc32:u32be
        payload[payload_len]
```

The real tail is exactly:

```text
image_count = 1
name = 302U1300.txt
payload_len = 5,111,858
payload_crc32 = 5CACED62       # validates
```

The single record consumes the tail exactly. No padding or second hidden member
exists.

## 3. CPU image: Motorola S-record

`302U1300.txt` is a valid Motorola S-record stream:

```text
1 x S0
65,536 x S2
1 x S8
```

All record checksums validate. Every S2 carries 32 data bytes, giving a single
contiguous 2-MiB address range `0x000000..0x1FFFFF`; the S8 entry address is
`0x014B00`. Reconstructing the address space gives:

```text
SHA-256 2b2db1d9766405d74706e56fc1baea544e2a00bbaf09ee36f5994f1617852735
```

The S0 data is `r041B60100\0\0`. The data image is not ordinary immediately
recognizable SH code: aligned `A1 DF E1 03` occurs **70,726** times, and the
whole `0x050000..0x05FFFF` and `0x1E0000..0x1EFFFF` 64-KiB regions consist of
that word. This is a reproducible property of the reconstructed image, not an
interpretation of what the word means.

The selected host path is now closed beyond the parser. `Cuw.exe` S-record
parser `0x4A9A9C` (0x61F bytes, SHA-256
`f2f19629ec980462b042bd7abed3c7f73fda6ec894593037159b2d23282a17ba`)
materializes the records through `0x4AB2D4` (0x1D3 bytes, SHA-256
`abe8a1e2a26ed78326ebfed08f551256edc2fa66394115b0de34fc0d0e6f6e31`).
The legacy `WriteBlock @ 0x465C74` ultimately reaches the CCanFlashWriter data
sender at `0x45C700` (0x165 bytes, SHA-256
`cf272798d1980d6ab166fc661ddd100bbd323079dc4ded957be124149d063261`),
which copies the materialized bytes into the J2534 transmit path without a
host-side crypto/recode stage. Therefore **Techstream sends this selected
legacy S-record image representation unchanged**. The semantic meaning of the
encoded-looking representation, including whether/how the ECU decodes it,
remains bounded. In particular, this package must not be fed to the modern
Tundra/RH850 `SeedKey`/`Nonce` AES-CBC extractor: those descriptor fields do
not exist here.

## 4. Old/new software passwords and exact CheckID wire consumer

The last 256 bytes of the reconstructed **new** image contain an intentional
plaintext metadata/security trailer. At the V18 row's
`PasswordAddress=0x001FFF00`:

```text
0x1FFF00  79 EF 38 FF                new-image password
0x1FFF04  2D 75 EB 31                unresolved word
0x1FFF08  "89663-02U13     "         image/part identifier
0x1FFF18  00 02 00 01 00 03 07 20    LocationID
```

`TCUWCalibrationFile.dll!CalibArchivedFile::GetPassword @ 0x10002EF0` reads
`PasswordAddress` and `ByteOrder`, indexes the archived image, and returns those
four bytes. `CalibrationFile::GetNewPassword @ 0x10003090` uses a descriptor
`NewPassword` override when present and otherwise falls back to the archived
value. This package has no override, so **`0x79EF38FF` is the new-image
software password for `302U1300`**. The descriptor parser at `0x408CE8` stores
an optional override at per-CPU source `+0x1C` and its presence flag at `+0x20`.

The **old/source** password is different and is encoded in each target's
`TargetData`. The exact decoder is the `TMemIniEx` escaped-string routine at
`0x4B3880` (0x170 bytes, SHA-256
`a62f3f89276881a88b6cff421772fd4ee43e2fa273a8c39f9ca0bc4737cf20fa`):
it hex-decodes eight bytes and subtracts the zero-based output-byte index from
each. The resulting eight ASCII hex digits are parsed as a uint32 by the reader
path at `0x4B3F34` / integer parser `0x402380`. The real descriptor therefore
yields:

| target CID | `TargetData` | decoded password | password bytes on CheckID wire |
|---|---|---|---|
| `302U1000` | `41364547383B483A` | `A5CD46B3` | `B3 46 CD A5` |
| `302U1100` | `41443A46384B364B` | `AC8C4F0D` | `0D 4F 8C AC` |
| `302U1200` | `37333947373C373A` | `727D3713` | `13 37 7D 72` |

`CFlashWriter::SelectRetryPassword @ 0x46CAB0` (0x6C-byte SHA-256
`c653fcca83bc5b43d5b710bcc93d8240950ea4980a941f1c7ebe87910bf7e48a`)
controls the old/new selector at writer object `+0x8C`: an explicit true input
selects new (`1`); a false input with writer status `+0x78 == 7` toggles it;
other false cases select old (`0`). The semantic label for status value `7` is
not promoted without independent evidence.

The downstream consumer is now byte-pinned as
`CCanCommonFlashWriter::CheckIDWithWaitOfSFs @ 0x45C86C` (0x570 bytes,
SHA-256 `302c53c53cd78441ce2c989def17ba5f1f910053f3d1d59c61c9ba772d653c9e`).
After the common four-byte CAN/J2534 identifier prefix it sends exactly five
frames. For this package's `LocationID=00 02 00 01 00 03 07 20`, the new-image
password case is:

```text
00
00
20 07 01 00 02 00
03 00
FF 38 EF 79
```

Frames 3 and 4 are `LocationID[7,6,3,2,1,0]` and `LocationID[5,4]`. The final
frame is the selected 32-bit software password in little-endian wire order, so
`0x79EF38FF -> FF 38 EF 79`. The same grammar carries the three source
passwords in the table above. This is a **legacy proprietary raw CheckID
handshake**, distinct from the UDS `27 01/27 02` SecurityAccess exchange in the
next section. `79EF38FF` must therefore not be called the `27 02` key.

## 5. Legacy SecurityAccess is exactly recoverable

`CCanFlashWriter::ChangeReprogrammingForECU @ 0x464254` invokes
`CCanFlashWriter::CollateSeedKey @ 0x463E80` for each target ECU before changing
reprogramming mode. `CollateSeedKey` implements:

```text
TX  27 01
RX  67 01 || seed[4]
key = CalcSeedKey(seed)
TX  27 02 || key[4]
RX  67 02
```

The key derivation is no longer merely a generic virtual call. The integrated
legacy writer initializes these four 16-bit round values at
`0x47F0C4..0x47F112`:

```text
A441
2172
A421
4172
```

`CalcSeedKey @ 0x45A1B0` dispatches to `BasicConversion @ 0x45A388`, whose exact
four-byte state operation is:

```text
[s0, s1, s2, s3] -> [s2, s3, s0 XOR round_hi, s1 XOR round_lo]
```

Applying all four compiled rounds collapses algebraically to:

```text
key[0] = seed[0]
key[1] = seed[1] XOR 0x60
key[2] = seed[2] XOR 0x60
key[3] = seed[3]

key = seed XOR 00 60 60 00
```

Thus this 2015–2016 engine family uses a trivial four-byte seed/key mechanism.
It is **not** the modern 16-byte SecurityUp construction recovered in TMS-019.

## 6. Legacy flash protocol after SecurityAccess

The integrated `CCanFlashWriter` uses Toyota/Denso's older proprietary
reprogramming command grammar rather than the newer Unified UDS download path.
The statically recovered operations include:

| operation | command |
|---|---|
| change reprogramming mode | `10 <mode>` → `50` |
| block check | `35` / `36` |
| block erase | `25` / `26` |
| write continuation | `45` |
| in-verify | `47` / `48` |
| verify | `15` / `16` |

`WriteBlock @ 0x465C74`, `CheckBlock @ 0x4658B4`, `EraseBlock @ 0x465A7C`,
`InVerifyBlock @ 0x46623C`, and `VerifyBlock @ 0x466430` supply the direct body
evidence. This explains why the package cannot be projected onto the RH850 EPS
bootloader solely from shared high-level names such as “SecurityAccess” and
“reprogramming.”

## 7. What transfers to the TSS3/RH850 work

This package is still useful for modern CUW reverse engineering:

1. It independently validates the complete outer CRC/member framing.
2. It closes one concrete format-specific tail: Version 4.
3. It proves the selector is package metadata → parameter row → concrete writer
   behavior, including old integrated rows that are outside the modern 196-row
   dynamic-DLL census.
4. It proves Toyota historically carried additional flash authorization
   material **inside the calibration image itself** (`PasswordAddress`) while
   keeping diagnostic SecurityAccess as a separate mechanism.
5. It gives a real example of descriptor CPU/ECU names joining cleanly to
   Techstream's internal enum strings and parameter tables.

What does **not** transfer:

- `seed XOR 00606000` is not an RH850 EPS key algorithm;
- `79EF38FF` is not an RH850 EPS password/key;
- SH72544R addresses and legacy raw flash commands are not the Unified EPS
  download grammar;
- absence of `ECUAuthKey`/`ServiceAuthKey` in this old package says nothing
  about their presence in a matching modern EPS CUW.

The high-value acquisition target remains a **matching modern EPS CUW**, such
as the known `8965F3` Tundra family package or an exact Sienna/Corolla EPS
package. That artifact would use the same now-validated outer-container tooling
but should exercise the modern descriptor/writer branch and can finally bind
real `ECUAuthKey`, `ServiceAuthKey`, `SeedKey`, `Nonce`, ranges, and the
Unified-vs-EachArea choice.
