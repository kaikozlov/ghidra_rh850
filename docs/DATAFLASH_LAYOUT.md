# RH850/P1M-E DataFlash layout

This note maps the complete 32 KiB DataFlash prefix from the China-market Sienna
EPS dump (`8965B4512000`). It corrects two earlier hypotheses:

1. pages 468–479 are not 12 ICU key-slot metadata pages; they are four ordinary
   SecOC-associated NvM objects stored as raw/XOR55/XORAA copies;
2. bootloader DIDs `0x201/0x202/0x203` are volatile RAM inputs and are not backed
   by this DataFlash.

The complete 122-record physical and logical-owner map is in
`../data/dataflash_nvm_records.csv` and is regenerated by
`../tools/generate_dataflash_layout.py`. `../tests/verify_dataflash_layout.py` checks the
physical map; `../tests/verify_dataflash_semantics.py` independently checks the ownership
classes, checkpoint format, unallocated lower half, and protected tail.

## 1. Top-level map

DataFlash has 512 64-byte pages:

| Pages | Virtual range | Size | Firmware-supported interpretation |
|---:|---|---:|---|
| 0–255 | `0xFF200000–0xFF203FFF` | 16 KiB | outside both configured persistent-object classes; no valid record envelope; raw/user-pool capacity or erased/retired history, with exact role unresolved |
| 256–431 | `0xFF204000–0xFF206BFF` | 11 KiB | 74 checkpoint-ring physical records for 32 logical slots |
| 432–479 | `0xFF206C00–0xFF2077FF` | 3 KiB | 48 raw/XOR55/XORAA records for 16 triplicate logical objects |
| 480–511 | `0xFF207800–0xFF207FFF` | 2 KiB | outside NvM and explicitly protected by the compiled DataFlash range validator; hardware documentation identifies the last 1/2 KiB as ICU-S-reserved |

The configured application NvM area is therefore exactly pages 256–479
(`0x3800` bytes). A two-range table at CodeFlash `0x293E4` protects
`0xFF207800–0xFF207FFF` and `0xFF206C00–0xFF206EFF`. The compiled validator at
`0x4EAD8` rejects any DataFlash request overlapping either range. The second range
is precisely the 12 pages holding all three copies of optional objects 12–15; the
first is the final 2 KiB ICU-S-shaped tail.

This protection evidence strengthens the tail classification, but it still does
not expose the protected contents or place this firmware's SecOC slot-4 key there.

## 2. NvM physical-record map

The relevant CodeFlash configuration is:

```text
NvM block/job count       124          @ 0x26DDC
NvM block descriptor table             @ 0x26DE0 (124 × 16 bytes)
physical storage map                   @ 0x27808 (six-byte entries)
```

Each physical storage entry is:

```c
struct StorageMap {
    uint16_t first_page;
    uint16_t payload_length;
    uint16_t flags;          // zero in this configuration
};
```

Storage indexes `1..122` pack contiguously and backwards from page 479 to page
256. Job 1 is non-persistent; jobs 0 and 2 both alias storage index 1; jobs
3–123 map to indexes 2–122.

In this captured image a committed/valid-looking record has these observable
properties:

- its first `uint16_t` equals the storage index;
- the final 32-bit word of its allocation is `0xAAAAAAAA`.

68 of 122 configured physical records meet both conditions. The remaining 54
read as erased, uncommitted, stale, masked, or otherwise invalid records. The
second header word varies and is intentionally left unnamed; it was not proven
to be a CRC.

The complete per-record CSV includes storage index, NvM jobs, page allocation,
virtual range, payload length, header/trailer state, validity, logical ownership,
ring/copy position, and checkpoint generation/complement state.

### 2.1 Every configured block has a logical owner

The 124-entry two-byte table at CodeFlash `0x2B1B0` closes the remaining ownership
gap:

```c
struct NvmLogicalOwner {
    uint8_t object_index;
    uint8_t owner_class;    // 0 checkpoint ring, 1 triplicate object
};
```

Blocks 0 and 1 are `FFFF` sentinels. Every persistent block 2–123 has exactly one
owner:

| Owner class | NvM blocks | Storage indexes | Pages | Logical slots | Physical records |
|---|---:|---:|---:|---:|---:|
| triplicate raw/XOR55/XORAA | 2–49 | 1–48 | 432–479 | 16 | 48 |
| checkpoint ring | 50–123 | 49–122 | 256–431 | 32 | 74 |

The map includes disabled logical slots. Eleven triplicate descriptors are active
(objects 0–6 and 12–15), while objects 7–11 are disabled; their 15 reserved
physical records are invalid in this image. Twenty-four checkpoint descriptors
are active and own 56 records. Eight disabled checkpoint slots account for the
remaining 18 configured records, all invalid. Thus no record in pages 256–479 is
an unclassified generic block anymore, even where its OEM field-level meaning is
unknown.

### 2.2 Checkpoint-ring record format

The 32 checkpoint descriptors start at CodeFlash `0x2AF2C`; their count is the
`0x20` halfword at `0x2AF10`:

```c
struct CheckpointObject {
    uint16_t data_length;
    uint16_t ring_blocks;
    uint16_t first_nvm_block;
    uint16_t reserved;
    uint32_t ram_mirror;
};
```

Enabled descriptors use either two or six rotating NvM blocks. Disabled entries
use block `FFFF`; seven have zero ring count, while disabled slot 16 retains a
count of two. The owner map still reserves their physical block IDs, but inactive
descriptor lengths do not necessarily describe the stale physical allocation.
`secoc_nvm_checkpoint_write_submit @
0x674A8` serializes each checkpoint NvM payload as:

```text
generation:u32
|| RAM data[data_length]
|| zero padding to max(data_length, 56)
|| bitwise_not(generation):u32
```

The outer physical-record header and allocation-end `AAAAAAAA` trailer remain
separate. `checkpoint_restore_complete @ 0x67A98` accepts only a generation whose
stored inverse XORs to `FFFFFFFF`, chooses the current ring candidate, and copies
bytes after the generation word to the configured RAM mirror.

All 50 physically valid records belonging to enabled checkpoint descriptors also
have a valid generation/complement pair. Six enabled ring copies are invalid or
uncommitted, and all 18 records reserved for disabled checkpoint slots are
invalid. Individual payload fields remain unnamed unless a consumer establishes
their semantics; structurally, however, these are generation-protected
SecOC-associated state/checkpoint objects rather than arbitrary calibration blobs.

### 2.3 Pages 0–255 are outside the object store

No entry in the storage map or owner table reaches below page 256, and the lower
16 KiB contains neither a valid configured record envelope nor an application
persistent-object owner. Its 4,096 directly dumped words comprise 2,250 all-zero,
1,306 all-one, and 540 mixed words.

Those values must not be treated as a hidden record format. Renesas documents that
reading an erased RH850 DataFlash word returns **undefined data**. The observed
mixture is therefore compatible with erased, retired, partially programmed, or
otherwise unowned flash history. Static evidence does not distinguish those cases.
The compiled range validator does not protect this lower half, so it is best
classified as unallocated/raw DataFlash capacity—not as NvM, ICU metadata, or a
recoverable key bank.

### 2.4 The final 2 KiB is protected ICU-S-shaped storage

Pages 480–511 are absent from both ownership classes and are one of the two exact
ranges rejected by `application_dataflash_range_allowed @ 0x4EAD8`. Every dumped
32-bit word is either `00000000` or `FFFFFFFF` (236 zero words and 276 all-one
words). FlashRunner's RH850 documentation states that ICU-S devices reserve the
last device-dependent 1 KiB or 2 KiB of DataFlash and omit it from ordinary
DataFlash erase/blank-check operations.

For this 32 KiB P1M-E image, the aligned final 2 KiB range, compiled protection,
and ICU-S-capable part make the reservation strongly supported. The CPU-visible
00/FF readback is not evidence of the secure contents. In particular, the
application CMAC path selects ICU-S slot 4 without reading this range, so no
specific SecOC key may be assigned to it from this dump.

## 3. SecOC-associated triplicate bank

The 16-entry table at CodeFlash `0x2B0AC` is definitive:

```c
struct SecocRedundantObject {
    uint16_t length;
    uint16_t base_nvm_block;
    uint32_t ram_mirror;
};
```

Configured objects use:

```text
base + 0: raw payload
base + 4: payload XOR 0x55
base + 8: payload XOR 0xAA
```

The three reads are reconciled by `secoc_nvm_triplicate_read_complete @ 0x67C34`
and copied into the descriptor's CPU-visible RAM mirror. Writes are constructed
by `secoc_nvm_persist_triplicate @ 0x67608`.

| Object | Len | Base block | RAM mirror | Raw / XOR55 / XORAA pages | State in this dump |
|---:|---:|---:|---:|---|---|
| 0 | 16 | 2 | `0xFEBEF468` | 479 / 475 / 471 | valid consensus |
| 1 | 16 | 3 | `0xFEBEF478` | 478 / 474 / 470 | valid consensus |
| 2 | 8 | 4 | `0xFEBEF400` | 477 / 473 / 469 | valid consensus |
| 3 | 16 | 5 | `0xFEBEF488` | 476 / 472 / 468 | valid consensus |
| 4 | 8 | 14 | `0xFEBEF408` | 467 / 463 / 459 | no valid copy |
| 5 | 8 | 15 | `0xFEBEF418` | 466 / 462 / 458 | valid zero consensus |
| 6 | 8 | 16 | `0xFEBEF460` | 465 / 461 / 457 | valid consensus |
| 7–11 | 8 | disabled | `0xFEBEF410` | — | disabled |
| 12 | 32 | 38 | `0xFEBF0288` | 443 / 439 / 435 | no valid copy |
| 13 | 32 | 39 | `0xFEBF02C8` | 442 / 438 / 434 | no valid copy |
| 14 | 32 | 40 | `0xFEBF02A8` | 441 / 437 / 433 | no valid copy |
| 15 | 32 | 41 (`0x29`) | `0xFEBF02E8` | 440 / 436 / 432 | no valid copy |

This table explains all pages 432–479. Pages 468–479 are only objects 0–3;
their first words (`1..12`) are physical storage indexes, not ICU key IDs.

## 4. The field-verified SecOC-key record

Object 15 resolves the previously unexplained `0xFF206E14` location:

| Copy | NvM block | Storage index | Page/record | Second 16-byte field |
|---|---:|---:|---:|---:|
| raw | 41 | 40 | page 440, `0xFF206E00` | **`0xFF206E14`** |
| XOR55 | 45 | 44 | page 436, `0xFF206D00` | `0xFF206D14` |
| XORAA | 49 | 48 | page 432, `0xFF206C00` | `0xFF206C14` |

The record has a four-byte physical header, so address `record + 0x14` is payload
bytes 16–31. A valid object is restored to RAM `0xFEBF02E8`; the corresponding
second field is therefore `0xFEBF02F8`.

Independent field evidence in the neighboring repositories establishes that this
field contains the operational SecOC AES key on related EPS variants:

- `RESEARCH_REPORT_EN.md` records Vance's CMAC-verified key in partner firmware
  `8965B4514000` at `0xFF206E14`.
- `calvinpark-openpilot/CLAUDE.md` records a later in-car Sienna extraction that
  CMAC-verified a key at the same address; `dump_dataflash.py` uses it only to
  decide whether a partial dump covered the useful region.
- Calvin's actual matcher remains exhaustive and oracle-driven; it does not trust
  the address when selecting a key.

For this exact committed `8965B4512000` snapshot, all three object-15 records are
invalid/uncommitted and the raw field is:

```text
0xFF206E14: 00000000040000808202000000000000
```

It has low entropy and the original report measured zero CMAC matches. Therefore:

- **Definitive:** this firmware reserves a triply redundant 32-byte NvM object at
  the same physical/RAM location used as a SecOC key object on related variants.
- **Definitive:** this particular snapshot does not contain a valid plaintext key
  in any of the three object-15 copies.
- **Strong external evidence:** provisioned related Sienna/Yaris/partner EPS
  variants store the operational key in object 15's second field.
- **Strong inference:** the whole optional 32-byte bank is unprovisioned or
  inactive in this snapshot. `SECOC_APPLICATION_CHAIN.md` adds that the compiled
  CMAC path selects ICU-S slot 4 and its known-answer vector corresponds exactly
  to an erased `FF*16` key. A masked/incomplete acquisition or different runtime
  policy remains possible, so a provisioned-unit experiment is still required.

The absence of a matching key in this dump is not evidence that pages 468–479 are
KDF metadata, nor does it prove per-boot ICU derivation. It only proves absence
from the captured readable bytes.

## 5. Bootloader DIDs are not DataFlash-backed

The complete access, response, and ordering analysis is in `DID_MODEL.md` and is
independently checked by `../tests/verify_did_model.py`. The four-entry DID table at
CodeFlash `0x8F14` contains:

| DID | Length | Destination/behavior |
|---:|---:|---|
| `0xF181` | 32 | read-only; generates `02 || 32*0x21` rather than a stored identifier |
| `0x0201` | 16 | direct copy to RAM `0xFEBF2D08` |
| `0x0202` | 16 | direct copy to RAM `0xFEBF2CF8` |
| `0x0203` | 5 | sequence-arm request; five data bytes ignored; no DataFlash pointer |

`uds_write_data_by_identifier @ 0x4948` calls `bootloader_did_write_dispatch @
0x6D5E`; mode 1 invokes a direct byte copy at `0x6D3A`. DID `0x201` becomes the
input to `payload_build_derive_key @ 0x7068`; DID `0x202` initializes payload
AES-CBC/CMAC at `0x709A`.

The DataFlash dump tooling writes these DIDs before each upload because they are
session crypto parameters. It does not persist them in NvM.

## 6. Implications for the previous lifecycle analysis

The prior correction remains valid that `0x65CD8 -> 0x66E48 -> 0x67590 ->
0x72F58` is NvM, not a CSM/ICU command chain. The broader conclusion changes:
this NvM subsystem is not exclusively non-key state. Object 15 is structurally a
key-bearing object on field-verified related variants, and a valid value would be
CPU-visible in its RAM mirror/work buffers.

Accordingly:

- the report's FEBEF capture locations remain wrong for the SecOC key;
- `0x72F58` remains generic `NvM_ReadBlock`, not key-set;
- the correct known related-variant locations are DataFlash `0xFF206E14` and RAM
  mirror field `0xFEBF02F8`;
- neither is validated as containing a key in this exact snapshot;
- the separate application verify path selects ICU-S slot 4 without reading the
  object-15 mirror, and this calibration's known-answer vector expects `FF*16`;
- the ICU-S tail may exist for other protected material, but it is no longer the
  best-supported location for this SecOC key.
