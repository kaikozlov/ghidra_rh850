## Exact Crown-vs-Camry boundary

`data/generated/crown_8965F3012000_camry_comparison.json` is regenerated from the
two canonical CodeFlash images. The first differing byte is at `0xA004`; the
boot core `0x0000..0x91FF` is byte-identical. Across the full 1 MiB, however,
621,353 bytes differ, so F3 family naming is not a license to transplant
application addresses blindly.

Several high-value architectural pieces do transfer exactly:

- payload-build root at `0xBFD8`, boot SecurityAccess root at `0xBFE8`, and
  application SecurityAccess root at `0x20840` are byte-identical;
- the 241-entry RDBI DID membership is identical (195 unique callbacks), with
  Crown's table relocated from Camry `0x2928C` to `0x28FA8`;
- command-5 synchronous wrapper: Camry `0x89BC2` -> Crown `0x87662`, exact
  138-byte body;
- command-5 dispatcher: Camry `0x89440` -> Crown `0x86EE0`, exact 150-byte body;
- freshness-48 packer: Camry `0x90566` -> Crown `0x8E006`, exact 120-byte body.

Target-native Ghidra additionally shows Crown `0x881C0` has the same command-5
engine structure as Camry `0x8A720`: it programs ICU-S command 5 after the same
state/input checks, with target-local internal callback/MMIO literal addresses.
This is strong evidence that the EPS-local signing architecture transfers; the
Crown resident still requires target-native address resolution.

### Important non-transfer: stock XCP/C7 transport is configured out

The first comparison only noticed that Crown lacked Camry's raw
`0x9FDC0002`/`0x9FE00002` request/response words. A full transport-config
comparison closes the reason rather than relying on a literal search. Camry's
generated-COM family table is `[5,0,4,0,0,1]` with route map
`[0,FF,2,FF,FF,4]`: family 5 has one route, and rule 46 is the extended
`0x1FDC0002` XCP/C7 request. Exact Crown keeps the same transport-table
architecture but its corresponding values are `[5,0,4,0,0,0]` and
`[0,FF,2,FF,FF,FF]`. Family 5 is therefore disabled in the production
configuration. Crown has 44 acceptance rules and stops after the three
diagnostic rules; there is no rule corresponding to Camry rule 46, and neither
`0x9FDC0002` nor `0x9FE00002` occurs in Crown CodeFlash or DataFlash.

This is a target configuration difference, not evidence that the RSCFD driver
or P1M-E hardware is different. The common CAN-driver architecture remains. A
minimal Crown port should therefore preserve the proven Camry C7 format and
signer behavior if possible, and treat restoration of an equivalent dedicated
ingress as a transport adaptation rather than redesigning the signer around an
unrelated native PDU.

## Diagnostic transport and stock-wire route

The exact Crown image closes the EPS diagnostic endpoint rather than relying on
part-number similarity. Its byte-identical boot core contains physical request
`0x7A1`, functional request `0x777`, and response `0x7A9` in the same boot
CanIf tables used by the other P1M-E targets. The Crown application has its own
relocated address block at `0x21E68..0x21E9F`: primary `0x7A1 -> 0x7A9`,
functional `0x777 -> 0x7A9`, plus secondary `0x7A0 -> 0x7A8`. Only the
application CAN1 interrupt pair is installed (`IRQ187 -> 0x65500`,
`IRQ188 -> 0x654BE`); the CAN0/CAN2 IRQ slots remain on the default handler.
Thus there is no application-to-boot CAN-controller or diagnostic-ID migration.

The contributor-reported acquisition route was also the stock Toyota-B direct
path we expected: ELM327 parameter 1 with Panda logical bus 1. The imported dump
files do not contain a route transcript, so that Panda mapping remains external
field provenance even though the ECU-side channel and `0x7A1/0x7A9` endpoint
are exact firmware facts.

## Volatile native-B6 signer port

The Crown now has an exact-target static port of the Camry-proven EPS-local
native-B6 signer architecture. The port is address-resolved from Crown
CodeFlash rather than built by applying one relocation delta.

The important result is that the signing machinery itself transfers strongly:
the Crown retains the same `00F/D7/B6` protected-profile architecture, ICU-S
slot-4 configuration, B6 freshness model, and byte-identical relocated
command-5 wrapper/dispatcher and freshness packer. Crown B6 again carries
Target Lateral ID in B3 low six bits and target raw in signed B4:B5; the
firmware also closes the B6[2]=0 and B8/B9=100/100 replacement tuple.

The target-angle scale is also closed directly from Crown firmware. Crown
`0x025` exposes the same measured steering-angle coarse/fraction geometry, the
measured path converts `(15*coarse + fraction)` by `1787/512`, then `CB640`
stores `2*A - measured` and `CB730` computes `2*A - prior`. The auxiliary `A`
therefore cancels algebraically and republishes the measured term with its
original sign. The B6 target path doubles signed B4:B5, and the common
comparator applies the same `0xB76/0x400` gain before target-minus-measured. Therefore the exact linear
controller-equivalent B6 scale is `1024/17870 = 0.05730274202574147` deg/count
(`1.0001215187701138` mrad/count). This is independently re-derived on the
Crown rather than copied from F33/H/F.

The ID11 target envelope is target-native too. `CBC52` maps Target Lateral ID
11 to mode 2, and `C9B22` selects calibration index `2 + (AC3C&1)*8`. Both
possible ID11 records point to signed absolute limit **3490** and step limit
**7** in the doubled internal target domain. Because `C9B64` forms
`2 * signed16(B4:B5)`, `C9C08` clamps ID11 to exactly **±1745 B6 raw counts**,
or about **±99.9933 deg** at the recovered Crown scale. The step limit is 3.5
B6-count-equivalent per target-conditioner foreground invocation; no time unit
is inferred from that calibration alone. This is retained as an EPS calibration
fact only; the volatile signer is deliberately left in the previously reviewed
working shape rather than duplicating the receiver limit in new host/helper
policy.

The temporary `0x1DA` mailbox experiment is no longer the preferred transport.
Contributor preflight showed the exact PDU45 generation byte moving, and the
firmware trace closes that byte to normal `0x1DA` receive delivery. That does
not by itself prove B1..B7 have application semantics, but it does prove the
original "idle private mailbox" premise false. No active `0x1DA` transmission
should be used for Crown bring-up. The transport problem is now narrower: the
Camry/Corolla C7 mechanism is proven, while Crown's stock image has the same
underlying RSCFD architecture with its XCP family configured out.

The resulting resident remains volatile, contains no flash-write primitive,
uses the native Toyota B6 as its carrier, and requires a byte-exact no-mutation
native-MAC oracle before it will replace any lateral field. The first live
replacement is stationary and targets the fresh measured `0x025` angle using
the Crown-proved scale. A separate `soak-current` qualification tool leaves the
resident bytes unchanged and repeats that same current-angle replacement for a
bounded one-second run, reporting native-B6, command-5, and signed-replacement
counters before any larger openpilot integration is attempted. The host
intentionally does not auto-decode Park from
`0x127`: although upstream Toyota TSS3 prior art calls B5[7:4] `GEAR`, the exact
Crown EPS `0x127` unpacker does not extract that nibble, so Park remains an
explicit operator confirmation rather than a transferred safety assumption.
Road steering authority remains a live question.

## Validation-status audit (2026-09-13)

At implementation revision `68b9d8a8`, the Crown is a **statically supported
port candidate, not a live-qualified resident or steering implementation**.
A fresh direct comparison of the canonical images confirms the shared boot
core and all five retained exact-body mappings. Contributor dump acquisition
is real evidence for acquisition, but there is no retained Crown resident,
signing-oracle, sustained-operation, or steering-response result in this
import. A successful signing counter would not itself prove downstream EPS
acceptance or physical steering authority.

The host/test audit also found these limitations:

- The documented one-shot-then-soak sequence can reject a successful first
  replacement. `crown_f30_b6_inline_signer.py:186-217` reports current trailer
  equality separately from its sticky initial verification flag. Its
  `wait_native_verification` still requires current equality; the soak calls
  that method at entry. After modified data is signed, unequal current
  trailers are expected. An isolated synthetic decoder check confirmed the
  sticky-success/current-inequality combination is rejected by that entry
  predicate. This is not a live Crown failure.
- `crown_f30_resident_soak.py:29-43` accepts one successful operation as a
  positive result. An isolated predicate check confirmed that one attempt and
  one replacement pass. Its verdict therefore does not establish sustained
  operation at the requested rate, let alone downstream acceptance.
- Stock-Panda compatibility is build-dependent, not unconditional. The host
  adapter requests `allOutput`. Checked official-upstream opendbc revision
  `954217059383e0129c650740f11be74cb286000a`, `opendbc/safety/safety.h:418-426`,
  registers that mode only in debug-enabled builds. Official Panda
  `SConscript:12-20` distinguishes release and debug builds. Availability of
  the CAN API alone does not establish that an unspecified installed release
  supports the mode used by this host.

This audit changes no resident, helper, host, or Panda behavior. The positive
firmware comparison remains valid; passing build/packaging tests must not be
reported as proof that the documented live sequence works end to end.


## Readiness recheck (2026-09-13)

The firmware supports this port as a strong candidate, not a demonstrated Crown
resident. A read-only review of checkout `68b9d8a8` rechecked the exact image
identity, boot comparison window, and all five mapped support-function bodies
against both binary images; they still match. The retained mruno inputs are
flash dumps, not resident-install, signing, downstream-acceptance, or steering
captures. Successful dump acquisition must not be promoted into resident or
steering qualification.

**The existing kit is not established as stock-release-Panda compatible.**
`InlineSignerSession.__init__` calls `monitor._alloutput_mode`, which selects
`SafetyModel.allOutput` (`crown_f30_b6_inline_signer.py:361-374` and
`camry_f33_runtime_monitor.py:168-173`, under `exploit/ephemeral_runtime/`).
The retained upstream opendbc revision
`954217059383e0129c650740f11be74cb286000a` registers that mode only inside
`ALLOW_DEBUG` (`opendbc/safety/safety.h:418-426`). Upstream Panda's `SConscript`
adds that define in the non-release branch. An unmodified-source development
build and shipped release firmware are therefore not equivalent here. The
presence of `set_canfd_auto` and ordinary CAN support is not sufficient proof
that this kit works with an arbitrary stock build. No contributor Panda build
identity was retained with these artifacts.

The specific TSKM distribution is less uncertain than an unspecified stock
release. Read-only inspection of `optskug/openpilot` branch `tskm` at
`7f207ac644d466723c58e3f02b9d583d00fea2eb` found its tracked
`panda/board/obj/panda_h7.bin.signed` carries version `DEV-6409a587-DEBUG`
(SHA-256 `9341c3dfad52b15ba68f03caf5a97284016f7ee7720f9b6fdbd3ae74364713ba`).
The accompanying `panda/board/obj/panda_h7/main.elf` defines
`alloutput_init`, `alloutput_tx_hook`, and `alloutput_hooks`; bundled
`opendbc_repo/opendbc/safety/safety.h:417-424` registers the mode under
`ALLOW_DEBUG`. An additional direct ELF/image check resolves the
`alloutput_hooks` object and verifies that the mode-17 registry entry pointing
to it is present in both `main.bin` and the shipped signed image. This
establishes that the checked TSKM bundle includes the mode, not that every
stock-release Panda does.

Mode availability is distinct from mode selection. TSKM's collector,
DataFlash dumper, and extractor select `elm327`, not `allOutput`
(`tsk/lib/collect_can.py:89`, `dump_dataflash.py:159`, `extractor.py:137`).
The checked Calvin `dump` implementation likewise selects `elm327` for its
three extraction/range-dump paths. Our current Crown test host instead requests
`allOutput`; that is a host dependency, not a requirement of ordinary Panda
operation or the successful dump acquisition. TSKM's normal `pandad` compares
the installed Panda signature to its bundled firmware and updates a mismatch
(`openpilot/selfdrive/pandad/pandad.py:16-31,46-49,98`). Thus a normal install of
this exact TSKM build is expected to have the capability already, without a
Crown-specific Panda change. Mruno's actual installed version/signature is not
retained, so this is bundle proof plus a source-derived installation expectation,
not a live-device attestation or proof of the rest of the kit's compatibility.

**The advertised one-shot followed by soak sequence has a host-side oracle
bookkeeping problem.** The host's `native_signature_match` compares the current
native/computed trailer buffers (`crown_f30_b6_inline_signer.py:186-206`). The
soak calls `wait_native_verification` again at entry
(`tools/targets/crown/live/crown_f30_resident_soak.py:57-62`). A successful
replacement can leave these buffers unequal because they now refer to original
and modified content, despite the sticky original verification verdict still
being true. The host can therefore reject a subsequent soak after a successful
one-shot. The existing unit test covers post-soak interpretation of unequal
trailers, not this entry sequence
(`tests/verify_crown_f30_b6_inline_signer.py:229-234`). This is a source-review
finding, not a live Crown observation; no runtime fix was made in this review.

**The soak verdict overstates what its counters establish.** Its predicate
accepts any positive signed count when attempt count equals signed count
(`crown_f30_resident_soak.py:29-43`); it does not require sustained completion at
the requested rate. One successful replacement is sufficient for that predicate.
Furthermore, the resident increments its replacement counter when it updates
the queue, before returning to stock processing
(`exploit/ephemeral_runtime/crown_f30_b6_inline_signer_helper.S:203-216`). That is
not independent evidence that stock verification accepted the message, that the
application adopted the request, or that physical steering authority followed.
A current-angle test does change the control request; it is not a passive test.

The remaining evidence requirements are distinct: exact-environment tool
compatibility, live resident survival, native signing agreement, repeated
operation with measured completion/timing, independent downstream acceptance,
and physical response/fallback. No conclusion here authorizes road use. This
review changed documentation only and left the resident, helper, host, and
build implementation untouched.

## Contributor preflight review (2026-09-14)

The new source artifacts are `community/mruno/crown-preflight.json` and
`crown_f30_sideband_preflight_heartbeat.py`, retained without rewriting. This is
contributor live diagnostic evidence, not a local bench-Crown result. No retained
local bench-Crown preflight or resident result exists to compare against it.

**Session maintenance:** the shipped preflight entered EXTENDED and then waited
five seconds without diagnostic requests before its closing SID23 read. The
contributor reports that the closing read failed with a session-related NRC and
that periodic TesterPresent fixed it. The successful JSON records three such
requests. This supports a missing keepalive, not an exact measurement of a
universal five-second ECU timeout. The ECU session-expiration timer and the
tester's keepalive interval must not be conflated.

**Receive-accounting defect:** the original probe and the contributor variant
count `0x1DA` only inside their outer loop. The retained TSKM
`opendbc_repo/opendbc/car/uds.py` binds `UdsClient` to the same Panda `can_recv`;
`IsoTpMessage.send` drains stale RX, and `CanClient._recv_buffer` filters other
frames while awaiting a diagnostic response. Thus a frame received during
TesterPresent or a memory-read transaction can be absent from the reported
counts. This is a source-confirmed observation blind spot; the supplied JSON
cannot prove that it explains this particular discrepancy. An empty
`observed_1da_counts_by_bus` also says nothing about other CAN identifiers.

**Generation-byte semantics:** direct Crown firmware closes substantially more
than the endpoint delta alone. `0x4B874` reads `FEBE4E91` as PDU 45's generated-COM
update generation before unpacking the sole configured `0x1DA` scalar. PDU 45's
exact communication record is `58 02 00 00 08 00 00 0C`; on the ordinary PDU
delivery path, the bit-2 flag is tested and then `0x8C212(pdu_id)` increments
`FEBE4E64[pdu_id]`. With `pdu_id=45`, that is exactly `FEBE4E91`. A second
callback path can call `0x8C244`, but it is guarded by record bit 1, which is
clear for PDU 45. Thus the observed byte is a **new-data/PDU-delivery generation
counter**, not a generic foreground tick and not an identified ICU-S-consumer
counter. The retained 115→120 endpoints still give only a modulo-256 delta of
five, not a one-Hz rate: five, 261, etc. intervening increments have the same
endpoints.

The exact lower receive path closes the source class further. The configured
controller has 41 normal receive descriptors starting at index zero; descriptor
40 is classic `0x1DA/8`, and the generated PDU base is 5, yielding PDU 45.
RSCFD FIFO/buffer readers `0x7FED0/0x7FF9C` build the received frame, `0x7FEA4 ->
0x7E1AC -> 0x7E0BC` queues it, and the foreground receive drain `0x792EE ->
0x7E06A -> 0x7DF42 -> 0x7DEF0` dispatches it. The matcher at `0x7E70C` resolves
that descriptor to PDU45 and routes through `0x7F11E/0x7F138` to module-0's Rx
callback `0x7AEE8`; PDU45's bit-2 flag then calls `0x8C212(45)`, incrementing
`FEBE4E91`.

The obvious internal alternatives are excluded by exact configuration. Crown's
five generated-COM transmit IDs are `0x030`, `0x351`, `0x394`, `0x4A3`, and
`0x4C8`, not `0x1DA`. SecOC successful-delivery routes target only PDU 9 (`00F`),
PDU 40 (`D7`), and PDU 42 (`B6`), not PDU45. PDU45's secondary generation path
is disabled by its clear bit-1 flag. Therefore the contributor's moving
`FEBE4E91` is evidence that the normal receive stack delivered PDU45; it is not
a generic timer, foreground tick, ICU-S counter, or SecOC side effect.

The external transmitter is not identified by CodeFlash, and the original
probe's shared-UDS receive drain can explain why the host-side outer loop saw no
`0x1DA`. A corrected capture is still useful to identify the source and rate, but
it is no longer needed to decide whether `0x1DA` is a safe private mailbox on
this specimen: the EPS has demonstrated native PDU45 delivery. The `0x1DA`
sideband is therefore disqualified for mruno's Crown. This blocks only the
**candidate host→resident carrier**, not the recovered B6 signing architecture
or resident hook itself.

**Change scope:** only the standalone read-only preflight is changed. It sends
TesterPresent every two seconds and before the closing read, and records CAN
counts at the shared Panda RX boundary so UDS-consumed frames are counted too.
The JSON now includes all-identifier bus counts, elapsed observation time, and
an explicitly modulo-256 generation delta. The eligibility predicate is unchanged;
the reported 115-to-120 case still stops. Resident/helper bytes, signing/control
code, the existing soak, and Panda configuration are not changed.

`tools/test crown_sideband_preflight` runs offline fixtures for session lifetime,
frames consumed during TesterPresent and both endpoint reads, TX-return separation,
modulo wrap, unrelated bus traffic, and failed keepalives. It does not contact a
vehicle or build a resident. Corrected capture is still needed to distinguish
missed host observations from EPS-internal publication; the new result is not
an authorization to skip preflight or evidence that the resident failed.
