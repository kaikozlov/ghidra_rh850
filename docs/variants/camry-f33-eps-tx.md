# Camry F33 EPS transmit surface (`8965F3307000`)

This document closes the transmit surface of the exact 2026 Camry F33 EPS application image `8965F3307000`.

The structural source of truth is `firmware/camry-8965F3307000/CodeFlash.bin` (SHA-256 `42dce8efc42f6ae31718e7713fa2d26bb9191b4a82439778aee4d7afded9b0e7`), cross-checked against the canonical decompiler corpus, retained PE1 RAM, GTS+/Techstream diagnostic semantics, and retained on-car CAN captures. The machine-readable reduction is `data/generated/camry_8965F3307000_eps_tx.json`, regenerated by `tools/targets/camry/analysis/analyze_camry_f33_eps_tx.py` and verified by `tests/targets/camry/verify_camry_f33_eps_tx.py`.

“Complete” here means the exact firmware's complete configured transmit surface, normal-message pack geometry, direct application writers, scheduler, lower routing, protection, diagnostic/special transmit endpoints, and every OEM semantic join we can actually prove. Where Toyota's OEM name for a field is not closed, this document keeps the structural meaning rather than importing a stale public-DBC label.

## 1. Executive result

The exact F33 EPS has **five normal generated-COM transmit I-PDUs**:

| PDU | CAN ID | Format | Bytes | Cycle | Role recovered from exact firmware | Protection |
| ---: | ---: | --- | ---: | ---: | --- | --- |
| 0 | `0x030` | CAN-FD | 32 | 10 ms / 100 Hz | protected EPS status, feedback, and cooperative-control state | inner additive checksum + SecOC `FV4 || MAC28` |
| 1 | `0x351` | classic CAN | 4 | 1000 ms / 1 Hz | electrical-monitor/status projection | direct CanIf, no configured SecOC |
| 2 | `0x394` | classic CAN | 3 | 300 ms / 3.333 Hz | lossy projection of a 17-state internal fault/state classifier | direct CanIf, no configured SecOC |
| 3 | `0x4A3` | classic CAN | 8 | 500 ms / 2 Hz | redundant steering-angle, driver-torque, motor-feedback, and status PDU | direct CanIf, no configured SecOC |
| 4 | `0x4C8` | classic CAN | 8 | 980 ms / 1.0204 Hz | mostly constant compatibility/status template; exact OEM role unresolved | direct CanIf, no configured SecOC |

The EPS also has non-cyclic transmit endpoints:

- UDS/ISO-TP responses on `0x7A9` and `0x7A8`.
- An extended-ID XCP-shaped response endpoint at `0x1FE00002`, paired with request ID `0x1FDC0002`; the transport exists structurally but stock exact-F33 execution is gated off before protocol dispatch by fixed CodeFlash state.

This corrects the old public-DBC interpretation of `0x030` as `POWERTRAIN_STATUS_3 (ECM)`: on this calibration, **`0x030` is unquestionably EPS-origin**.

## 2. Generated-COM table and scheduling

Class-0 CanIf records at `0x21F58` are:

```text
PDU0  raw ID 0x40000030   CAN-FD 0x030   handle 0
PDU1  raw ID 0x00000351   classic 0x351  handle 1
PDU2  raw ID 0x00000394   classic 0x394  handle 1
PDU3  raw ID 0x000004A3   classic 0x4A3  handle 1
PDU4  raw ID 0x000004C8   classic 0x4C8  handle 1
```

The five PDU descriptors at `0x226C0` are:

```text
0x030: cycle=2    length=32
0x351: cycle=200  length=4
0x394: cycle=60   length=3
0x4A3: cycle=100  length=8
0x4C8: cycle=196  length=8
```

At the registered nominal80MHz timer domain, the foreground interval is5ms and these descriptor counts produce the nominal cycle times above. They specify invocation-count scheduling.

All five belong to the same generated-COM Tx I-PDU group. The group starts at PDU0, contains five PDUs, and every member has communication mask `0x10`. The retained PE1 RAM snapshot proves that this is not merely dormant configuration:

```text
BswM mask/complement        10 EF
Tx group desired/current    10 10
PDU runtime states          81 81 81 81 81
periodic countdowns         2, 139, 23, 31, 143
configured periods          2, 200, 60, 100, 196
```

Every periodic counter is nonzero and within its configured period, so **all five cyclic schedulers were armed in the retained on-car runtime snapshot**.

There is also an important direct-pack distinction:

- `0x351` and `0x394` use `0x7D1DC`, the change-aware signal pack helper. On an actual value change it calls `0x7E196(pdu, 0x80)`, so those messages can request event transmission in addition to the periodic schedule.
- `0x030`, `0x4A3`, and `0x4C8` use the raw pack helper `0x7D31E`; their direct packers do not themselves create a change-triggered transmit request.

The F33 application task reaches all five normal application packers through the normal source-preparation/packing sequence.

### 2.1 Payload generation is not transmit admission

The 2026-10-15 reconstruction separates live COM storage, pending requests and
accepted snapshots. Application pack roots `5F464/5F91C` call the normal packers
when their mode argument exceedsFF. Packers such as `4C97A/4CED0` snapshot
application fields and pack the live COM image **before** handling inhibition.
The five images begin at `FEBE4A48`, offsets0/32/36/39/47. Individual pack
helpers have their own critical sections; this is not an atomic whole-PDU
snapshot across interrupts.

Application state `7F96==5A` asserts the per-PDU inhibit through `7E612`;
zero releases it through `7E696`. Other values take neither transition.
Release can cancel pending request classes: `4CED0` cancels both40/80,
whereas `4C97A` cancels the periodic class. This is separate from communication
group activation and does not prevent a newer payload from being produced.

Under module state `3DF2==FE01`, `7A254` reaches scheduler `7E13A`.
It applies group transitions, services countdowns, then dispatches.
Exact `21C5E=1` bounds attempts per group per invocation. Admission `7DCA0`
requires a permitted pending class, zero minimum-delay countdown, intersecting
current group membership, and a valid inverse inhibit pair with the PDU bit clear.
Event pending takes precedence over periodic pending.
The relevant generations are separate:

- PDU flags493E, periodic countdowns496E and minimum-delay countdowns4978.
- Inhibit bitmap/inverse4A34/35.
- Periodic/event pending4A39/3A and desired/current group masks4A3B/3C.
- Event/periodic admission enables4A3D/3E.

Group disable clears both pending classes, applies flags`&3B`, and zeros both
countdowns. Enable clears pending, applies flags`|84`, and arms configured
offsets plus one. Neither transition copies or clears the payload.
Dispatcher `7DF14` reads the live COM pointer **after admission**; the exact
normal descriptor flags3 bypass its optional scratch/callout branch.


## 3. Lower routing and hardware transmit objects

The PduR lower-route table makes the protection split explicit:

```text
PDU0  selector 0      -> 0x8ED8E SecOC Tx
PDU1  selector FFFF   -> 0x7FEF8 direct CanIf fallback
PDU2  selector FFFF   -> 0x7FEF8 direct CanIf fallback
PDU3  selector FFFF   -> 0x7FEF8 direct CanIf fallback
PDU4  selector FFFF   -> 0x7FEF8 direct CanIf fallback
```

Thus **`0x030` is the only normal EPS transmit PDU with a configured SecOC Tx profile**.

CanIf then separates the FD and classic messages onto sibling hardware objects of the same lower driver node:

| IDs | CanIf handle / HTH | lower driver object | driver node/mailbox | writer |
| --- | --- | --- | --- | --- |
| `0x030` | 0 / HTH0 | 47 | node 1 / mailbox 0 | `0x8549E` CAN-FD writer |
| `0x351`, `0x394`, `0x4A3`, `0x4C8` | 1 / HTH1 | 50 | node 1 / mailbox 3 | `0x853AA` classic-CAN writer |

The retained HTH-state snapshot is `5A 69 69 69 69`: HTH0 happened to be active/in-flight while HTH1 was idle. `0x69` is a normal idle/available state in this driver state machine; it is **not evidence that the classic Tx handle is disabled**.

### 3.1 Queue ownership, busy results and the hardware boundary

The exact ABI carries `F33PduInfo {data*,length:u16,opaque:u16}` in `r7`
through PduR/SecOC forwarding. Missing second arguments in the old decompilation
were not missing firmware arguments. `7FEF8` also has a consequential `r10`
return: default1 or the result of `7FD46`.

For ordinary classic traffic, `7FD46` first copies up to64 bytes into scratch
`4FB2` and calls its configured callback, **before** checking controller state,
route and queue capacity. Admission requires controller sentinels
`48D8==57A8`, `4903==5A`, `48FE==5555` and valid routing.
Queue1 has capacity7 words at descriptor21AD6, buffer3E2C and cursor triple48E0.
The exercised classic record occupies five words.

Queue-full return2 occurs before queue writes, leaving old queued content and
cursors intact even though scratch now contains the newer source. `7DF14`
maps this to−19 and **retains the COM pending request**. A later attempt
samples the then-current COM image; there is no separate COM retry snapshot.
Successful admission and other lower failure codes consume both pending classes.

Protected PDU0 instead enters `8ED8E`: module54F4 must beFE01, descriptor/data
nonnull, source mapped to0 and length inside4..32. `8FABA` requires claim state
`5568/69=E1/5A`, changes it toD2/A5 and increments generation556A **before**
copying. For a32-byte image, `8E9C6` copies28 application bytes into5488,
initializes slot5458 and then publishes head/inverse5460/62.
The four-byte trailer is outside this copy.

Occupied-generation rejection21 occurs before copying: old protected snapshot,
descriptor, head and generation remain unchanged. Unlike classic queue-full2,
this result **consumes the COM pending request**; newer live COM remains for
a later opportunity. This preservation is specific to the outer occupied claim:
an internal malformed queue can fail after `8E9C6` has copied application data.

Queue service `8025A→8015C` passes the retained queue payload to `85112`.
Driver rejection marks hardware group3C without consuming the
record. Admission marks group and queue5A; later `8043C` advances the read
cursor and subtracts occupancy. State3C does not consume that record.
The eventual RSCAN boundary is `852FE`: ID/control/payload stores precede the
byte1 request at `8539E..853A4` to `CFDTMC[channel][mailbox]`.
The channel1 request base isFFD20224. Classic admission checks
`CFDTMSTS & 1E`; FD additionally checks retained nibble consistency.

Native compositions execute the real scheduler for classic admission
(`camry_f33_tx_publication_classic_due_enqueues_snapshot`), classic queue-full
retention (`camry_f33_tx_publication_classic_full_retains_queued_content`),
protected application-only copying
(`camry_f33_tx_publication_protected_due_copies_application_only`) and occupied
protected-generation rejection
(`camry_f33_tx_publication_protected_busy_preserves_generation`). Those
scenarios are retained in `decomp/camry-8965F3307000/oracles.jsonl`.
All passed with real callees and explicit RAM, without firmware overlays or
hardware-model extension. Group transitions, queue wrapping/large-record paths,
concurrent interrupts, MAC completion and physical transmission are not covered
by these executions.


## 4. `0x030`: protected EPS control-status / feedback PDU

### 4.1 Protection

The application packer `0x4C97A` constructs B0..B27. SecOC appends B28..B31 afterward.

```text
MAC input = 00 30 || application B0..B27 || full freshness[6]

B28[7:6] = message counter low2
B28[5:4] = reset counter low2
B28[3:0] = MAC28[27:24]
B29       = MAC28[23:16]
B30       = MAC28[15:8]
B31       = MAC28[7:0]
```

Exact profile:

- SecOC DataID `0x0030`
- 28 authenticated application bytes
- full freshness 46 bits in six-byte storage
- transmitted freshness 4 bits
- authenticator 28 bits
- Freshness Value ID 3
- ICU-S command 5 / MAC generation
- ICU-S key selector 4

B7 is a separate inner application checksum:

```text
B7 = low8(B0 + B1 + ... + B6 + 0x38)
```

The retained pre-SecOC generated-COM buffer has B28..B31 all zero while live wire frames carry changing `FV4 || MAC28`, proving the security tail is appended below the application packer.

## 5. `0x351`: electrical-monitor/status projection

Wire-visible application fields:

| Sig | Wire | Meaning |
| ---: | --- | --- |
| 38 | B2[7:5] | debounced electrical-monitor/status code |
| 39 | B2[4] | companion force/special-status flag |

The base state follows:

```text
FEBEBDE4 -> FEBEE82B -> 0x4C1C0 -> FEBE8100 -> signal 38
```

`0x4C1C0` applies a calibration count of 7 before updating the projected state. `0x4C216` has a separate broad force path that writes code 7 and flag 1 when `(FEBE6764 & 3) != 0 && FEBE8143 != 0`.

This family is related to Toyota Techstream DTC `C159B49`, **Power Steering Motor "B" Terminal Voltage Detect Circuit / Internal Electronic Failure**, but the broad force-7 state is not equivalent to the DTC and should not be renamed after it.

B0, B1, B2[3:0], and B3 remain at the initial zero image absent another mechanism.

## 6. `0x394`: internal fault/state classifier projection

The EPS first selects one of **17 internal states** and maps that state through a 17x5 table at `0x2A19C`. The rows are:

```text
 0: 0 0 0 0 0
 1: 4 3 0 0 0
 2: 4 7 0 0 0
 3: 5 3 0 0 0
 4: 4 3 0 0 0
 5: 1 1 0 0 0
 6: 3 3 2 1 2
 7: 3 3 2 1 0
 8: 6 3 3 0 2
 9: 6 3 3 0 0
10: 3 7 1 1 1
11: 3 7 4 1 1
12: 6 7 7 0 1
13: 6 7 6 0 1
14: 6 7 5 0 1
15: 2 2 0 0 0
16: 4 7 0 0 0
```

`0x4C24A` exports only columns 4, 1, 2, and 3:

| Sig | Wire | Classifier source |
| ---: | --- | --- |
| 40 | B1[7:6] | table column 4 |
| 41 | B1[5:3] | table column 1 |
| 42 | B2[3:1] | table column 2 |
| 43 | B2[0] | table column 3 |

Column 0 and the explicit internal state number are not transmitted in this PDU, so `0x394` is intentionally a **lossy status projection**. State 0 is the deepest recovered clear/normal state, but it is not itself the OEM GTS `Ready Status` DID.

## 7. `0x4A3`: redundant steering state / feedback

All eight bytes are directly produced:

| Sig | Wire | Meaning |
| ---: | --- | --- |
| 44 | B0 | `0x20 |` steering/current-fault/status aggregate |
| 45-46 | B1[3:0]:B2 (`B1[7:4]=0`) | signed12 coarse steering-angle-family source received on `0x025` (`FEBE8048`) |
| 47-48 | B3[3:0]:B4 (`B3[7:4]=0`) | signed12 EPS **Steering Angle** from `FEBE7D46`; this is the exact source also used by GTS DID1037 |
| 49 | B5 | signed **Steering Wheel Torque**, `0.1 N.m/count` |
| 50-51 | B6:B7 | signed motor-feedback/current-family proxy from source `FEBE6718` |

The motor-feedback field is **not an actuator request** and is not literal DID1151 amp units. DID1151 `Motor Actual Current Q Axis` uses a different underlying source (`FEBE670E`) even though the signals belong to the same physical feedback family.

This message therefore provides a second, low-rate EPS-origin steering-state/status plane alongside the richer protected `0x030`.

## 8. `0x4C8`: constant compatibility/status template

The normal packer constructs:

```text
09 00 00 00 00 00 00 00
```

Directly recovered fields are:

| Sig | Wire | Meaning |
| ---: | --- | --- |
| 52 | B0 | constant `0x09` |
| 53 | B1[7] | constant clear |
| 54 | B2:B3 | constant zero |

Signal 55 is assigned to PDU4 by configuration but has no literal generated pack-helper call anywhere in the canonical corpus. B4..B7 therefore remain at the zero initial image under the recovered normal path.

The exact OEM semantic of `0x4C8` remains unresolved. Its shape is consistent with an inherited compatibility/status PDU, but assigning a stronger name would exceed the evidence.

## 9. Diagnostic and special transmit endpoints

### UDS / ISO-TP

The exact diagnostic Rx table contains:

```text
0x7A1  primary physical request
0x777  functional/special diagnostic request path
0x7A0  secondary physical request
```

The class-2 Tx table contains:

```text
0x7A9
0x7A9
0x7A8
0x7A8
```

Thus application diagnostic responses use `0x7A9` for the primary/functional paths and `0x7A8` for the secondary physical endpoint.

### Extended XCP-shaped transport

The class-5 response route is raw hardware ID word `0x9FE00002`, i.e. extended CAN ID `0x1FE00002`. The paired request route is `0x9FDC0002`, i.e. `0x1FDC0002`.

The endpoint is structurally present, but exact F33 stock execution is disabled: fixed CodeFlash state at `0x30D68 = 0x5A` makes the protocol gate at `0x98E80` reject execution before CONNECT/opcode handling. It therefore belongs in the complete Tx inventory but not in the stock-reachable normal protocol surface.

## 10. On-car wire evidence and the remaining discrepancy

Tracked on-car logs strongly confirm `0x030`:

- one retained route contains exactly 6,000 native src0 `0x030/32` frames over 59.993426 s, i.e. essentially 100 Hz;
- the larger SecOC oracle validates the inner checksum and freshness/MAC behavior frame-for-frame;
- source/bus census proves `0x030` originates on the EPS/chassis side rather than the camera side.

Two retained parked censuses contain thousands of native `0x030` frames while recording zero `0x351`, `0x394`, `0x4A3`, or `0x4C8` frames.

That absence is real **for those captures**, but it does not invalidate the firmware reconstruction. The exact firmware and retained PE1 RAM independently show:

1. all five messages configured in the normal Tx class;
2. all five in the active `0x10` Tx group;
3. all five cyclic PDU state bytes active (`0x81`);
4. all five periodic timers armed;
5. the four classic messages routed through a real sibling CanIf HTH on the same lower driver node as the FD path.

Therefore the precise current statement is:

> `0x351`, `0x394`, `0x4A3`, and `0x4C8` are genuine, scheduler-armed EPS transmit PDUs in exact F33 firmware, but they have not been observed in the retained external CAN captures we currently possess.

The reason for this runtime-versus-capture discrepancy remains unresolved.
Selective forwarding at the EBU/arbitration junction is a **hypothesis**:
under that model, the EPS sends the classic PDUs locally but the junction only
forwards0x030 to the Panda-visible segment. The retained evidence does not
establish that per-PDU local transmission premise.

The lifecycle above retains distinct software failure boundaries.

## 11. Consequence for DBC work

For exact F33, message ownership and semantics should now be derived from this firmware-backed map rather than inherited Toyota public-DBC names.

In particular:

- `0x030` originates from EPS.
- its security trailer is genuinely Toyota SecOC `FV4 || MAC28`.
- it combines physical feedback with EPS cooperative-control and inhibit state.
- `0x4A3` is another EPS-origin steering-state/feedback PDU.
- `0x351` and `0x394` project EPS status/fault state.
- `0x4C8` should remain unnamed beyond its recovered structural role until Toyota semantics are closed.

The machine-readable artifact should be treated as the canonical exact-F33 transmit inventory for subsequent DBC and openpilot work.
## 12. On-car routing evidence

The September-18 exact-F33 experiment records two distinct results:

- The EPS authentication oracle matched three of three captured native
  `0x08A` samples.
- A separate byte-exact ID0 replay completed through the EPS lower transmit
  path, but no matching frame appeared on the healthy Panda-visible stream.
  This bounds that tested outward route; it does not identify the downstream
  forwarding implementation.

The retained result supports separating signing from final publication.
Current software ownership is specified in the
[runtime contract](../architecture/toyota-tss3-minimal-runtime.md), not by the
experimental transport implementations used during this measurement.

The post-repin READY capture also separates three network roles: chassis/state
on bus 0, native FRC requests on bus 2, and radar objects on bus 1. Native
`0x00F` originates on bus 0; its bus-2 appearance is a forwarded echo.
This source/echo distinction matters when interpreting old stock-harness
captures. The maintained topology has one owner in the runtime contract.
