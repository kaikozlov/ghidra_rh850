# Camry F33 EPS transmit surface (`8965F3307000`)

This document closes the transmit surface of the exact 2026 Camry F33 EPS application image `8965F3307000`.

The structural source of truth is `firmware/camry-8965F3307000/CodeFlash.bin` (SHA-256 `42dce8efc42f6ae31718e7713fa2d26bb9191b4a82439778aee4d7afded9b0e7`), cross-checked against the canonical decompiler corpus, retained PE1 RAM, GTS+/Techstream diagnostic semantics, and retained on-car CAN captures. The machine-readable reduction is `data/generated/camry_8965F3307000_eps_tx.json`, regenerated by `tools/targets/camry/analysis/analyze_camry_f33_eps_tx.py` and verified by `tests/verify_camry_f33_eps_tx.py`.

“Complete” here means the exact firmware's complete configured transmit surface, normal-message pack geometry, direct application writers, scheduler, lower routing, protection, diagnostic/special transmit endpoints, and every OEM semantic join we can actually prove. Where Toyota's OEM name for a field is not closed, this document keeps the structural meaning rather than importing a stale public-DBC label.

## 1. Executive result

The exact F33 EPS has **five normal generated-COM transmit I-PDUs**:

| PDU | CAN ID | Format | Bytes | Cycle | Role recovered from exact firmware | Protection |
| ---: | ---: | --- | ---: | ---: | --- | --- |
| 0 | `0x030` | CAN-FD | 32 | 10 ms / 100 Hz | protected EPS status, feedback, and cooperative-control state | inner additive checksum + SecOC `FV4 || MAC28` |
| 1 | `0x351` | classic CAN | 4 | 1000 ms / 1 Hz | electrical-monitor/status projection | direct CanIf, no configured SecOC |
| 2 | `0x394` | classic CAN | 3 | 300 ms / 3.333 Hz | lossy projection of a 17-state internal fault/state classifier | direct CanIf, no configured SecOC |
| 3 | `0x4A3` | classic CAN | 8 | 500 ms / 2 Hz | redundant steering-angle, driver-torque, motor-feedback, and status PDU | direct CanIf, no configured SecOC |
| 4 | `0x4C8` | classic CAN | 8 | 980 ms / 1.0204 Hz | mostly constant compatibility/status template; exact OEM role unresolved | direct CanIf, no configured SecOC |

The EPS also has non-cyclic transmit endpoints:

- UDS/ISO-TP responses on `0x7A9` and `0x7A8`.
- An extended-ID XCP-shaped response endpoint at `0x1FE00002`, paired with request ID `0x1FDC0002`; the transport exists structurally but stock exact-F33 execution is gated off before protocol dispatch by fixed CodeFlash state.

This corrects the old public-DBC interpretation of `0x030` as `POWERTRAIN_STATUS_3 (ECM)`: on this calibration, **`0x030` is unquestionably EPS-origin**.

## 2. Generated-COM table and scheduling

Class-0 CanIf records at `0x21F58` are:

```text
PDU0  raw ID 0x40000030   CAN-FD 0x030   handle 0
PDU1  raw ID 0x00000351   classic 0x351  handle 1
PDU2  raw ID 0x00000394   classic 0x394  handle 1
PDU3  raw ID 0x000004A3   classic 0x4A3  handle 1
PDU4  raw ID 0x000004C8   classic 0x4C8  handle 1
```

The five PDU descriptors at `0x226C0` are:

```text
0x030: cycle=2    length=32
0x351: cycle=200  length=4
0x394: cycle=60   length=3
0x4A3: cycle=100  length=8
0x4C8: cycle=196  length=8
```

The exact F33 foreground scheduler is 5.000 ms, so those descriptor periods directly produce the cycle times above.

All five belong to the same generated-COM Tx I-PDU group. The group starts at PDU0, contains five PDUs, and every member has communication mask `0x10`. The retained PE1 RAM snapshot proves that this is not merely dormant configuration:

```text
BswM mask/complement        10 EF
Tx group desired/current    10 10
PDU runtime states          81 81 81 81 81
periodic countdowns         2, 139, 23, 31, 143
configured periods          2, 200, 60, 100, 196
```

Every periodic counter is nonzero and within its configured period, so **all five cyclic schedulers were armed in the retained on-car runtime snapshot**.

There is also an important direct-pack distinction:

- `0x351` and `0x394` use `0x7D1DC`, the change-aware signal pack helper. On an actual value change it calls `0x7E196(pdu, 0x80)`, so those messages can request event transmission in addition to the periodic schedule.
- `0x030`, `0x4A3`, and `0x4C8` use the raw pack helper `0x7D31E`; their direct packers do not themselves create a change-triggered transmit request.

The normal application packers are live, not dead configuration: the F33 application task reaches all five through the normal source-preparation/packing sequence.

| --- | --- | --- | --- | --- |

## 4. `0x030`: protected EPS control-status / feedback PDU

### 4.1 Protection

The application packer `0x4C97A` constructs B0..B27. SecOC appends B28..B31 afterward.

```text
MAC input = 00 30 || application B0..B27 || full freshness[6]

B28[7:6] = message counter low2
B28[5:4] = reset counter low2
B28[3:0] = MAC28[27:24]
B29       = MAC28[23:16]
B30       = MAC28[15:8]
B31       = MAC28[7:0]
```

Exact profile:

- SecOC DataID `0x0030`
- 28 authenticated application bytes
- full freshness 46 bits in six-byte storage
- transmitted freshness 4 bits
- authenticator 28 bits
- Freshness Value ID 3
- ICU-S command 5 / MAC generation
- ICU-S key selector 4

B7 is a separate inner application checksum:

```text
B7 = low8(B0 + B1 + ... + B6 + 0x38)
```

The retained pre-SecOC generated-COM buffer has B28..B31 all zero while live wire frames carry changing `FV4 || MAC28`, proving the security tail is appended below the application packer.

## 5. `0x351`: electrical-monitor/status projection

Wire-visible application fields:

| Sig | Wire | Meaning |
| ---: | --- | --- |
| 38 | B2[7:5] | debounced electrical-monitor/status code |
| 39 | B2[4] | companion force/special-status flag |

The base state follows:

```text
FEBEBDE4 -> FEBEE82B -> 0x4C1C0 -> FEBE8100 -> signal 38
```

`0x4C1C0` applies a calibration count of 7 before updating the projected state. `0x4C216` has a separate broad force path that writes code 7 and flag 1 when `(FEBE6764 & 3) != 0 && FEBE8143 != 0`.

This family is related to Toyota Techstream DTC `C159B49`, **Power Steering Motor "B" Terminal Voltage Detect Circuit / Internal Electronic Failure**, but the broad force-7 state is not equivalent to the DTC and should not be renamed after it.

B0, B1, B2[3:0], and B3 remain at the initial zero image absent another mechanism.

## 7. `0x4A3`: redundant steering state / feedback

All eight bytes are directly produced:

| Sig | Wire | Meaning |
| ---: | --- | --- |
| 44 | B0 | `0x20 |` steering/current-fault/status aggregate |
| 45-46 | B1[3:0]:B2 (`B1[7:4]=0`) | signed12 coarse steering-angle-family source received on `0x025` (`FEBE8048`) |
| 47-48 | B3[3:0]:B4 (`B3[7:4]=0`) | signed12 EPS **Steering Angle** from `FEBE7D46`; this is the exact source also used by GTS DID1037 |
| 49 | B5 | signed **Steering Wheel Torque**, `0.1 N.m/count` |
| 50-51 | B6:B7 | signed motor-feedback/current-family proxy from source `FEBE6718` |

The motor-feedback field is **not an actuator request** and is not literal DID1151 amp units. DID1151 `Motor Actual Current Q Axis` uses a different underlying source (`FEBE670E`) even though the signals belong to the same physical feedback family.

This message therefore provides a second, low-rate EPS-origin steering-state/status plane alongside the richer protected `0x030`.

## 9. Diagnostic and special transmit endpoints

### UDS / ISO-TP

The exact diagnostic Rx table contains:

```text
0x7A1  primary physical request
0x777  functional/special diagnostic request path
0x7A0  secondary physical request
```

The class-2 Tx table contains:

```text
0x7A9
0x7A9
0x7A8
0x7A8
```

Thus application diagnostic responses use `0x7A9` for the primary/functional paths and `0x7A8` for the secondary physical endpoint.

### Extended XCP-shaped transport

The class-5 response route is raw hardware ID word `0x9FE00002`, i.e. extended CAN ID `0x1FE00002`. The paired request route is `0x9FDC0002`, i.e. `0x1FDC0002`.

The endpoint is structurally present, but exact F33 stock execution is disabled: fixed CodeFlash state at `0x30D68 = 0x5A` makes the protocol gate at `0x98E80` reject execution before CONNECT/opcode handling. It therefore belongs in the complete Tx inventory but not in the stock-reachable normal protocol surface.

## 10. On-car wire evidence and the remaining discrepancy

Tracked on-car logs strongly confirm `0x030`:

- one retained route contains exactly 6,000 native src0 `0x030/32` frames over 59.993426 s, i.e. essentially 100 Hz;
- the larger SecOC oracle validates the inner checksum and freshness/MAC behavior frame-for-frame;
- source/bus census proves `0x030` originates on the EPS/chassis side rather than the camera side.

Two retained parked censuses contain thousands of native `0x030` frames while recording zero `0x351`, `0x394`, `0x4A3`, or `0x4C8` frames.

That absence is real **for those captures**, but it does not invalidate the firmware reconstruction. The exact firmware and retained PE1 RAM independently show:

1. all five messages configured in the normal Tx class;
2. all five in the active `0x10` Tx group;
3. all five cyclic PDU state bytes active (`0x81`);
4. all five periodic timers armed;
5. the four classic messages routed through a real sibling CanIf HTH on the same lower driver node as the FD path.

Therefore the precise current statement is:

> `0x351`, `0x394`, `0x4A3`, and `0x4C8` are genuine, scheduler-armed EPS transmit PDUs in exact F33 firmware, but they have not been observed in the retained external CAN captures we currently possess.

The final reason for that static/runtime-vs-capture discrepancy is not yet statically closed. The **leading topology hypothesis** is selective forwarding at the EBU/arbitration junction between the EPS-native chassis segment and the Bus-4 segment visible to Panda/FRC: the EPS transmits all five PDUs locally, while the EBU forwards `0x030` onto Bus 4 because upstream ADAS consumers need its steering-wheel-torque/control-status information and does not forward the four classic sibling status PDUs because they have no Bus-4 consumer. Under that model, the retained captures are observing the far side of a selective gateway rather than the EPS's native transmit segment.

This interpretation fits all currently recovered evidence: the generated-COM scheduler, PduR, CanIf, and lower driver objects are live inside the EPS, yet only `0x030` appears at our external Bus-4 observation point. It remains a **hypothesis**, not a recovered routing fact, until the EBU RX→TX/gateway table or equivalent junction logic is reconstructed. The practical next question is therefore not “why does the EPS fail to send these four PDUs?” but **“which EPS-origin PDUs does the EBU/arbitration junction forward onto Bus 4?”** We should not paper over the discrepancy with a fabricated EPS-side “disabled” flag: the retained HTH idle state is normal, and the firmware evidence says the transmit routes are live.

## 11. Consequence for DBC work

For exact F33, message ownership and semantics should now be derived from this firmware-backed map rather than inherited Toyota public-DBC names.

In particular:

- `0x030` is EPS-origin, not ECM-origin.
- its security trailer is genuinely Toyota SecOC `FV4 || MAC28`.
- it is not merely “telemetry”: it combines physical feedback with EPS cooperative-control and inhibit state.
- `0x4A3` is another EPS-origin steering-state/feedback PDU.
- `0x351` and `0x394` are status/fault projections, not generic powertrain messages.
- `0x4C8` should remain unnamed beyond its recovered structural role until Toyota semantics are closed.

The machine-readable artifact should be treated as the canonical exact-F33 transmit inventory for subsequent DBC and openpilot work.
## 12. Bounded `0x08A` sender experiments

The recovered production Tx stack now has a field-ready discriminator for the
open question that this report leaves at the EBU boundary. The existing F33
command-5 probe first has a non-transmitting `verify-native-08a` mode that asks
selector 4 to reproduce captured stock `0x08A` MAC28 values. A separate volatile
RAM probe then replays **one byte-exact stock Target-Lateral-ID0 `0x08A`** through
`FUN_00085112`, HTH0 / lower driver object 47 (node 1, mailbox 0), with CAN ID word `0x4000008A`. Its software-PDU handle is
`0x00F0`; exact F33 lower object 47 stores that value in pending-handle cell
`FEBE502A`, and physical Tx completion removes that unique ownership before
dispatching no-op `0x8152E`. Because stock `0x030` shares HTH0, the next sampled
handle can already belong to the successor stock Tx rather than idle `0xFFFF`.
The probe therefore uses departure from `0x00F0` as its completion witness and
cannot forge an upper-layer `0x030` confirmation. It permits one successful
Tx per boot and refuses nonzero Target Lateral ID; it does not sign, alter
freshness, touch B6, or write flash.

The second experiment is intentionally a routing test, not an actuation or
receiver-acceptance test. If the otherwise-unique captured FV4+MAC frame becomes
visible at Panda only after EPS lower-driver completion, the EPS-local Tx path
reaches the observed Bus-4 domain. If the lower driver physically completes the
replay but Panda never sees the exact frame, selective EBU/Brake-domain forwarding remains the leading
explanation and a comma-side sender with the EPS used only as a MAC oracle stays
the simpler architecture. Detailed field ordering and proof boundaries are in
[`../../exploit/ephemeral_runtime/camry_f33_08a_sender_experiments.md`](../../exploit/ephemeral_runtime/camry_f33_08a_sender_experiments.md).

### 12.1 Live result — 2026-09-18

Both discriminators have now run on the exact maintained F33 vehicle.

**Experiment A closed positive.** `verify-native-08a` completed all three requested
stock samples with `samples_matched=3/3`. For sample 3, the captured native MAC28
`d64e2a5` was reproduced exactly by EPS ICU-S selector 4 over domain
`008a || B0..B27 || freshness48`, with trip `620`, reset `1109`, and reconstructed
message counter `8`. This dynamically verifies the exact F33 EPS slot-4 command-5
path as a valid MAC oracle for stock `0x08A`; the remaining oracle problem is
transport/latency, not key-domain compatibility or authenticated-input framing.

**Experiment B closed negative for outward routing.** The EPS helper replayed one
byte-exact stock ID0 frame
`0000000080000012ffae00ffae7fff007fff004b0000000000002e0088f34177`
through HTH0 / lower object 47. The lower writer returned `0`, enqueue count became
`1`, the unique pending software handle `0x00F0` completed and returned to successor
`0xFFFF`, and the helper recorded `completion_count=1`. Thus the exact F33 lower
CAN path physically completed the requested transmit. The Panda-visible Bus-4
stream remained healthy but contained zero copies of the replayed frame, yielding
`eps_origin_08a_not_observed_at_panda`.

This closes the practical topology discriminator: **the current EPS-local Tx path
is not a usable final `0x08A` sender to the Panda-visible/Brake-side Bus-4 domain.**
The observation is consistent with selective EBU/junction forwarding or an
equivalent downstream routing boundary; it does not by itself identify the
forwarding implementation. The preferred integration shape is therefore EPS as
a TSK/CMAC oracle and comma as final `0x08A` emitter at the visible Bus-4 boundary.

The same run also gives a direct stock cadence bound. Five native `0x08A` frames
were observed in the 120-ms uniqueness window, and the post-treatment stream
continued with monotonically advancing B26 low-6 sequence values, consistent with
approximately **40 Hz / 25 ms** native publication. That is the rate target for a
real-time oracle transport.

### 12.2 High-rate oracle transport candidate

The selected A-positive/B-negative architecture now has an exact-F33 runtime
candidate: `camry_f33_08a_oracle_stream`. It deliberately does **not** transmit
`0x08A`. Host requests use the stock physical `0x7A1` CanTp/PduR reassembly path
into DCM buffer `FEBE5651`; after the exact `0x79EDE` receive drain, the resident
passes the complete 36-byte `00 8A || application[28] || freshness[6]` domain to
stock command 5 / selector 4. The first four CMAC bytes are returned on `0x7A9`
through exact diagnostic HTH2 lower object 53 (node 1 / mailbox 6) using special
no-op completion handle `0x00F0`, so the private reply does not fabricate a
CanTp TxConfirmation.

The host protocol is fixed at a 40-byte request N-SDU and one 8-byte response.
A retained Experiment-A domain/MAC pair (`d64e2a5`) is the mandatory live
known-answer gate. Only after that matches should the bounded 20-request / 25-ms
benchmark be used to determine whether this RPC satisfies the observed ~40-Hz
stock `0x08A` cadence. The runtime contains no host or EPS `0x08A` transmit,
no B6 transmit, no SecOC-result bypass, and no key extraction.

The first field carrier (`3799d97e`, payload `178cd81b…993bd`) returned the stock
application but then read back an all-zero high-tail resident/state and no low
helper installation. The corrected carrier therefore does not copy executable
code after startup: the helper stays at the already-live-qualified executable
GlobalRAM slot `FEF07C00` and is invoked there directly; low RAM is data/state
only. The superseded payload must not be rerun. The subsequent live retry proved the
corrected resident survives and initializes, but its first C9 request left
`request_count=0`; the ingress tag check was still incorrectly requiring DCM
B0:B1=`C9 C9`. The oracle now follows the already-live C6/C7 rule and keys only
on durable N-SDU **B1=`C9`**, because B0 is the unsupported SID and is not a
stable recurring-carrier byte. Field procedure:
[`camry_f33_08a_oracle_stream.md`](../../exploit/ephemeral_runtime/camry_f33_08a_oracle_stream.md).

### 12.3 Live oracle KAT closes crypto; CanTp STmin is now the bottleneck

The corrected `961750c2` runtime completed the retained Experiment-A domain with
MAC28 `d64e2a5` exactly, and resident telemetry recorded command5 rc0/done1/status0,
output length 16, response lower-Tx rc0, and one request/success/response. This
closes the streaming command5 path itself.

The physical `0x7A1` CanTp receiver advertised flow-control `30 00 28`, i.e.
block-size zero and **STmin 40 ms**. Honoring that value across five Consecutive
Frames produced ~244.5 ms request-start→response, whereas final-CF→signed reply
was ~27 ms. Exact F33's dedicated `0x1FDC0002` ingress is not a CAN-FD escape:
`0x830D0` rejects lengths greater than 8 before copying to `FEBE4C34`.

The host-only 0-ms CF-spacing probe then succeeded byte-for-byte. F33 still
advertised 40-ms STmin, but accepted the five CFs with no host delay and returned
the same MAC28 `d64e2a5`. Full request-start→response fell to **19.071 ms** and
final-CF→signed reply to **3.957 ms**; resident request/success/response counters
advanced coherently from 1/1/1 to 2/2/2. Thus the complete non-actuating oracle
transaction fits within the observed ~25-ms native `0x08A` period on this sample.
The next gate is a sustained 20-request / 25-ms schedule using the same 0-ms CF
gap, with per-transaction RTT and scheduler lateness recorded.

### 12.4 Sustained oracle reliability closes; host batching is the remaining cadence optimization

The 20-request fast-CF benchmark completed all 20 transactions successfully with
resident counters advancing coherently to 22 requests / 22 successes / 22
responses. Median full RTT was 22.721 ms, p95 28.980 ms, and max 39.244 ms; six
of 20 exceeded the 25-ms native period. Median final-CF->signed-response was only
7.219 ms (p95 12.314, max 13.124), while host scheduled-start lateness reached
24.651 ms.

Inspection of the host path found that the shared `PandaTap.can_send_many()`
implementation was not actually batching: it looped over individual
`can_send()` calls, causing five Panda USB writes for each five-CF request. The
oracle host path now bypasses that wrapper behavior locally and invokes Panda's
native `can_send_many()` under the existing send lock, leaving the live resident,
authenticated domain, and response path unchanged. Additional timing splits
measure FF->FC, CF batch submission, and final-CF->response independently.

### 12.5 Native Panda batching leaves only the FC handshake as the cadence outlier

The native-Panda CF batching follow-up again completed 20/20 oracle transactions.
Median full RTT fell to 20.355 ms, p95 to 23.531 ms, and max scheduled-start
lateness to 3.919 ms. Exactly one transaction exceeded the 25-ms period: seq 28
at 27.239 ms, with 16.553 ms spent waiting FF->flow-control. CF batch submission
was normally below 1 ms. The remaining bounded discriminator is therefore one
non-actuating KAT that submits FF+all five CFs in a single Panda batch without
waiting for FC; if accepted, the final host-side handshake jitter is removable.

### 12.6 Immediate FF+CF burst is too early; fixed-delay receiver readiness is next

The one-batch FF+five-CF no-FC probe timed out and resident counters remained
42/42/42, proving the physical CanTp receiver did not complete the N-SDU. F33
therefore needs some interval after FF before accepting CFs even though the host
need not necessarily wait to *receive* FC. The next bounded test sends FF, waits
a fixed 5 ms, then submits all five CFs in one Panda batch; this leaves the live
resident and authenticated domain unchanged and tests receiver readiness rather
than host-observed FC latency.

### 12.7 Receiver-readiness threshold is 1.5-2.0 ms on the live sample

Single KATs without waiting for host receipt of FC established a sharp boundary:
0/1.0/1.5-ms FF->CF delays failed before the resident, while 2.0 ms and 5.0 ms
succeeded with full RTTs of 13.538 ms and 16.282 ms respectively. The sustained
candidate therefore uses a conservative 2-ms fixed delay, native Panda CF batch,
and the unchanged non-actuating known-answer domain on a 25-ms schedule.
