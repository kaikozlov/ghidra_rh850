# Corolla `8965F1208000` EPS comparative analysis

> **Scope:** Span's reported 2025 Toyota Corolla Hybrid EPS, observed F181
> `8965F1208000 / 8A3111213000`.
>
> **Status:** comparative static analysis closed to the same application-code
> boundary as the 2023 `8965H1202000` Corolla corpus; calibration meaning and
> remaining hardware-only questions are explicitly bounded below.
>
> **Evidence:** tracked raw acquisition + deterministic byte comparison + fresh
> target-native Ghidra structure + independent semantic resolvers + direct
> comparison with canonical Sienna `8965B4512000`.

## 1. Executive result

Span's 2025 image is not merely "similar" to the 2023 albinoelephant Corolla.
It is the **same executable/application generation with a different low
calibration/identity image**.

The normalized 1-MiB CodeFlash images differ in only **2,190 bytes**. Every
changed byte lies in `0xA004..0x17DFF`; from `0x17E00` through `0xFFFFF` the two
images are byte-identical. In particular:

- the complete high-CodeFlash CRC region beginning at `0x18000` is identical;
- the repository's application-function region `0x20000..0xFFFFF` is identical;
- a fresh clean Span Ghidra import produces the same 5,425-function structural
  fingerprint corpus as the clean H import, byte-for-byte, SHA-256
  `b7acbb2265b97d3811652d75900850b48d799eb5f0e59b7e14d0e6d4952b3051`;
- Span-vs-Sienna produces the same 6,375-row exact-body transfer result, the
  same 2,542 unique complete instruction-shape homologs, and the same 1,113-row
  named transfer ledger as H-vs-Sienna;
- the generated application Rx table, SecOC queue, Gate-2 verifier, runtime
  scheduler/COM anchors, diagnostics implementation, XCP implementation,
  steering supervisor, motor-control implementation, and NvM code therefore
  transfer at the **code/table** level from H to Span at the same addresses;
- low-region calibration/identity bytes remain a separate behavior boundary and
  are not silently promoted to semantic equality.

The most important openpilot consequence is also the same as for H: **do not
port the Sienna `0x2E4/0x131` steering bridge by assumption**. Span's resolved
Gate-2 queue is exactly `0x00F / 0x0D7 / 0x0B6`; the Sienna `0x2E4/0x131`
profiles are absent from both its normal-Rx table and its SecOC queue.

### 4.2 The low delta contains active unit calibration, not just identity/checksum fallout

The first comparison pass correctly bounded the 2,190 changed bytes below

The application obtains that bank indirectly through `FUN_00050e6a`, which

The exhausted machine report is
`data/generated/corolla_8965F1208000_low_calibration_delta.json`, regenerated by

#### 4.2.1 Nine-record unit-calibration / identity family at `0xA000`

The application uses the **16-bit** count `9 @ 0x2A974` and a byte-identical
nine-entry descriptor table at `0x2AB8C`. Each 12-byte descriptor is
`{u16 length, u16 zero padding, u32 runtime-RAM destination, u32 CodeFlash source}`. Reading the
count as a dword would incorrectly merge the adjacent `0x0012` field into
`0x00120009`; the verifier explicitly guards this width.

| record | source | length | RAM destination | Span/H payload delta | bounded role |
|---:|---:|---:|---:|---:|---|
| 0 | `0xA000` | `0x28` | `FEBEF600` | 26 bytes | active multi-channel gain/offset calibration |
| 1 | `0xA030` | `0x08` | `FEBEF630` | 0 | unresolved |
| 2 | `0xA040` | `0x40` | `FEBEF640` | 37 | active six-channel calibration/state coefficients |
| 3 | `0xA088` | `0x10` | `FEBEF688` | 6 | active three-way motor-angle offset coefficients |
| 4 | `0xA0A0` | `0x10` | `FEBEF6A0` | 0 | marker `A55A5AA5` + Toyota part number `8965012N50` (89650-12N50); Sienna's same-shaped record carries `8965045170` (89650-45170); Techstream `ECU Part Number` vocabulary — evidence-bounded identity, no recovered firmware reader |
| 5 | `0xA0B8` | `0x308` | `FEBEF6B8` | 758 | three active 256-byte motor-rotation-angle correction LUTs |
| 6 | `0xA3C8` | `0x108` | `FEBEF9C8` | 0 | active-addressed 256-byte **zero** correction table |
| 7 | `0xA4D8` | `0x28` | `FEBEFAD8` | 9 | marker + 20-char unit serial embedding the same `89650-12N50` part-number family (matches observed F18C); Techstream serial-display vocabulary — evidence-bounded identity, no recovered firmware reader |
| 8 | `0xA508` | `0x18` | `FEBEFB08` | 3 | changed opaque unit record |

The generic family code is also recovered: `0x6009E/0x604AA` validate/read the
CodeFlash-backed records, `0x60418/0x60010` update the runtime RAM copy, and
`0x602A0` initializes the family. Eight records have a four-byte terminal fixup
for which `zlib.crc32(payload || fixup) == 0xFFFFFFFF`; record 1 is the sole
zero-fixup exception. This describes the observed record integrity convention;
it does **not** claim application self-programming of CodeFlash.

The active dataflow is not inferred from record shape alone. The fixed-index
readers first stage the validated CodeFlash data and separate copy/gate routines
promote it into working state. Record 0 follows
`0x6009E(0x200) -> 0x2DF98 -> FEBE679E..67C0 -> 0x2DE9A -> FEBE6776..6798`;
`0x43528` then consumes those live sign-dependent multi-channel gain/offset
values. Record 2 follows
`0x6009E(0x202) -> 0x2FB36 -> FEBE68F4..6928 -> 0x2F40A/0x2F318 -> FEBE6896..68CA`;
`0x2FC22` bounds-checks that live coefficient set, while the related six-channel
state machinery can feed derived/current values back through the runtime-copy
path `0x30008 -> 0x60010(0x202)`. Record 3 follows
`0x6009E(0x203) -> 0x2DAA8 -> FEBE671A/1C/1E -> 0x2DA0A -> FEBE6712/14/16`;
`0x42700 -> 0x42720` then selects and consumes one coefficient. Those three
coefficients change from `244, 0, 270` on H to `-786, -795, -723` on Span before
the downstream angle/trigonometric-vector path.

Record 5 is the clearest direct behavioral delta. `0x42C42` selects mode
`0/1/2`; `0x42B98` calls `0x50E6A`, indexes `0xA0C0 + mode*0x100`, linearly
interpolates adjacent signed bytes, and subtracts the correction from the
rotation-angle input. The three 256-byte curves change in **254 / 253 / 251**
positions respectively. Record 6 is the sibling path used by `0x42D28`, which
indexes `A000 + 0x3D0 = 0xA3D0` (record-6 payload+8). The **entire 0x108-byte
payload is zero** in both specimens, including an absent `A55A5AA5` marker; its
terminal CRC fixup is nevertheless valid. The addressed 256-byte table is therefore
a formatted null/default slot and contributes zero with these retained bytes.

This proves that Span-vs-albino is **not** merely serial/F181/checksum drift.
It does **not** prove a 2023-to-2025 model-year tuning revision. The specimens are
different physical ECUs, so the changed values may be per-unit manufacturing
calibration, service calibration, variant tuning, or some combination. The
firmware corpus cannot distinguish those origins, and the report deliberately
uses bounded unit-calibration language rather than assigning unavailable OEM
field names.

#### 4.2.2 `0x10000..0x17DEF`: structured shadow bank, semantics still bounded

`FUN_0005c992` and the byte-identical XCP-E4 helper `FUN_00092700` copy exactly
CodeFlash `0x10000..0x17DEF` to `FEBF7C00..FEBFF9EF`. This source span accounts
for **1,311** of the 2,190 changed bytes. Its structure is real: for example,
`0x120F4..0x1237B` contains eighteen aligned `0x24`-byte rows, each eight dwords
followed by a `0x7FFFFFFF` sentinel (the first two rows are unchanged), and the larger `0x10100+` bank preserves the
same sentinel geometry between H and Span while numeric coefficients differ.

No reviewed target-native application path has yet established the semantic CPU
consumer of those `0x10000+` shadow values beyond the startup/E4 copies and XCP
calibration-page bookkeeping. Apparent aligned "pointers" found in application
data were packed metadata/numeric values, not dereferences. Computed pointers or
an undocumented overlay remain possible. Therefore these bytes are **structured
and variant-specific, but semantically bounded**; they are not promoted to named
motor/steering tuning merely because their shape resembles calibration tables.

#### 4.2.3 The final 16 changed bytes are the region-0 AES-CMAC tag

The low shadow span ends at `0x17DF0`; including its terminal fixup at
`0x17DEC..0x17DEF`, `zlib.crc32(0x10000..0x17DEF) == 0xFFFFFFFF` in both images.
The following 16-byte field `0x17DF0..0x17DFF` changes in all 16 positions and
is **not opaque**: it is the region-0 AES-CMAC tag.

The boot integrity-region table at `0x8DE0` (three 28-byte rows, byte-identical
between specimens) declares, per row: region start, end-inclusive, CMAC tag
address (field +8), validity-marker address (+0xC), a field at +0x10, an enable
flag, and the CRC descriptor-table pointer. Region 0 is `0x10000..0x17DFF` with
its tag at `0x17DF0` — exactly the region's final 16 bytes — and its marker at
`0x17E00` (`5AA5A55A`, unchanged). Region 1 is `0x18000..0xFFDFF` (tag
`0xFFDF0`, marker `0xFFE00`); because H and Span are byte-identical above
`0x18000`, region 1 does not enter this delta.

The verification chain is target-native and byte-identical between specimens
(all bodies hash-pinned in the artifact):

- `boot_memory_region_get_cmac_tag @0x3376` — iterates the `0x8DE0` table and
  returns field +8 (`0x17DF0` for region 0);
- `routine_verify_crc_cmac_task @0x591A` — the CRC+CMAC routine task; resolves
  region start/length and starts verification;
- `payload_cmac_verify_enqueue @0x6E9E` -> `payload_cmac_verify_setup
  @0x7106` — stores the tag pointer, initializes the AES-CMAC IV block, and sets
  message current = start, end = start + length − 0x10, i.e. the CMAC covers
  `0x10000..0x17DEF` with the tag excluded;
- `payload_cmac_verify_step @0x7154` — pumps 16-byte blocks; on the final block
  it byte-compares all 16 generated CMAC bytes against the stored tag;
- `aes_cmac_process_block @0x7DF0` (CBC-MAC-style XOR with subkey handling and
  `0x80` final-block padding), AES core `0x7336`, `aes_cmac_generate_subkeys
  @0x7D34`.

The complete 16/16-byte tag change between H and Span is therefore **expected
cryptographic integrity fallout** of the changed calibration page, not
independent tuning data.

Boundary: the verification role and code path are proven, but the exact DID
`0x201` key material and DID `0x202` IV/build-time inputs used by the factory
to produce the stored low-region tag are not recovered from this static
image/session; zero-valued DID material used by public RAM fixtures does not
reproduce the stored tag. The boot payload-build root at `0xBFD8` is present in
the image, so this is an input-recovery boundary, not a statement that the key
is absent. Whether the region-1 tag slot is programmed on this generation is
not asserted (its `0xFFDF0..0xFFDFF` filler is identical in both specimens).

Together the disjoint accounting is exact: **863** changed bytes in the A000
record bank + **1,311** in the `0x10000..0x17DEF` shadow source + **16** in the
region-0 AES-CMAC tag = **2,190** total. No low difference is left unclassified
by location, and the final sixteen are now closed semantically as integrity
material.

## 6. Boot trust, programming, and authenticated RAM

Span exposes the same two self-describing valid CRC regions as H:

- low region `0x10000..0x17DF0`, whose content/fixup changes with the Span
  identity/calibration image;
- high region `0x18000..0xFFDF0`, byte-identical to H.

The SecOC Gate-2 patch lies in the unchanged high region. A fresh semantic
resolver independently finds exactly one candidate:

```text

Gate-2 compare       0x88C62
original bytes       e0 d1
replacement          e0 01
branch               0x88C64

```

The high-region stock CRC fixup remains `0xAD59D70C`; after the Gate-2 rewrite,
the deterministic replacement is `0xDD5F1477`, producing residue
`0xFFFFFFFF`. These are the same H values because that full region is exact.

Span also independently upgrades the authenticated-RAM bootstrap profile to
**observed**. Its field acquisition executed target-built range payloads through
the shared `0x0203 -> 0x0201 -> 0x0202`, `FEBF0000/0x1000`, `10F0`, `FF00`

separately from H.

Evidence boundary: this does **not** prove byte-for-byte acceptance of the
repository's Sienna `ram_dump_payload.bin`; that exact fixture cryptographic
proof remains Sienna-specific. It proves that Span's target-built acquisition
used the same authenticated-RAM architecture and that its firmware roots/flow

The existing XCP retention result also survives unchanged: unauthenticated XCP
can place bytes in `FEBF7C00..FEBFFBFF`, and the live application→boot
PROGRAMMING handoff does not clear that supervisor-executable RAM. This remains
**code placement + retention**, not a recovered no-auth PC pivot.

|---:|---:|---:|
| `0x00F` | 8 | 9 |

## 9. Steering and motor-control implications

Span carries the exact H application that was already decompiled stage-by-stage.
Therefore the H implementation-level conclusions transfer:

- the Sienna `0x131` LTA angle-command smoothing stage is absent/unpaired;
- the Sienna `0x2E4/0x131` normal receive modes are absent from generated Rx;
- the H/Span `0x0B6` FD interface is supervisory: gate/mode/sequence/scaling and
  validity state are recovered, while its only signed 16-bit scalar has no
  recovered direct runtime consumer as a torque command;
- the retained Sienna-shaped external torque clamp/rate branch exists in code
  but is zero-fed by the complete direct-writer evidence;
- the ordinary EPS steering supervisor and motor-control implementation remains
  substantial and active, including the recovered Clarke/Park, d/q PI,
  limiting, phase conditioning, duty publication/selection, and TSG3 commit
  chain;
- H's expanded plausibility/estimator machinery is present unchanged.

This does **not** mean every numerical control behavior is identical between the
2023 and 2025 vehicles. Low calibration material differs (§4.2), so gains,
thresholds or feature calibration can differ even where the code is exact.

For openpilot, the static problem is now narrower: there is no basis to reuse the
Sienna external steering ingress by ID. We need the actual 2025 Corolla command
provenance/interface, or proof that this generation exposes no remotely
commanded lateral mode through the mapped EPS Rx surfaces.

## 10. DataFlash / NvM comparison

The `R7F701383` has **32 KiB physical DataFlash**. Span's payload captured the
requested `FF200000..FF20FFFF` 64-KiB host range three times, but only the first
`0x8000` bytes are interpreted as physical DataFlash. The analyzer now supports
`--physical-prefix-size 0x8000` so provenance of the full host range is retained
without assigning NVM semantics to the upper half.

Tracked first-read report:
`data/generated/corolla_2025_span_dataflash_analysis.json`.

All three physical captures repeat the same high-level geometry:

```text
configured physical records             122
committed records                         61
triplicate records                         9
checkpoint records                        52
reference-enabled checkpoint envelopes    50
reference-disabled owner-28 envelopes       2  (117/118)
```

Objects `0`, `2`, and `5` each have three valid consensus copies in every Span

retain the same consensus payload hashes as albino/Sienna; object `2` is stable
across all three Span reads but differs from albino's mutable state.

Relative to the tracked albino read, Span adds exactly one committed checkpoint
slot: **storage index 104**. The owner-28 disabled ring remains slots `117/118`,
with Span generations `0x35/0x34` versus albino's older `0x25/0x24` epoch.
This is consistent with the same NvM format carrying different vehicle/runtime

Object-15 result boundary: the tracked CPU-visible triplicate geometry does not

SecOC oracle this does **not** prove absence of the opaque ICU-S key or prove a

## 11. Extended CodeFlash and RAM

Span's 48-KiB extended-CodeFlash dump has SHA-256
`90cc7b3d88e0c8b7ef330160ecb792134f5fbf9b9d8219c80d038a5451a15cc7` and is
**byte-identical to all three albino extended-CodeFlash reads**. This is an
additional invariant outside normal CodeFlash.

Runtime snapshots behave differently, as expected:

- Span GlobalRAM is 64 KiB; its differences versus the three albino GlobalRAM
  snapshots are only `867 / 854 / 907` bytes, comparable to albino's own
  time-to-time churn (`782..791` bytes).
- Span PE1 LocalRAM and the later self-alias LocalRAM are complete 128-KiB
  views and differ by 3,678 bytes.

## 13. Remaining evidence boundary / next work

The broad static application RE is no longer an open task for Span. Repeating
H decompilation on identical bytes would add ceremony, not evidence. The
remaining high-value questions are narrower:

1. **Interpret the remaining structured shadow bank.** The `0xA000` unit-calibration
   family is now structurally closed through active motor/sensor consumers, but
   `0x10000..0x17DEF` still lacks a proved semantic CPU dereference. Correlate those
   rows with OEM/Techstream concepts only where independent evidence permits;
   do not treat specimen differences as a proved model-year tuning revision.
2. **Find the real lateral-command provenance, if one exists.** The known
   Sienna `2E4/131` ingress is absent; B6 is not statically a replacement torque
   command. Use vehicle traces plus the already-closed COM/supervisor graph.
3. **Dynamic ICU-S policy only if needed.** Slot-4 command-5 permission/timing
   and any live cryptographic oracle remain hardware questions, not missing
   static reverse engineering.
4. **Runtime-retention geometry for an H/Span-specific RAM runtime.** The
   semantic resolver closes code anchors but intentionally reports no
   image-bound RAM-execution geometry for this variant. The Sienna runtime
   manifest must not be transplanted blindly.
5. **Correlate mutable NvM state only with a concrete feature question.** The
   storage format is closed; slot 104/object-2 differences are facts, but naming
   them requires independent state/Techstream evidence.
