## Confirmed by Corolla field probes

Observed on a live vehicle (sources: calvinpark/openpilot
`tsk/COROLLA_INVESTIGATION.md`, Discord probe captures Jul 2026, and pinned
`dump/CLAUDE.md` for the 2026-08-19 route preflight). These are real
observations, not hypotheses:

- **Application software ID:** `8965F1208000`
- **Secondary software ID:** `8A3111213000`
- **Diagnostic bus:** CAN-FD (bus 1 carries 32-byte frames; EPS is on bus 1,
  not bus 0/2)
- **Physical diagnostics:** request `0x7A1` → response `0x7A9`
- **Application DIDs observed:** `F181` = `8965F1208000` + `8A3111213000`
  (count `0x02`, two records); `F186` = session; `F18C` = serial
  `8965012N50E12H030731`
- **13 application SIDs answer:** `10,14,19,22,23,27,2E,31,36,37,3E,AB,BA`
  (`11/28/34/85` absent from extended)
- **SecurityAccess level `0x03`:** seed returned in extended session; stable
  within a session, regenerates across sessions, session-gated (default → NRC
  `0x7F`). Level `0x01` → NRC `0x7E` in extended.
- **Earlier `10 02` programming request** to `0x7A1` produced an inconclusive
  timeout (no NRC); session after = `0x01`. The corrected 2026-08-21 direct
  route probe supersedes that ambiguity: `(bus 1,param 1)` opened PROGRAMMING,
  returned a SecurityAccess seed, accepted the key, and completed the requested
  range dumps.
- **`0x14`** crashes the diagnostic stack on subfunction probe.
- **`0x23`** validates addresses (NRC `0x31`) — unlike Sienna's inert echo.
- **2026-08-19 route preflight:** on a flipped Toyota-B harness, the EPS answered
  DEFAULT on logical bus 1 under **both** ELM327 `param=0` and `param=1`; buses
  0/2 were silent for the EPS probe. This is the first live proof that the
  `param=1` direct-harness route reaches this ECU. The preflight version then in
  use incorrectly chose `(bus1,param0)` by array order, so its PROGRAMMING and
  following range-dump failures were OBD/gateway-route measurements. Final
  `dump @ 42d1120` selects by actual PROGRAMMING reachability. The corrected
  **2026-08-21** run then selected `(bus1,param1)`, opened PROGRAMMING, unlocked,
  and captured CodeFlash/DataFlash/local/global RAM successfully.
- **SecOC:** sync ID `0x0F` observed; secured CAN IDs `0x2E4`, `0x131`,
  `0x344`. A 90-second READY capture saw 0 SecOC-signed EPS transmissions —
  consistent with ingress-only SecOC.

## Persisted firmware-static result from the Span dump

The tracked 2026-08-21 bundle contains a complete 2-MiB CodeFlash image. Its
observed application F181 remains `8965F1208000 / 8A3111213000`, while raw
CodeFlash identity strings include `8965H1213000` at `0x17D80`,
`8A3111213000` at `0x17DC0`, and `8965F1208000` at `0x20860`. The exact OEM
relationship between those two first-component identifiers is not assigned
until the F181 producer is recovered target-natively.

A deterministic byte-level comparison against the tracked albinoelephant
`8965H1202000` image is nevertheless decisive for the XCP/PROGRAMMING lifetime
question: **2,094,962 / 2,097,152 bytes (99.8956%) are identical at the same
addresses**, and every critical region for the retained-code-placement primitive
is byte-identical:

- generic XCP opcode map at `0x22A48` (including zero GET_SEED/UNLOCK entries);
- all 18 generic XCP callback words at `0x22A74`;
- LocalRAM bounds at `0x229C4` and shadow geometry at `0x2AE00`;
- the five H-family exclusion intervals at `0x28F0C`;
- packed standard-CAN `0x7F7/0x7F8` descriptors and receive callback pointers;
- application PROGRAMMING handoff caller at `0x5F208`;
- the complete 100-byte boot-entry stub at `0x9F00`;
- boot retained-state copier at `0x1472`; and
- reset-only LocalRAM initializer/clear body at `0x13E8`.

The exact `0x9F00` body still establishes `SP=FEBE8000`, `GP=FEBF9800`, boot
`TP=0x867C`, writes `MPM=0`, and calls `0x1472` without clearing
`FEBF7C00..FEBFFBFF`. The exact `0x5F208` handoff body reaches that stub without
a reset, while the reset-only `0x13E8` initializer is a separate path. Therefore
the Span image preserves the same composition already verified on
Sienna and tracked `8965H1202000`:

```text
no SecurityAccess
  -> XCP CONNECT / DOWNLOAD into FEBF7C00..FEBFFBFF
  -> UDS 10 02
  -> live application-to-boot handoff
  -> bytes remain resident in supervisor-executable LocalRAM, MPM=0
```

This is now a repository-**verified firmware-static** claim, checked by
`tests/verify_spanconstant_corolla_codeflash.py`. It establishes code placement
plus cross-lifecycle retention, **not** a no-auth PC redirection or complete RCE.

## Sienna-firmware-resolved interpretations of Corolla field observations

These are field observations whose *meaning* is now resolved by the Sienna
firmware analysis (`data/application_diagnostic_map.csv`, table indices
15/16/10). The service-table structure is Denso-family-stable: the Corolla
field probe sees exactly 13 SIDs answering — a subset of the Sienna's 17-SID
application table — and the four silent services (`0x11/0x28/0x34/0x85`) are
precisely those gated behind PROGRAMMING session on the Sienna.

- **`0xAB` is a proprietary event-record service, not a security path.**
  Sienna table index 15: an asynchronous event-record service with three
  subfunctions — `01` lists active event IDs, `02` queries one event,
  `03` queries event detail/snapshot. It reads checkpoint-backed state (75
  snapshot descriptors, 6 detail descriptors). Its presence on the Corolla
  confirms shared application-table structure but it offers no path to key
  material or memory access.
- **`0xBA` is an inert echo — a no-op.** Sienna table index 16: null callback,
  DSP disabled, echoes `SID|0x40 + request` via `0x8F6FA`. The Corolla
  investigation noted its behavior was anomalous (answering in one pass,
  `0x11` in another) — this is exactly what a no-op echo with
  session-dependent allow-lists produces. Nothing to exploit.
- **`0x34` silence is application-level, not a missing service.** Sienna table
  index 10: `0x34` RequestDownload is *also* a no-op simple-response in the
  application firmware (session allow `[2]` programming-only, null callback).
  The real `RequestDownload` logic lives in the **bootloader** (at `0x5D68`),
  unreachable without a PROGRAMMING transition. The Corolla's `0x34` silence is
  consistent with the EPS being in application mode. This resolves Corolla
  open question #2 ("why is `0x34` silent when `0x36`/`0x37` answer"):
  `0x36`/`0x37` are also application-inert echoes that happen to answer,
  while `0x34` is gated to programming session only and produces no response
  when that session cannot be entered.
- **The old `10 02` timeout was route-confounded, not a refusal.** The
  corrected 2026-08-21 `(bus1,param1)` preflight directly opened PROGRAMMING,
  received a seed, accepted the key, and completed range dumps. The older
  `(bus1,param0)` timeout remains useful only as evidence about the indirect
  OBD/gateway route.
- **The level-`0x04` send-key probe is non-diagnostic.** It used a bootloader
  secret (`f05f36…`), not the application secret (`893e08…`); NRC `0x35` is
  expected even on Sienna. Whether the Corolla shares the Sienna application
  SA secret (`893e08418c741ffa2a9c044bffa55813`) is **UNTESTED**.
- A reset-window probe found no bootloader acceptance during manual reboot.

## Diagnostic vocabulary: P4DK4 as a Corolla template

The Techstream DDB corpus includes `EPS_P4DK4.ddb` (JP region only), which is
the richest EPS database and a useful supplementary vocabulary source for
Corolla firmware analysis:

| Database | DTCs | Supported-PID rows | Freeze-data monitors | PID rows |
|---|---|---|---|---|
| NA `EPS_CAN_P4DK` | 30 | 8 | 75 | 32 |
| JP `EPS_P4DK4` | 26 (45 records) | 16 | 89 | 85 |

P4DK4 carries dual naming for most DTCs (formal + alternate name per code)
and adds 13 seq-derived candidate firmware-DID labels absent from the NA
database — e.g. torque-sensor-3 output (candidate `0x0138`), backup-power-supply
voltage (`0x0140`), and assist-map state (`0x0147`). These are structural
monitor-vocabulary candidates, not `CDbDidTable` rows or Corolla firmware
facts. They reflect JP-market EPS feature differences, not a temporal
generation gap: the Techstream V18.00.003 distribution (December 2022)
predates both the 2023 Sienna and the 2025 Corolla. With the Span dump now
persisted, running the correlation engine against both NA and JP databases can
test more candidate vocabulary than either alone.
