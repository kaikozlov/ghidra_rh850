# Corolla `8965F1208000` EPS comparative analysis

> **Scope:** Span's reported 2025 Toyota Corolla Hybrid EPS, observed F181
> `8965F1208000 / 8A3111213000`.
>
> **Status:** comparative static analysis closed to the same application-code
> boundary as the 2023 `8965H1202000` Corolla corpus; calibration meaning and
> remaining hardware-only questions are explicitly bounded below.
>
> **Evidence:** tracked raw acquisition + deterministic byte comparison + fresh
> target-native Ghidra structure + independent semantic resolvers + direct
> comparison with canonical Sienna `8965B4512000`.

## 1. Executive result

Span's 2025 image is not merely "similar" to the 2023 albinoelephant Corolla.
It is the **same executable/application generation with a different low
calibration/identity image**.

The normalized 1-MiB CodeFlash images differ in only **2,190 bytes**. Every
changed byte lies in `0xA004..0x17DFF`; from `0x17E00` through `0xFFFFF` the two
images are byte-identical. In particular:

- the complete high-CodeFlash CRC region beginning at `0x18000` is identical;
- the repository's application-function region `0x20000..0xFFFFF` is identical;
- a fresh clean Span Ghidra import produces the same 5,425-function structural
  fingerprint corpus as the clean H import, byte-for-byte, SHA-256
  `b7acbb2265b97d3811652d75900850b48d799eb5f0e59b7e14d0e6d4952b3051`;
- Span-vs-Sienna produces the same 6,375-row exact-body transfer result, the
  same 2,542 unique complete instruction-shape homologs, and the same 1,113-row
  named transfer ledger as H-vs-Sienna;
- the generated application Rx table, SecOC queue, Gate-2 verifier, runtime
  scheduler/COM anchors, diagnostics implementation, XCP implementation,
  steering supervisor, motor-control implementation, and NvM code therefore
  transfer at the **code/table** level from H to Span at the same addresses;
- low-region calibration/identity bytes remain a separate behavior boundary and
  are not silently promoted to semantic equality.

The most important openpilot consequence is also the same as for H: **do not
port the Sienna `0x2E4/0x131` steering bridge by assumption**. Span's resolved
Gate-2 queue is exactly `0x00F / 0x0D7 / 0x0B6`; the Sienna `0x2E4/0x131`
profiles are absent from both its normal-Rx table and its SecOC queue.

## 3. F181 is now statically reconciled

The raw image contains three nearby-looking identifiers:

| address | Span bytes | role |
|---|---|---|
| `0x17D80` | `8965H1213000` | separate one-record identity path |
| `0x17DC0` | `8A3111213000` | F181 secondary record |
| `0x20860` | `8965F1208000` | F181 primary record |

This ambiguity is closed by the H target-native producer, whose application body
is byte-identical in Span. `FUN_0004a328` constructs the two-record F181 result
from `0x20860` and `0x17DC0`. A separate producer `FUN_0004a2e0` uses
`0x17D80`. Therefore the live F181 response is exactly explained by Span's
firmware bytes; `8965H1213000` is **not** the F181 primary software ID.

The H/Span identity-consistency helper at `0x5C032` is also unchanged. Its only
meaningful direct changed-data reference in this neighborhood is the expected
secondary-ID difference at `0x17DC4`.

## 4. Direct 2023 Corolla comparison

The durable machine report is
`data/generated/corolla_8965F1208000_vs_8965H1202000_codeflash_equivalence.json`.
It is regenerated from both raw range dumps by
`tools/analyze_corolla_codeflash_equivalence.py`.

### 4.1 Exact byte boundary

Normalized first-MiB result:

```text
bytes compared                 1,048,576
identical                      1,046,386
different                          2,190
first difference                 0xA004
last difference                 0x17DFF
exact changed micro-runs             886
coalesced changed regions              18
```

No changed byte reaches the high-CodeFlash validity marker at `0x17E00` or the
second CRC-protected region beginning at `0x18000`.

The changed bands are confined to:

- low boot/calibration tables around `0xA004..0xA523`;
- calibration/parameter blocks under `0x10000..0x1236F`;
- one byte at `0x13E46`;
- identity records at `0x17D80` and `0x17DC0`; and
- the corresponding low-region CRC/fixup material through `0x17DFF`.

The serial at `0xA4DC` changes from albino's
`8965012N50A05G310920` to Span's `8965012N50E12H030731`.

### 4.2 Calibration caveat is real, not boilerplate

Exact executable identity does **not** imply equal vehicle tuning. The altered
`0xA0C0..0xA3C3` and `0x10000..0x1236F` material is retained as a calibration
boundary.

A direct-reference audit of the clean H application corpus found only two
classes of apparent references whose addressed bytes themselves change:

1. the real F181/identity read at `0x17DC4`; and
2. instructions represented by Ghidra as references to `0xA240`, where the
   machine operand is the numeric saturation constant `-24000`
   (`0xFFFFA240`) paired with `+24000` (`0x5DC0`), not a dereference of the
   changed table bytes at CodeFlash `0xA240`.

That is useful negative evidence against a simple direct application load from
those changed tables. It is **not** proof that all calibration material is
unused: generated calibration descriptors or indirect lookup machinery can
consume low data without a direct literal xref. Thresholds/gains/mode
calibration therefore remain target-specific unless the exact data bytes are
also equal.

### 4.3 Security roots are identical

The three established H roots are unchanged at the same addresses:

| role | address | Span/H value |
|---|---:|---|
| payload-build secret | `0xBFD8` | `ba052435f8843f985fd1329d2b6117b0` |
| boot SecurityAccess secret | `0xBFE8` | `f05f36b7d78c03e24ab4faef2a57d044` |
| application SecurityAccess secret | `0x20840` | `893e08418c741ffa2a9c044bffa55813` |

The application SecurityAccess root is also observed verbatim once at LocalRAM
offset `+0x17B80` in both Span snapshots, exactly as in all three albino PE1
snapshots. The payload-build and boot-SA roots are not found verbatim in Span's
retained DataFlash/extended-CodeFlash/GlobalRAM/LocalRAM captures.

This closes the earlier question of whether the application SA secret merely
*resembled* the Sienna/H family: Span contains the same root in the same
byte-identical application implementation.

## 5. Independent Span-vs-Sienna result

The Span image was not accepted by transitive reasoning alone. The same generic
Sienna comparison pipeline was rerun directly against Span.

### 5.1 Exact function-body census

`data/generated/corolla_8965F1208000_function_body_transfer.json`:


Every one of the 6,375 per-function classification rows and every relocation

Span-vs-Sienna raw-body relationship is not merely similar in aggregate.

### 5.2 Fresh target-native structural import

A clean Span Ghidra import independently recovered 5,425 target functions. Its
complete structural fingerprint JSONL was byte-for-byte identical to the clean
H import. Matching that fresh Span corpus against Sienna yielded
`data/generated/corolla_8965F1208000_structural_function_transfer.json`:

```text
unique complete instruction-shape homologs        2,542
...with >=8 instructions                           2,324
named unique-shape homologs                           264
named >=8                                             254
```

The complete 2,542-row match set is identical to H's. The joined named ledger,
`data/generated/corolla_8965F1208000_named_function_transfer_ledger.json`, is
also row-for-row identical:

```text

exact-byte transfer                288
unique-shape candidate             136

```

As with H, a unique instruction-shape match is a homolog candidate, not proof
that operands or calibration values are equal. Material H semantic promotions
remain backed by target-native H decompilation; Span's exact high-image bytes
make those *code* conclusions transferable, while §4.2 preserves the low-data
boundary.

## 6. Boot trust, programming, and authenticated RAM

Span exposes the same two self-describing valid CRC regions as H:

- low region `0x10000..0x17DF0`, whose content/fixup changes with the Span
  identity/calibration image;
- high region `0x18000..0xFFDF0`, byte-identical to H.

The SecOC Gate-2 patch lies in the unchanged high region. A fresh semantic
resolver independently finds exactly one candidate:

```text
verify function      0x88C16
Gate-2 compare       0x88C62
original bytes       e0 d1
replacement          e0 01
branch               0x88C64
verified fallthrough 0x88C66
```

The high-region stock CRC fixup remains `0xAD59D70C`; after the Gate-2 rewrite,
the deterministic replacement is `0xDD5F1477`, producing residue
`0xFFFFFFFF`. These are the same H values because that full region is exact.

Span also independently upgrades the authenticated-RAM bootstrap profile to
**observed**. Its field acquisition executed target-built range payloads through
the shared `0x0203 -> 0x0201 -> 0x0202`, `FEBF0000/0x1000`, `10F0`, `FF00`
family. `data/variant_bootstrap_profiles.json` now records this specimen
separately from H.

Evidence boundary: this does **not** prove byte-for-byte acceptance of the
repository's Sienna `ram_dump_payload.bin`; that exact fixture cryptographic
proof remains Sienna-specific. It proves that Span's target-built acquisition
used the same authenticated-RAM architecture and that its firmware roots/flow
match H.

The existing XCP retention result also survives unchanged: unauthenticated XCP
can place bytes in `FEBF7C00..FEBFFBFF`, and the live application→boot
PROGRAMMING handoff does not clear that supervisor-executable RAM. This remains
**code placement + retention**, not a recovered no-auth PC pivot.

## 7. Application COM/Rx and SecOC

### 7.1 Normal receive topology is exactly H

`data/generated/corolla_8965F1208000_application_rx_diff.json` is regenerated
from the raw Span image. Relative to Sienna:

- 39 normal-Rx descriptors are shared;
- the same eight Sienna descriptors are removed:
  `2E4, 191, 131, 2FD, 132, 423, 020, 1DA`;
- the only added descriptor is 32-byte CAN-FD `0x0B6`.

The entire 40-entry Span target descriptor table is byte-for-byte identical to
H's.

### 7.2 SecOC implementation transfers; steering profile does not

A fresh runtime/Gate resolver recovers the same three queue-1 records:

| CAN ID | secured length | generated PDU |
|---:|---:|---:|
| `0x00F` | 8 | 9 |
| `0x0D7` | 32 | 40 |
| `0x0B6` | 32 | 42 |

All three use the same H/Sienna-style protected ICU-S selector-4 configuration.
The SecOC verification implementation, DataID/payload/freshness construction,
CMAC submission, freshness/tag split, queueing, and command-7 plumbing are in
the byte-identical application and therefore transfer exactly at the code
level.

But **`0x2E4` and `0x131` are absent from Span's Gate-2 queue**, exactly as on H.
The resolved runtime manifest consequently reports
`semantic-resolved-steering-unsupported` for the Sienna bridge.

Historical vehicle-bus observations of secured `0x2E4/0x131/0x344` traffic must
therefore be kept separate from EPS configuration. Presence on the vehicle bus
is not proof that this EPS receives or authenticates those IDs. The persisted
2026-08-21 `can_oracle.ndjson` is empty, and the retained READY capture does not
supply a same-session SecOC oracle for those IDs. No Span-specific raw key or
CMAC-domain conclusion is claimed from that capture.

## 8. Diagnostics and XCP

Because the complete application image is identical to H, the target-native H
application diagnostic closure transfers at the implementation/table level:

- the same outer UDS stack and generated service/action structures;
- the same H RDBI/RoutineControl/WDBI callback surfaces;
- the same F181 producer resolved in §3;
- the same H `0x23` memory-read semantics and target-specific bounds;
- the same H XCP custom command table and callback bodies.

The XCP channel therefore retains H's established static properties at the same
addresses: physical `0x7F7/0x7F8`, no configured GET_SEED/UNLOCK, caller-selected
LocalRAM reads within H's five exclusion intervals, and generic DOWNLOAD/
MODIFY_BITS writes into `FEBF7C00..FEBFFBFF`. Custom E4 still copies
CodeFlash `0x10000..0x17DEF` into the shadow window.

This is a code/table transfer statement. Physical gateway reachability remains a
dynamic route question, and the low calibration bytes are not used to invent
new diagnostic semantics.

## 9. Steering and motor-control implications

Span carries the exact H application that was already decompiled stage-by-stage.
Therefore the H implementation-level conclusions transfer:

- the Sienna `0x131` LTA angle-command smoothing stage is absent/unpaired;
- the Sienna `0x2E4/0x131` normal receive modes are absent from generated Rx;
- the H/Span `0x0B6` FD interface is supervisory: gate/mode/sequence/scaling and
  validity state are recovered, while its only signed 16-bit scalar has no
  recovered direct runtime consumer as a torque command;
- the retained Sienna-shaped external torque clamp/rate branch exists in code
  but is zero-fed by the complete direct-writer evidence;
- the ordinary EPS steering supervisor and motor-control implementation remains
  substantial and active, including the recovered Clarke/Park, d/q PI,
  limiting, phase conditioning, duty publication/selection, and TSG3 commit
  chain;
- H's expanded plausibility/estimator machinery is present unchanged.

This does **not** mean every numerical control behavior is identical between the
2023 and 2025 vehicles. Low calibration material differs (§4.2), so gains,
thresholds or feature calibration can differ even where the code is exact.

For openpilot, the static problem is now narrower: there is no basis to reuse the
Sienna external steering ingress by ID. We need the actual 2025 Corolla command
provenance/interface, or proof that this generation exposes no remotely
commanded lateral mode through the mapped EPS Rx surfaces.

## 10. DataFlash / NvM comparison

The `R7F701383` has **32 KiB physical DataFlash**. Span's payload captured the
requested `FF200000..FF20FFFF` 64-KiB host range three times, but only the first
`0x8000` bytes are interpreted as physical DataFlash. The analyzer now supports
`--physical-prefix-size 0x8000` so provenance of the full host range is retained
without assigning NVM semantics to the upper half.

Tracked first-read report:
`data/generated/corolla_2025_span_dataflash_analysis.json`.

All three physical captures repeat the same high-level geometry:

```text
configured physical records             122
committed records                         61
triplicate records                         9
checkpoint records                        52
reference-enabled checkpoint envelopes    50
reference-disabled owner-28 envelopes       2  (117/118)
```

Objects `0`, `2`, and `5` each have three valid consensus copies in every Span
read. Object `15` has **zero valid copies in every read**. Objects `0` and `5`
retain the same consensus payload hashes as albino/Sienna; object `2` is stable
across all three Span reads but differs from albino's mutable state.

Relative to the tracked albino read, Span adds exactly one committed checkpoint
slot: **storage index 104**. The owner-28 disabled ring remains slots `117/118`,
with Span generations `0x35/0x34` versus albino's older `0x25/0x24` epoch.
This is consistent with the same NvM format carrying different vehicle/runtime
state, not a new storage architecture.

Physical first-32-KiB read-to-read byte differences are
`2860 / 3017 / 2934`; 28,430 of 32,768 positions are stable across all three
reads. Dynamic churn is therefore preserved rather than treated as firmware
version evidence.

Object-15 result boundary: the tracked CPU-visible triplicate geometry does not
contain a valid object-15 copy, just as on albino. Without a same-session Span
SecOC oracle this does **not** prove absence of the opaque ICU-S key or prove a
cryptographic key value.

## 11. Extended CodeFlash and RAM

Span's 48-KiB extended-CodeFlash dump has SHA-256
`90cc7b3d88e0c8b7ef330160ecb792134f5fbf9b9d8219c80d038a5451a15cc7` and is
**byte-identical to all three albino extended-CodeFlash reads**. This is an
additional invariant outside normal CodeFlash.

Runtime snapshots behave differently, as expected:

- Span GlobalRAM is 64 KiB; its differences versus the three albino GlobalRAM
  snapshots are only `867 / 854 / 907` bytes, comparable to albino's own
  time-to-time churn (`782..791` bytes).
- Span PE1 LocalRAM and the later self-alias LocalRAM are complete 128-KiB
  views and differ by 3,678 bytes.
- Span PE1 LocalRAM differs from the three albino PE1 snapshots by
  `6205 / 6793 / 7010` bytes; this is runtime state, not executable divergence.

Stable Span PE1/self-alias probes include:

- SecOC slot metadata at `FEBE6EC0`: `0022000003000000...`;
- zeroed candidate master/factory key buffers at `FEBE6E60` / `FEBF42E0`;
- zeroed object-15 RAM field and three work buffers at
  `FEBF02F8`, `FEBF0C28`, `FEBF0C48`, `FEBF0C68`;
- identity mirrors `8965H1213000` at `FEBFF980` and `8A3111213000` at
  `FEBFF9C0`.

These zeros are observed runtime-state facts, not proof that ICU-S lacks an
opaque protected key.

## 12. What is inherited from the H analysis

The correct evidence model is:

```text
Span raw bytes
  -> prove H equivalence boundary
     -> exact high/app bytes
     -> independent clean structural import
     -> independent Span-vs-Sienna body/Rx/resolver runs
  -> only then reuse H target-native semantic names at identical addresses
```

Accordingly, the detailed target-native H work in
[corolla-2023-us-public-route.md](corolla-2023-us-public-route.md) is the semantic
companion for Span. Its code-level conclusions transfer for:

- boot memory-safety and diagnostic mechanics;
- application diagnostics and generated callback tables;
- scheduler/system orchestration;
- CAN/COM transport and generated receive dispatch;
- XCP custom commands and memory boundaries;
- SecOC/ICU-S verify plumbing and selector-4 provenance;
- steering supervisor stage inventory;
- motor-control pipeline;
- storage/NvM restore code;
- deadline/plausibility/generated adapter families.

What does **not** transfer merely because code matches:

- low calibration values and their physical meaning;
- mutable DataFlash contents/generations;
- live ICU-S protected key state;
- physical bus/gateway reachability;
- hardware timing/permission behavior;
- an actuation interface that is absent from the generated H/Span Rx profile.

## 13. Remaining evidence boundary / next work

The broad static application RE is no longer an open task for Span. Repeating
H decompilation on identical bytes would add ceremony, not evidence. The
remaining high-value questions are narrower:

1. **Interpret the low calibration delta.** Map the changed
   `0xA004..0x17DFF` parameter blocks to OEM/Techstream names where external
   evidence permits. This can explain 2023→2025 tuning/feature differences
   without relabeling code.
2. **Find the real lateral-command provenance, if one exists.** The known
   Sienna `2E4/131` ingress is absent; B6 is not statically a replacement torque
   command. Use vehicle traces plus the already-closed COM/supervisor graph.
3. **Dynamic ICU-S policy only if needed.** Slot-4 command-5 permission/timing
   and any live cryptographic oracle remain hardware questions, not missing
   static reverse engineering.
4. **Runtime-retention geometry for an H/Span-specific RAM runtime.** The
   semantic resolver closes code anchors but intentionally reports no
   image-bound RAM-execution geometry for this variant. The Sienna runtime
   manifest must not be transplanted blindly.
5. **Correlate mutable NvM state only with a concrete feature question.** The
   storage format is closed; slot 104/object-2 differences are facts, but naming
   them requires independent state/Techstream evidence.
