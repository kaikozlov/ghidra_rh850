## DataFlash key field

The June 8 report identifies the successful 16-byte candidate at:

```text
absolute address: 0xFF206E14
offset from 0xFF200000: 0x6E14 = 28180
key SHA-256 prefix: 1d1c53a6d634016a
```

This repository independently maps `0xFF206E14` to the second 16-byte field of
32-byte NvM object 15 in `8965B4512000`; see
[`../storage/dataflash.md`](../storage/dataflash.md). The address agreement is
strong structural corroboration. It does **not** by itself prove that the
`4514000` descriptor table, RAM mirror, or redundant raw/XOR55/XORAA encoding
is identical: the completed partner dump was not available to inspect those
surrounding bytes.

## Reported cryptographic validation

The corrected synchronization input is:

```text
u16be(0x00F) || u16be(trip_cnt) || u20be(reset_cnt) || zero_pad4
```

Equivalently, the final three bytes are the big-endian representation of the
20-bit reset counter shifted left four bits. The ordinary protected input is:

```text
DataID_be16 || payload[0:4] || trip16 || reset20 || msg8 || reset_low2 || 00b
```

Both use the first 28 bits of AES-CMAC. This packing matches the independently
firmware-derived implementation in [`../../tools/toyota_secoc_signer.py`](../../tools/toyota_secoc_signer.py);
its synthetic known-answer suite passes 26/26 assertions. That independently
checks the algorithm and packing, **not** Vance's private key or raw captures.

The pinned June 8 report gives these final vehicle-data results:

| Stream | Matches | Evidence status |
|---|---:|---|
| synchronization `0x00F` | 1,024 / 1,024 | external report |
| protected `0x131` | 226 / 226 | external report |
| protected `0x2E4` | 225 / 225 | external report |
| protected `0x344` | 112 / 113 | external report |
| protected total | 563 / 564 | external report |
| later one-shot protected run | 730 / 750 | external report; failure distribution unavailable |

The 28-bit matches across multiple Data IDs are cryptographic evidence that the
same candidate is operational for those observed streams. The report also says
the key was applied on the partner vehicle successfully. This is evidence for
that vehicle and calibration; it does not establish family-wide key reuse or
key uniqueness.

## Superseded synchronization conclusion

Vance's May 22 report and its companion method note recorded `0/512` sync
matches and considered a different sync key or format. The June 8 report
identifies the cause as a verifier bug: `RESET_CNT` was packed incorrectly.
After correction, the same key validates `1024/1024` synchronization frames.
The May conclusion is retained only as investigation history and is
superseded, not an active hypothesis.

## Raw-artifact reproduction audit

The pinned Vance tree and the four supplied bundle archives were inspected for
completed partner outputs. The tree contains analysis code, deployment tools,
candidate tables from earlier work, and reports, but no target artifacts named
or shaped as:

```text
dump_*.bin
metadata.json
transcript*.jsonl
frames.csv
frames.jsonl
protected_frames.jsonl
sync_frames.jsonl
secoc_key_probe_results.json
secoc_key_probe_results.csv
```

The three `20260531_othersienna_secoc_bundle*` archives contain dump/capture
**tooling**, wrapper scripts, manifests, and two 4 KiB payloads. The
`TSS3_Capture_20260601.zip` archive contains read-only capture tooling and its
README. None contains a completed partner dump or capture output. The v3 README
explicitly instructs the partner to return separately generated output
directories; the candidate-f05 payload is retained as a non-default candidate.

Consequences:

- `0xFF206E14`, the key fingerprint, and all match counts remain pinned
  external-source observations rather than locally reproduced facts.
- The surrounding object-15 redundancy cannot be decoded for `4514000`.
- The sole `0x344` mismatch cannot be isolated or tested against alternate sync
  associations.
- The source and clustering of the later 20 misses in `730/750` cannot be
  determined.
- Recomputing CMAC from report prose would be circular and was not attempted.

## What the current evidence proves

- On the externally observed `8965B4514000` partner vehicle, the DataFlash
  candidate at `0xFF206E14` produced the reported key fingerprint and validates
  corrected sync plus protected `0x131`, `0x2E4`, and `0x344` traffic.
- The field address aligns with object 15's second field in the independently
  analyzed `8965B4512000` NvM layout.
- The same key authenticating both steering-related and PCS/AEB-related Data
  IDs is evidence for a broader observed ADAS SecOC security domain on that
  vehicle, not merely a narrowly named steering key.

## What the current evidence does not prove

- Whether `4514000` consumes object 15 directly in software.
- Whether it provisions ICU-S slot 4 and uses command 7 at runtime.
- Whether object 15 is only persistence/mirror state for an independently
  provisioned hardware key.
- Whether `4514000` EPS receives or transmits `0x344`.
- Which physical ECU originates `0x344` on the TSS 3 Sienna.
- Whether the key is per vehicle, per calibration, per model, per region, or
  reused more broadly.
- Any fact about `8965B4512000` beyond the separate firmware-static evidence in
  this repository. In particular, `0x344` remains absent from that image's EPS
  receive profiles and its object-15 copies remain invalid/uncommitted.
