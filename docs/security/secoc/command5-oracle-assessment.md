# ICU-S command-5 oracle assessment

> **Scope:** Toyota Sienna EPS `8965B4512000`, application context
>
> **Question:** can an unauthenticated tester use the EPS's protected ICU-S slot
> 4 to sign arbitrary SecOC traffic without learning the key?
>
> **Status:** the stock diagnostic test bank is a real chosen-input crypto
> interface, but it is **not a production SecOC signing oracle**. It fixes the
> command-5 message length to exactly 16 bytes and keeps the generated bytes
> private. The lower command-5 API is variable-length and is sufficient for the
> real 12-byte classic and 36-byte CAN-FD SecOC domains when invoked from
> application-context code. A bounded one-instruction length adaptation can turn
> the existing observer experiment into a classic-12-byte oracle if slot 4
> permits command 5 on hardware.

## 1. Executive verdict

The important distinction is between **cryptographic capability inside ICU-S**
and **what the stock diagnostic harness exposes on the wire**.

| Path | Authentication needed | Tester-chosen input | Length | Output | SecOC-signing consequence |
|---|---|---|---:|---|---|
| Stock RID `0x100F` bank, mode 1 | none | yes | exactly 16 B | local 16-byte compare only | **Not a direct SecOC signer** |
| Existing 6-byte observation patch | no Dcm SA for activation | yes | exactly 16 B | generated CMAC observable | 16-byte CMAC oracle only; still wrong domain length |
| Observer patch + `0x68B8A` length `16→12` | no Dcm SA for activation | yes | 12 B | first 12 MAC bytes observable | **Classic `0x2E4/0x131/0x132` signing primitive**, hardware permission still dynamic |
| Application-resident call through `0x88350→0x87CCC` | requires an application-context execution foothold | yes | 0..80 B | up to 16 B | **Covers classic 12 B and FD 36 B** if slot 4 permits generation |
| Stock RID `0x100F` bank, mode 0 | none | yes | exactly 16 B | local 16-byte compare only | Raw-AES test; expected to be rejected for a standard SHE MAC-use slot |

None of these paths reveals the 128-bit slot-4 key. A successful command-5 path
uses the protected key *in place*.

## 2. Stock activation is genuinely unauthenticated

The application RoutineControl table contains enabled RID `0x100F`. Its policy
has zero SecurityAccess entries and permits sessions 1/2/3. StartRoutine consumes
zero option bytes. The wire request is therefore:

```text
31 01 10 0F
```

The exact activation edge is:

```text
RoutineControl RID 0x100F
  -> application_routine_control_action_08_callback @ 0x8A782
     -> call @ 0x8A786
        -> crypto_test_bank1_activate @ 0x69018
```

Direct `ghidra-cli x-ref to 0x69018` returns that one call at `0x8A786`.
`0x69018` sets `FEBE508F=1`, initializes state `0x11`, clears the bank, and
snapshots the five COM update counters. It only arms from active state zero.

After activation, `crypto_test_bank1_can_input_collect @ 0x6875E` consumes:

| CAN | Content committed by the test bank |
|---:|---|
| `0x01B` | selector + mode |
| `0x01C`, `0x01D` | 16 chosen message bytes |
| `0x01E`, `0x01F` | 16 chosen expected-result bytes |

The bank requires three stable observations after the update is noticed before
committing the values. Once all five inputs are ready, state becomes `0x22` and
`crypto_test_bank1_state_step @ 0x68BC2` calls `icus_crypto_test_submit @
0x68B42`.

## 3. The stock command-5 request is fixed to exactly 16 bytes

Mode 1 at `0x68B42` is the MAC-generation arm. Direct Ghidra disassembly pins:

```text
0x68B86  ld.bu   crypto_test_runtime_key_selector, r1
0x68B8A  movea   0x10, r0, r9
0x68B8E  st.w    r9, DAT_febe5060
...
0x68B9A  movea   FEBE517A, gp, r8
...
0x68BAC  jarl    crypto_generate_driver_dispatch @ 0x88350
```

The recovered call is:

```text
crypto_generate_driver_dispatch(
    1,
    &config,                    // type 1, tester-selected slot at +4
    FEBE517A,                   // chosen message
    0x10,                       // input length
    FEBE51AA,                   // generated result
    &DAT_febe5060,              // output capacity, initialized to 0x10
    1)
```

Thus the stock diagnostic interface does **not** accept arbitrary message
lengths. It asks command 5 to MAC exactly 16 bytes.

The selector is genuinely tester-controlled. Direct xrefs to `FEBE5098` show
only reset, the CAN collector write, and the two reads in `0x68B42`; there is no
hard-coded substitution of slot 4 in the test bank. Setting selector `4` asks the
lower driver to use slot 4.

## 4. Why a 16-byte CMAC oracle does not sign the real SecOC messages

The six Sienna receive profiles authenticate these byte lengths:

```text
0x00F sync:                  7 bytes
0x2E4 / 0x131 / 0x132:     12 bytes
0x090 / 0x0D7 CAN-FD:      36 bytes
```

For the classic protected messages the input is:

```text
DataID_be16 || payload[4] || full_freshness[6] = 12 bytes
```

For the FD messages it is:

```text
DataID_be16 || payload[28] || full_freshness[6] = 36 bytes
```

AES-CMAC is length-sensitive. For a complete one-block 16-byte message `B`, the
final block uses CMAC subkey `K1`:

```text
CMAC_K(B) = AES_K(B xor K1)
```

For an incomplete 12-byte message `M`, CMAC appends the `0x80`/zero padding and
uses the *different* secret-derived subkey `K2`:

```text
CMAC_K(M) = AES_K(pad(M) xor K2)
```

Therefore asking for `CMAC_K(M || 00 00 00 00)` does not give
`CMAC_K(M)`. The unknown `K1/K2` relation is derived from `AES_K(0^128)` and is
not exposed by the fixed-16 CMAC service. A 36-byte CMAC additionally needs the
intermediate CBC-MAC chaining state across multiple blocks.

This is why the existing observer patch, by itself, exposes a useful 16-byte
CMAC oracle but **not** a production SecOC signing oracle.

## 5. Stock output is private; the existing observer patch changes only observation

On successful command-5 completion, the lower driver puts the result in
`FEBE51AA..FEBE51B9`. The stock completion callback `0x6926A` calls comparator
`0x69068`, which compares all 16 generated bytes against the tester-supplied
expected buffer at `FEBE518A..FEBE5199`.

Direct `ghidra-cli x-ref to 0xFEBE51AA` returns only:

- reset/zeroing at `0x67FAA`;
- use as the command-5 output pointer at `0x68BA4`;
- the local comparator read at `0x69072`.

There is no stock UDS/RMBA byte-return path for this buffer. A command failure
and a successful-generation/expected-value mismatch both eventually produce the
same terminal negative state and DTC `0x00D317`, so that DTC is not a MAC-byte
oracle.

`SEC-EXP-001` already provides a bounded observation-only experiment: it NOPs
the RID `0x1010` result-reader zero-fill branch and redirects the existing
48-byte copy source from `FEBE523A` to `FEBE51AA`. Those two sites total six
instruction bytes. They do not change the activation, selector, command ID, or
SecOC receive gate.

## 6. The lower command-5 API is not fixed to 16 bytes

The limitation belongs to the **stock test caller**, not ICU-S command 5 itself.
`icus_command5_mac_generate_prepare @ 0x87A94` accepts input length `param_3`
when:

```text
param_3 < 0x51
```

so the admitted range is 0..80 bytes subject to the normal non-null/output
checks. It stores:

```text
bit_length = param_3 << 3
selector   = config[4]
```

The serialized path is:

```text
crypto_generate_driver_dispatch @ 0x88350
  -> icus_command5_mac_generate_adapter @ 0x87CCC
     -> icus_command5_mac_generate_start @ 0x87C70
        -> icus_command5_mac_generate @ 0x89630
           -> ICUSCMD = (selector << 16) | 5
```

The result-copy worker `0x87B46` preserves caller output capacities at or below
16 and only clamps larger values down to 16. Therefore both production domain
sizes—12 and 36 bytes—are already supported by the stock lower software stack.
A small application-resident proxy can request the exact SecOC input length and
receive enough CMAC bytes to construct the transmitted 28-bit tag.

That is the real basis for the application-resident signing-proxy design. It is
stronger than the stock diagnostic bank, but it requires application-context
code execution or an equivalent hook.

## 7. A bounded one-instruction adaptation covers classic SecOC

There is an especially small bridge between the existing diagnostic experiment
and the 12-byte classic SecOC domain.

At `0x68B8A`, stock instruction bytes are:

```text
20 4E 10 00    movea 0x10, r0, r9
```

Changing only the immediate to `0x0C` gives:

```text
20 4E 0C 00    movea 0x0C, r0, r9
```

The same `r9` supplies the input-length argument and initializes the caller's
output-capacity cell. The generic prepare accepts 12. On successful completion,
`0x87B46` keeps output capacity 12 rather than rejecting it, so the first 12
CMAC bytes are copied to `FEBE51AA`. Twelve bytes is far more than the 28 bits
transmitted by Toyota SecOC.

Combined with the already-audited observation patch, this is a **three-site
classic-CMAC experiment**. It would make the chosen first 12 bytes from
`0x01C/0x01D` cryptographically congruent with the classic SecOC authenticated
input. The final four bytes in the 16-byte message buffer become irrelevant.

Two boundaries remain:

1. slot-4 command-5 permission must be observed on real P1M-E ICU-S hardware;
2. signing a useful frame still requires the correct live sender freshness.

The 12-byte output capacity also means the stock 16-byte expected-result
comparator will normally see stale/zero tail bytes and may report terminal
mismatch. That does not invalidate the generated prefix and does not matter to
the observation shim, but it is another reason not to treat the bank's terminal
state as the success criterion.

This report documents the mutation as a static experiment design. It does not
promote it to the production patcher.

## 8. CAN-FD still needs the generic path

The FD authenticated input is 36 bytes. Bank 1 exposes only 16 chosen message
bytes, so the one-instruction length change cannot provide the complete FD
message. The lower command-5 API accepts 36 bytes, but a caller must provide a
36-byte buffer. The application-resident proxy in `sender-implementation.md`
therefore remains the clean architecture for FD signing.

A different diagnostic buffer could in principle be repurposed, but that would
be a new patch/dataflow design and is not needed to establish capability.

## 9. Neighboring mode 0 is a stronger negative-control experiment

The same bank has mode `0`. It does **not** call command 5. `0x68B42` instead
calls the neighboring crypto dispatcher `0x88748` using the same tester-selected
slot and the same 16-byte message.

Its prepare function `0x8768E` explicitly requires input length exactly
`0x10`. The staged descriptor fixes the operation selector to the command-1 arm,
and the lower engine `0x8954C` supports ICU-S command 1/3 with software slot
selectors `0..14`. Its 16-byte output lands at `FEBE519A` and is compared against
the same expected buffer by `0x69042`.

Under standard AUTOSAR SHE semantics, command 1 is `CMD_ENC_ECB`. A key whose
`KEY_USAGE` marks it for MAC is not an encryption/decryption key, so slot 4
should reject this test. That makes mode 0 a valuable **negative control** for
slot-policy characterization.

The current command-5 observer image cannot directly observe this mode: mode 0
writes `FEBE519A`, while the existing RID-`0x1010` source redirect points at
`FEBE51AA`. A clean policy experiment therefore needs a separate observation
variant that redirects the same copy instruction to `FEBE519A` (GP-relative
displacement `0x999A`, encoded source instruction `24 96 9A 99`) or equivalent
driver-status instrumentation. The DTC alone remains ambiguous between command
rejection and successful AES followed by expected-result mismatch.

If P1M-E unexpectedly allows command 1 with slot 4, the impact is much larger:
an observed AES-encrypt oracle can calculate `AES_K(0^128)`, derive CMAC
subkeys `K1/K2`, and evaluate CMAC for arbitrary message lengths without ever
extracting the key. This outcome is not expected under standard SHE and is not
claimed.

## 10. Slot-4 permission: strong prior, still a hardware discriminator

Firmware proves that production SecOC verification selects ICU-S slot 4 and
issues command 7. It also proves that command 5 accepts selector 4 in software.
It cannot prove how the protected slot is provisioned internally.

The public AUTOSAR SHE specification defines `KEY_USAGE` as the distinction
between encryption/decryption and MAC generation/verification. Its
`CMD_GENERATE_MAC` service accepts an explicit message bit length and returns a
128-bit CMAC; `CMD_VERIFY_MAC` uses the corresponding MAC-key operation.

Renesas public P1M material describes ICU-S as SHE-compliant and explicitly says
it processes ECB/CBC plus **CMAC generation and verification**. That makes
slot-4 command-5 success the natural expectation if slot 4 is an ordinary
SHE-style MAC key.

However, “standard SHE has no verify-only flag” is not the same as “no real
implementation can add one.” Vector's SHE key-update documentation describes an
additional **CMAC USAGE** flag outside the basic SHE FID semantics that can make
a MAC-use key verification-only. This is evidence that a vendor extension can exist in a SHE-adjacent
implementation. It is not evidence that Renesas P1M-E implements that extension.

The correct confidence boundary is therefore:

- **firmware verified:** command 7 uses slot 4; command 5 software accepts slot 4;
- **external-source strong prior:** standard SHE and Renesas public ICU-S material
  support MAC generation as a normal service;
- **dynamic unknown:** this ECU's provisioned slot-4 policy/lifecycle actually
  accepts command 5.

A single application-context bench run can settle the last point.

## 11. Freshness remains independent of the crypto oracle

A CMAC oracle solves only the cryptographic operation. Valid Toyota SecOC frames
also require the sender to construct the same full freshness value the receiver
expects.

For classic `0x2E4`/`0x131`, that means maintaining the appropriate per-PDU
message counter while following the authenticated `0x00F` synchronization epoch
(trip/reset state). A successful command-5 result for the wrong freshness is
still the wrong tag.

Thus “no plaintext secret is needed” does **not** mean “no protocol state is
needed.” The sender-state design in `sender-implementation.md` remains required.

## 12. Recommended dynamic sequence

The safest information-gain order is:

1. fresh application boot; confirm exact F181 and diagnostic route;
2. activate stock bank 1 with `31 01 10 0F`;
3. run selector 4 / mode 1 with the existing observation patch and a 16-byte
   chosen message; record generated bytes, DTC state, completion latency, and
   command-7 contention;
4. on a separate fresh boot, use the mode-0 observation-source variant
   (`FEBE519A`, not the command-5 `FEBE51AA` source) and run selector 4 / mode 0
   as the expected-negative raw-AES policy control; do not infer rejection from
   the DTC alone;
5. only after command-5 success is established, test the bounded `16→12`
   instruction adaptation and compare the first 28 generated bits against an
   independently computed/observed classic SecOC frame;
6. if a production signer is desired, move to the generic 12/36-byte
   application-resident wrapper rather than growing the diagnostic patch.

No command-8 key update is required for any of these tests.

## 13. Security consequence

The most accurate statement is:

> The Sienna application exposes an unauthenticated, tester-controlled crypto
> test path to the ICU-S key selector. Stock mode 1 requests a 16-byte CMAC and
> compares it locally. This is not directly congruent with any configured SecOC
> authenticated-input length. The underlying command-5 driver, however, accepts
> the real 12-byte and 36-byte SecOC domains, and a one-instruction length
> adaptation is sufficient to make the existing observer experiment congruent
> with classic SecOC. If the provisioned slot-4 hardware policy accepts command
> 5, plaintext key recovery is unnecessary for signing.

That is a serious capability, but it is more precise than “any unauthenticated
tester can already sign anything with stock firmware.”
