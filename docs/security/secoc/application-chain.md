# Application SecOC receive chain and provisioned-unit experiment

> **Scope:** Sienna EPS `8965B4512000`
>
> **Document type:** subsystem analysis
>
> **Status:** active
>
> **Evidence profile:** mixed — claims carry individual grades; see FINDINGS SECOC-001..SECOC-008
>
> **Canonical artifacts:** —
>
> **Verification:** `tests/verify_secoc_application.py`
>
> **Related:** [key-storage](key-storage-and-lifecycle.md), [dataflash](../../storage/dataflash.md)

This note traces the application-side SecOC receive configuration in the
China-market Sienna EPS image `8965B4512000`. It also specifies the dynamic
experiment needed to determine how a **provisioned** `12000` unit relates the
CPU-visible object-15 key field to ICU-S key slot 4.

The central correction is that the premise “object 15 feeds the CMAC routine” is
not true for this image. Object 15 is a generic triplicate NvM object whose second
field is a field-verified key location on related variants, but this CodeFlash has
no static consumer of `0xFEBF02F8`. The active SecOC verification path resolves
CryptoIf handle 0 and selects **ICU-S key slot 4**.

The two functions that reference the embedded `FF*16` known-answer vector are
compiled out: both require fixed CodeFlash byte `0x30EF3` to equal `0x5A`, while
this calibration stores `0x00`. The vector is latent dead data and says nothing
about the live slot-4 key. Static evidence therefore establishes a
hardware-backed receive profile, but does not determine whether Lochuan's donor
slot was personalized, erased, or otherwise provisioned.

A separate, structurally paired **ICU-S command-5 MAC-generation family** is also
present. It accepts a runtime key selector, input pointer/length, output pointer,
and output-length pointer, and returns up to 16 generated bytes. Its software
validator accepts selectors `0..14`, so selector 4 reaches the hardware engine.
The only configured caller is a dormant, CAN-fed application crypto-test harness.
That harness has no recovered activation caller, compares the generated bytes
locally rather than transmitting them, and is not a production SecOC transmit
path. Static analysis therefore establishes the available crypto primitive but
not slot-4 hardware permission or an application-code execution foothold.

`../tests/verify_secoc_application.py` checks the configuration, routing,
disabled KAT gate, command-5/command-7 driver families, selector validation,
dormant test inputs, key-slot selection, freshness/MAC profile, and object-15
state directly from the committed images.

## 1. Six configured receive profiles

Application `tp` is `0x23EE4`. Six `0x50`-byte SecOC receive records begin at
CodeFlash `0x25970` (`tp + 0x1A8C`):

| CAN/Data ID | CAN format | Application RX PDU | Secured length | Trailer | Payload | Full freshness | Transmitted freshness | CMAC | Transmitted CMAC | CSM handle |
|---:|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| `0x00F` | classic | 11 | 8 | 8 | 0 | 36 bits | 36 bits | 128 bits | 28 bits | 0 |
| `0x2E4` | classic | 6 | 8 | 4 | 4 | 46 bits | 4 bits | 128 bits | 28 bits | 0 |
| `0x131` | classic | 26 | 8 | 4 | 4 | 46 bits | 4 bits | 128 bits | 28 bits | 0 |
| `0x132` | classic | 35 | 8 | 4 | 4 | 46 bits | 4 bits | 128 bits | 28 bits | 0 |
| `0x090` | CAN FD | 46 | 32 | 4 | 28 | 46 bits | 4 bits | 128 bits | 28 bits | 0 |
| `0x0D7` | CAN FD | 47 | 32 | 4 | 28 | 46 bits | 4 bits | 128 bits | 28 bits | 0 |

The hardware acceptance index maps to application PDU `6 + index`, exactly
matching the records' receive-PDU field:

```text
CAN 2E4: acceptance 0  -> PDU 6
CAN 00F: acceptance 5  -> PDU 11
CAN 131: acceptance 20 -> PDU 26
CAN 132: acceptance 29 -> PDU 35
CAN 090: acceptance 40 -> PDU 46
CAN 0D7: acceptance 41 -> PDU 47
```

`0x344` is different. It has no application RX acceptance rule, no SecOC record,
no aligned 32-bit literal in CodeFlash, and no statically assigned route in this
image. It may be transmitted by another ECU, transmitted by a related EPS, or
belong to a different calibration, but the external four-ID oracle must not be
projected onto this firmware as an EPS receive route.

## 2. Receive and authenticated-input data flow

The configured receive path is:

```text
CAN1 RX interrupt / queue
  -> application_can_normal_rx_demux @ 0x80006
  -> application_pdu_rx_router       @ 0x80C44
  -> SecOC ingress                    @ 0x8DC64
  -> record lookup                    @ 0x8E024
  -> queue/dispatch                   @ 0x8E0BE
  -> verification worker             @ 0x8E4BA
  -> split payload, freshness, tag    @ 0x8E1A8
  -> reconstruct full freshness       @ 0x8E8E6 / 0x8EECA
  -> build authenticated input        @ 0x8DB22
  -> CSM/CryptoIf wrappers            @ 0x8E3EA -> 0x88B6A/0x88B9C/0x88BA8
  -> lower crypto dispatch            @ 0x88556
  -> ICU-S CMAC-verify implementation @ 0x880DC -> 0x88080 -> 0x897F4
```

`0x8DB22` constructs the authenticated input as:

```text
DataID_be16 || authentic_payload || full_freshness
```

For `0x2E4`, `0x131`, and `0x132`, this is exactly 96 bits:

```text
2-byte CAN/Data ID || first 4 CAN bytes || 6-byte full freshness
```

For `0x090` and `0x0D7`, the same rule authenticates 28 payload bytes, producing
a 36-byte input. The `0x00F` synchronization frame has no authentic payload; its
input is the big-endian ID plus the five-byte, left-aligned 36-bit sync freshness.

The trailer is bit-packed rather than byte-separated:

- normal profiles: 4 freshness bits followed by the 28 most-significant CMAC bits;
- sync profile: 36 freshness bits followed by the 28 CMAC bits;
- consequently a classic protected frame is `payload[0:4] || freshness_nibble || tag28`;
- a sync frame is `trip16 || reset20 || tag28`.

The 28-bit value occupies the low nibble of byte 4 and bytes 5–7 in an eight-byte
frame. This matches the independent CAN oracle, but the static evidence above is
sufficient to establish the configured widths and bit extraction.

## 3. Freshness representation

`0x8EA4C` packs normal full freshness into six bytes as 46 meaningful bits followed
by two zero pad bits:

```text
trip_counter[16]
|| reset_counter[20]
|| message_counter[8]
|| reset_counter_low2[2]
|| 00b
```

Equivalently:

```python
freshness = pack_be16(trip) + pack_be32(
    (reset20 << 12) | (message8 << 4) | ((reset20 & 3) << 2)
)
```

The ordinary transmitted four-bit FreshnessValue is separately packed as
`message_counter_low2 || reset_counter_low2` in the high nibble of trailer byte 0.
`0x8EBC2` splits those two fields; `0x8EE5C` combines them with the receiver's
retained trip/reset state and counter window to reconstruct a candidate full value.
The transmitted nibble is therefore not simply a contiguous four-bit slice of the
six-byte full-freshness representation.

The `0x00F` synchronization profile transmits the 36-bit prefix directly:

```text
trip_counter[16] || reset_counter[20]
```

Successful authentication commits the reconstructed freshness through
`0x8E942`, with normal and synchronization state handled by `0x8F084` and
`0x8F112` respectively.

## 4. The CMAC key is ICU-S slot 4, not an object-15 pointer

The SecOC crypto configuration initialized at `0x25950` is:

```text
algorithm/type word = 1
ICU-S key selector  = 4
remaining bytes     = 0
```

`0x8DF0E` copies this record into the job configuration. `0x87F70` reads byte
`config + 4` and places it in the ICU request descriptor. `0x897F4` then starts
ICU-S command `7` (MAC verify) by writing:

```text
FFC5D000 = (key_slot << 16) | 7
```

The CPU supplies the authenticated message, its bit length, the received tag,
and the 28-bit tag length. It does **not** supply key bytes. No instruction in
this chain reads `0xFEBF02F8`, and no direct or generic object-15 owner call was
found outside the redundancy framework.

### Compiled-out slot-4 known-answer check

Code at `0x680F8` and `0x682A6` contains a fixed 16-byte KAT vector for the same
ICU-S slot-4 selector:

```text
message @ 0x215E4: 00000000000000000000000000000000
CMAC    @ 0x215F4: B290FA2EA7B6B52EB124134522A6E540
config  @ 0x21604: type 1, slot 4
```

The embedded tag is exactly:

```text
AES-CMAC(key=FFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF,
         msg=00000000000000000000000000000000)
```

Neither crypto body executes in this calibration. Both begin with the same
fixed-byte gate:

```text
load CodeFlash[0x30EF3]
compare with 0x5A
branch over crypto body when unequal
```

`CodeFlash[0x30EF3]` is `0x00`, so both functions branch directly to their
report-only tails. Command 7 is never issued by this KAT path. The fact that the
dead vector happens to equal the `FF*16` CMAC places no constraint on protected
slot 4 and cannot support an erased/default-key inference.

All six live receive profiles pass CryptoIf handle `0` from record offset
`+0x20`. `0x88508` resolves this to lower record 0, whose callback is `0x880DC`.
Verify record 1 is referenced only by the disabled asynchronous KAT body. The
values `8` and `32` at profile offset `+0x24` are buffer/PDU lengths, not job IDs.
Thus the live generated receive path reaches the ICU-S command-7 verify adapter.

## 5. ICU-S command 5 is the MAC-generation twin

The firmware contains a second two-record lower-driver table at `0x27F78` and a
complete operation family paired with command 7:

| Stage | Command 5 | Command 7 |
|---|---:|---:|
| request preparation | `0x87A94` | `0x87ED0` |
| start wrapper | `0x87C70` | `0x88080` |
| lower-driver adapter | `0x87CCC` | `0x880DC` |
| completion worker | `0x87DD0` | `0x881DC` |
| hardware engine | `0x89630` | `0x897F4` |
| normal completion callback | `0x88B5C` | `0x88C0A` |

Command-5 preparation stages the input, retains a caller-provided output buffer
and output-length pointer, loads the key selector from `config + 4`, and clamps
the returned output to 16 bytes. The engine writes:

```text
FFC5D000 = (runtime_key_selector << 16) | 5
```

On successful completion, `0x87B46` copies the generated 16-byte ICU result to
the caller. The only direct upper caller, `0x68B42`, selects command 5 when its
runtime mode byte is 1 and passes:

```text
selector:       RAM 0xFEBE5098
input:          RAM 0xFEBE517A, 16 bytes
expected:       RAM 0xFEBE518A, 16 bytes
generated out:  RAM 0xFEBE51AA, capacity 16
```

Its asynchronous callback `0x6926A` calls `0x69068`, which compares all 16
generated bytes with the expected buffer. Together with the type-1 crypto
configuration and the immediately paired command-7 CMAC-verification family,
this substantially recovers command 5 as **MAC generation**.

The engine checks that the runtime selector is at most `14`; selector 4
therefore passes every recovered CPU-side validation before `ICUSCMD` is
written. This proves software reachability of the slot number, not the ICU-S
slot's operation policy. Only a live command-5 submission can show whether the
provisioned hardware accepts generation with slot 4.

### 5.1 Dormant CAN-controlled crypto-test bank

The sole configured caller belongs to a generated test bank, not the SecOC
receive stack:

```text
periodic task 0x65750
  -> crypto test scheduler 0x68C0C
  -> bank-1 state step 0x68BC2, only when FEBE508F == 1
     state 0x11 -> collect stable COM inputs at 0x6875E
     state 0x22 -> submit command 5 at 0x68B42
     completion -> compare result at 0x6926A -> 0x69068
```

The input collector requires three identical COM updates before committing:

| CAN ID | Signal IDs | Test-bank use |
|---:|---:|---|
| `0x01B` | 95, 96 | runtime key selector and mode |
| `0x01C`, `0x01D` | 97, 98 | 16-byte chosen message |
| `0x01E`, `0x01F` | 99, 100 | 16-byte expected result |

The five PDUs use update-counter indices `20..24`. Their committed state is:

```text
FEBE5098       runtime key selector
FEBE5099       mode; 1 selects command-5 generation
FEBE517A..189  chosen 16-byte message
FEBE518A..199  expected 16-byte result
FEBE51AA..1B9  generated 16-byte result
```

`crypto_test_bank1_activate @ 0x69018` is the only recovered function that sets
`FEBE508F=1`; it initializes state `0x11`, clears the bank, and snapshots the
five COM update counters. It has no recovered direct caller and neither it nor
the command-5 dispatcher `0x88350` appears as a CodeFlash function pointer.
Consequently ordinary receipt of `0x01B..0x01F` cannot arm the stock image:
those frames only populate input after some as-yet-unrecovered path activates
the bank.

The stock completion path does not export a signing oracle. It compares all 16
generated bytes against the CAN-supplied expected buffer. Equality returns
`0x33`; mismatch returns `0x44` and latches the bank failure at `FEBE5097`
through `0x68D0E`. No generated MAC bytes are routed to CAN.

### 5.2 Application-context access and contention

Code already executing after normal application initialization has a suitable
driver route:

```text
upper dispatcher 0x88350
  -> generated CryptoIf serialization
  -> shared lower ICU-S lock
  -> command-5 adapter 0x87CCC
  -> engine 0x89630
  -> EIINT 292/293
  -> interrupt completion 0x87C14
  -> result copy and callback
```

Startup `0x65626 -> 0x88C4C -> 0x8735E` initializes that driver state. The
wrapper arbitrates the same lower device used by command-7 verification and
handles busy/completion state, so an application-resident payload should use
the wrapper rather than write ICU registers directly.

No existing diagnostic upload route supplies that execution context. Application
SIDs `0x34/0x36/0x37` have null callbacks and simple responses, and the recovered
`0xAB` routine table has no edge to the test-bank activator or ICU generation
dispatcher. The public bootloader callback payload instead runs with different
GP/TP, RAM, interrupt, and peripheral-driver state. It is therefore not a safe
substitute for an application-resident hook without reproducing initialization
and excluding driver contention.

### 5.3 No configured SecOC transmit path

The command-5 upper dispatcher has exactly one direct call, from `0x68B42`, and
no CodeFlash function-pointer entry. The recovered SecOC configuration and
function graph are receive-only. The six ordinary COM transmit PDUs are
`0x260/0x262/0x351/0x394/0x4A3/0x4C8`; none passes through command 5 or a SecOC
transmit wrapper. Thus this calibration has no statically configured production
SecOC transmit path to repurpose.

A practical signing proxy would still need:

- a live proof that protected slot 4 permits command-5 generation;
- an application-context execution foothold;
- a new result transport or an in-EPS frame-transmit hook;
- sender-side freshness state and scheduling; the recovered state is receiver
  freshness and cannot simply be reused for forged transmit traffic;
- latency and contention measurements under normal command-7 receive load.

## 6. Why all object-15 copies are invalid

Object 15 remains structurally definitive:

```text
length 32, base NvM block 41, RAM mirror 0xFEBF02E8
raw:   block 41 / page 440 / key field 0xFF206E14
XOR55: block 45 / page 436 / key field 0xFF206D14
XORAA: block 49 / page 432 / key field 0xFF206C14
RAM second field: 0xFEBF02F8
```

In this dump:

- none of blocks 41/45/49 has the expected physical header and committed
  `AAAAAAAA` trailer;
- decoding the three payloads with raw/XOR55/XORAA does not produce a consensus;
- objects 12, 13, and 14 are also wholly invalid, so this is the state of the
  entire optional 32-byte bank rather than isolated corruption of object 15;
- the raw candidate field is low entropy and matches no captured CMAC oracle;
- no application owner reads or updates object 15 through IDs `0x0F`/`0x10F`.

Together these facts establish that the CPU-visible optional NvM bank is invalid
in this dump. They do **not** establish the state of protected ICU-S slot 4,
because the active verify path does not consume object 15 and the only static KAT
is disabled. A personalized nonvolatile ICU-S slot, an unprovisioned slot, a
masked/incomplete acquisition, and a different production policy remain
distinguishable only by dynamic measurement.

A separate address correction follows from the application GP value
`0xFEBEB800`: the restore work-buffer root is `gp + 0x5308 = 0xFEBF0B08`, **not**
`0xFEBFEB08`. Object 15 uses group `15 & 3 = 3`, hence:

```text
raw destination:   0xFEBF0C28
XOR55 destination: 0xFEBF0C48
XORAA destination: 0xFEBF0C68
```

The persistence source buffers at `0x67608` are `0xFEBF06A8/06C8/06E8`.

## 7. Correct dynamic experiment on a provisioned `12000`

The experiment must correlate NvM **submission and asynchronous completion**,
CPU RAM, post-write DataFlash, ICU slot selection, and CAN behavior. An entry hook
at `0x72F58` alone is not sufficient.

### 7.1 Preconditions and baseline

1. Record the exact CodeFlash/DataFlash hashes and software ID. Do not combine
   results from a `14000`, a different `12000` calibration, or a modified image.
2. Save a complete pre-test 32 KiB DataFlash image.
3. Capture timestamped CAN/CAN-FD frames with bus, ID, DLC, flags, and full payload.
   Include `0x00F`, `0x2E4`, `0x131`, `0x132`, `0x090`, `0x0D7`, and external
   candidate `0x344`; do not assume `0x344` is an EPS receive route.
4. Start from a true cold boot so NvM restore and ICU initialization are observed
   from the beginning. Confirm that both compiled-out KAT functions skip their
   command-7 bodies as the static `0x30EF3=0x00` gate predicts.

### 7.2 NvM restore instrumentation

Log these events with monotonic timestamps and call stacks:

1. `secoc_nvm_restore_triplicate @ 0x67590`, filtered to object index 15.
2. `nvm_read_block_submit @ 0x72F58`, filtered to blocks **41, 45, and 49**.
   Record block ID, destination pointer, immediate return, and request/queue ID.
3. `secoc_nvm_triplicate_read_complete @ 0x67C34` for those three blocks.
   Record the completion status argument and snapshot the corresponding destination
   only after completion—not at submit time.
4. When reconciliation returns completion (`0x5A`), dump:
   - `0xFEBF0C28..0xFEBF0C87` (object-15 raw/XOR55/XORAA work group),
   - `0xFEBF02E8..0xFEBF0307` (RAM mirror),
   - `0xFEBF02F8..0xFEBF0307` (candidate key),
   - object-15 validity/status byte `0xFEBF0367`.

Verify independently that raw, `XOR55 ^ 55`, and `XORAA ^ AA` agree before calling
the mirror field a key.

### 7.3 Update/persistence instrumentation

Monitor for the full test period, including any legitimate provisioning action:

1. `secoc_nvm_object_update @ 0x65CD8` and
   `secoc_nvm_redundant_object_update @ 0x66E48`, filtered to object 15
   (namespace ID `0x10F`). Record the caller and 32-byte source.
2. `secoc_nvm_persist_triplicate @ 0x67608`, filtered to index 15. Snapshot
   `0xFEBF06A8`, `0xFEBF06C8`, and `0xFEBF06E8`.
3. `nvm_write_block_submit @ 0x72F84`, filtered to blocks 41/45/49, plus the
   corresponding asynchronous completion/status events.
4. After confirmed write completion and power-cycle, acquire a second full
   DataFlash image and verify physical headers, trailers, three-way decode, and
   restore into `0xFEBF02E8`.

This identifies the actual diagnostic/RTE caller if provisioning occurs; it does
not mislabel a generic NvM API as a dealer key-set command.

### 7.4 ICU and CAN correlation

1. Confirm that `0x680F8`/`0x682A6` branch directly to their report tails and do
   not submit an ICU job.
2. At `ICU MAC verify @ 0x897F4`, record command, key-slot selector, authenticated
   input pointer/bit length, received-tag pointer/bit length, and result. The
   expected selector is 4; ICU key bytes are not CPU-readable through this API.
3. Establish an application-resident hook only after startup has initialized
   the ICU driver. Submit a chosen message through upper dispatcher `0x88350`,
   lower record 0, type 1, selector 4, output capacity 16. Do not call
   `0x89630` directly. Wait for the normal callback and record immediate status,
   completion status, full output, latency, and any command-7 contention.
4. Feed the generated result to command 7 with the same selector/message. A
   successful generate/verify round trip proves operation compatibility without
   exposing the key. A command-5 policy rejection paired with successful live
   command-7 verification proves that slot 4 is verify-only.
5. Validate any object-15 candidate `K`, and any command-5 output, against
   multiple synchronized CAN samples:
   - sync input: `be16(0x000F) || trip16 || reset20<<4`;
   - classic protected input:
     `be16(CAN_ID) || payload[0:4] || freshness48`;
   - FD protected input:
     `be16(CAN_ID) || payload[0:28] || freshness48`;
   - compare the first 28 CMAC bits with the packed frame tag.
6. Require repeated matches across sync and protected frames, not one accidental
   28-bit match. Keep `0x344` as a separate oracle class until its transmitter and
   direction are independently established.
7. If generation works, separately measure whether a patched application can
   transport results or transmit complete protected frames while maintaining
   sender freshness and deadlines. The dormant stock harness proves neither.

### 7.5 Outcomes that distinguish the hypotheses

| Observation | Interpretation |
|---|---|
| Valid 41/45/49 consensus; RAM field matches CAN oracle and command-5 output | Object 15 represents the operational slot-4 SecOC key on that unit/calibration |
| Object 15 remains invalid; slot-4 command-5/command-7 round trip and CAN verification succeed | Operational key is protected in ICU-S or another source; object 15 is unused |
| Valid object 15 but it fails command-5/CAN oracle comparison | Object 15 belongs to another key domain or stale provisioning state |
| No 41/45/49 submissions despite the descriptor | Runtime policy/configuration disables object-15 restore |
| Writes appear only after a specific caller/action | That caller is the provisioning trigger; capture it rather than inferring a dealer command |
| Command 5 rejects slot 4 while command 7 verifies live traffic | Slot policy is verify-only; the signing-oracle route is closed |
| Both commands work only after application initialization | ICU access is lifecycle/context bound; a bootloader payload needs application-resident execution or equivalent initialization |
